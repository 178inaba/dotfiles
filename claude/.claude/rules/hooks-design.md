# フック・シム・許可ルールの設計意図

各フックと、フックと同じ役割を PATH 上で担う shim、および形そのものが不変条件を担っている `permissions.allow` のルールについて、「何を防ぐために存在するか」の記録。挙動を変更する前に、その事故が再発しないかを確認する。

- `~/.local/shims/gh` (PATH shim、ソース: `go/cmd/gh` + `go/internal/ghshim`。`stow` ではなく `GOBIN=~/.local/shims go -C go install ./cmd/gh` で置かれる) — `gh` の書き込み系サブコマンドで対象リポジトリの明示を必須化し、別リポジトリへ `cd` した状態で意図しないリポジトリに Issue/PR を作成する事故を防ぐ。守る不変条件は「対象リポジトリが cwd 由来の暗黙解決でないこと」で、`-R/--repo` はその十分条件の1つに過ぎない（`gh repo edit` 等は `-R` を持たず位置引数でリポジトリを取り、`-R` を持たないサブコマンドでは `GH_REPO` も効かないため、`-R` の存在で実装すると満たしようのない要求になり、迂回（`gh api` 直叩き）を誘発する）。判定は noun 別の通過条件で行う。**フックではなく shim なのは、PreToolUse が受け取るのが実行前のコマンド文字列で、そこからは「実際にどのコマンドが走るか」を決められないため**。文字列マッチには見逃し（1つの `-R` が同じ行の全 write を覆う）と過剰ブロック（引用符・heredoc 内のリテラルを write とみなす）の両方があり、いずれもパターンの改良では消えなかった。shim はシェルが渡す実 argv を読むので、どちらも成立しない。判定は `CLAUDECODE` が設定されているときだけ行い（対話シェルの挙動は変えない）、read サブコマンドは判定前に exec する。ブロックは `exit 78`（`gh` 自身の 0/1/2/4 と衝突しない値）で、判定中の内部エラーも exec せずブロックに倒す。**同じ shim が本文系の 3 ルールも担う**（元は `PreToolUse` フックが持っていたが、コマンド文字列を見るために本文と無関係な heredoc の改行で誤爆しており、argv を読む位置へ揃えた）: 複数行の本文をインラインの本文フラグ（`--body`/`-b`・`--notes`/`-n`・`--comment`/`-c`）で渡すことをブロックしてファイル代替へ誘導し、引用符レイヤの重なりによる誤エスケープで本文にリテラルの `\` が残る事故を防ぐ（誘導先は verb ごとに違うため復旧手順も出し分ける。`gh issue close` / `reopen` と `gh pr close` / `reopen` は `-c/--comment` が唯一の本文フラグでファイル代替を持たないので、本文を `gh <noun> comment --body-file` で別途投稿してから `-c` なしで実行する形へ誘導する）。本文中に項番とみられる素の `#N` の連番を検出した場合もブロックし、無関係な Issue/PR へ参照通知（mentioned 表示）が飛ぶ事故を防ぐ。`gh pr create` / `gh pr edit` の本文中にバッククォートで囲まれた実番号付き closing keyword（`Closes #N` 等）を検出した場合もブロックし、closing keyword が解釈されず Issue が自動 close されないまま残る事故を防ぐ。本文は verb ごとに定義した本文フラグの値から読む（同じ `-b` が verb によって `--base`・`--branch` を意味するため、フラグ名だけでは本文を特定できない）。**本文フラグ表に載せるかは綴りではなく「GitHub が markdown としてレンダリングする本文を運ぶか」で決める**（ルール2〜4 が防ぐ事故はいずれもレンダリングされる本文でしか起きないため）。この軸で `gh label create|edit --description` と `gh repo edit --description` は表外 — プレーンテキストとしてレンダリングされ、素の `#N` が autolink しない。**フェイルクローズ方針への唯一のカーブアウトは、本文を stdin 綴り（`--body-file -`）で渡したときの fail open**で、届く範囲は後ろ 2 つのルールだけ。shim が stdin を読むと `gh` が読むはずの分を消費してしまい、走査と両立しないため諦めている。**名前付きパスが読めない場合（欠落・通常ファイルでない・権限なし）はブロックする**（`gh` 自身も本文ファイルを API に触れる前に読むので、ブロックによって成功したはずのコマンドは失われない）。当初はここも「ファイルはこれから書かれることがある」として fail open だったが、`-F=path` の解析ずれで本文ルールが無警告でスキップされる事故（#71）を起こしたため、カーブアウトを stdin 限定に狭めた — カーブアウトの安全性は「shim の解析 = pflag の解析」に依存しており、手写しの値取りフラグ表がずれるたびに無警告で fail open するため。**同じ shim が review thread の返信・解決（ルール5）も担う**: `gh api` の GraphQL mutation `addPullRequestReviewThreadReply` / `resolveReviewThread` と、REST `POST repos/{owner}/{repo}/pulls/<n>/comments/<id>/replies` をブロックし、`ccx pr reply-threads`（path + line でスレッドを指し、セレクタを検証してから投稿する）へ誘導する。防ぐのは、手打ちの返信が resolve されないまま Copilot のスレッドを1日 open のまま残した事故と、opaque な `PRRT_…` id の取り違えで隣のスレッドへ返信した事故（#140）。**スキル文言ではなく shim なのは、事故がスキルの外で起きたため** — スキル実行の合間に手で叩かれたので、SKILL.md をどう直しても届かない。`gh api` は verb を持たない（`argv[1]` はエンドポイント）ので `writeVerbs` の行にできず、noun での分岐を write 判定より前に置く。ルール1（リポジトリ明示）は適用しない — エンドポイント自身がリポジトリを名指すため。エンドポイントは正規化してから照合する（URL はパスへ還元 → 先頭 `/` → GHE の `api/v3/`・`api/` の順で除去。`graphql` と `https://api.github.com/graphql` が同じになる）。REST 側は method が POST のときのみ（`-X`/`--method` の明示、または `-F`/`-f`/`--input` があるときの gh の暗黙 POST。明示が優先するので `-X GET` は通る）。GraphQL のクエリ本文は `-F`/`-f` の `query` キーと `--input` の JSON から集め、読めないファイルはブロックに倒す（カーブアウトは本文ルールと同じ stdin 綴り `--input -` / `-F query=@-` のみ。JSON でない・`query` キーが無い `--input` は gh に委ねる）。`unresolveReviewThread` は識別子の境界判定で通す（スコープ外）。**`ccx` 自身はこの shim にブロックされない** — `go/internal/ghapi` が go-gh の HTTP クライアントで in-process に叩くため。唯一 `gh` を起動しうるのは go-gh のトークン解決（env・gh の config にトークンが無いときの `gh auth token --secure-storage`。`ghapi.go` の `New` のコメント参照）だが、これは read なのでどのルールも判定せず素通りする。許可リストの類は要らない（検出条件・値取りフラグ表・本文フラグ表の詳細は `go/internal/ghshim` のパッケージコメントと `rules.go` 参照）
- `ccx hook no-op-wait-guard` (PreToolUse) — 完了待ちを目的とした no-op コマンド（`echo idle1`・`sleep 1; echo waiting`・`true`・`sleep 5m` 等）をブロックし、ターンを終えて完了通知で自動再開する経路へ誘導する。防ぐのは、バックグラウンドのコマンド・タスク・サブエージェントの完了を待つ間、ターンを終えずに no-op Bash 呼び出しを数秒間隔で反復する busy-wait（1 セッションで 541 回の実測。トークンの浪費とトランスクリプトのノイズに加え、「親はターンを終えて待つ」前提で通知を抑止する `ccx hook idle-notify` のガードも無効化する）。**閾値方式ではなく 1 回目の呼び出しでブロックする**のは、ループ内に thinking が無く 2 回目以降は反射的コピーになるため、ターンを終える選択が残っている点が 1 回目しかないから。**文言（SKILL.md・CLAUDE.md 等）での対策を採らない**のは反証済みだから: 同種の文言修正を入れたセッションで再発し、その文言をロードしない `/issue-draft` セッションでも発生した。ハーネスの Agent ツール説明が既に正しい振る舞いを記述しており、モデルは指示を欠いているのではなく無視しているため、プロンプトレベルのルールには作用する余地がない（検出条件・除外・fail-open の詳細、および 1 回目でブロックする理由の詳細はフックのパッケージコメント参照）
- `ccx hook worktree-edit-guard` (PreToolUse) — session cwd が linked worktree 内なのに Edit/Write/NotebookEdit の対象パスが同一リポジトリの worktree 外（メインツリー本体・別 worktree）を指す場合にブロックし、worktree 側の対応パスへ誘導する。EnterWorktree は session cwd を切り替えるがツールに渡す絶対パスは自動変換されないため、切替前の調査で Read したメインツリー絶対パスを Edit に流用してメインツリーを誤修正する事故を防ぐ（Read はどちらのツリーでも同じ内容が返るため直前まで気付けない）。所属ツリーは `git worktree list` で分類し、どのツリーにも属さないパス（scratchpad 等）は対象外。dir symlink 経由でツリー内を指すパス（stow の `~/.claude/skills/...` 等）は物理化されブロック対象になるが、ファイル単体の symlink は解決せず素通りする（既知の限界）
- `ccx hook skill-frontmatter-check` (PostToolUse) — 保存された SKILL.md の frontmatter を検査し、違反を stderr に並べて `exit 2` で返す。防ぐのは、標準の YAML として壊れた frontmatter が誰にも気付かれずに main へ入ること — Claude Code のパーサーが寛容でスキル自体は読み込めてしまうため、壊れに気付ける契機が「編集中に誰かが目視で気付く」か「検査コマンドを覚えている人が手で走らせる」しかなく、実際に壊れた `argument-hint` が 2 ファイル分そのまま残った。**PreToolUse ではなく PostToolUse なのは、編集後のファイル内容をペイロードから得る公式手段が無いため**（hooks ガイド・リファレンスのいずれにも無い）。PreToolUse 版は `old_string`/`new_string` を自前で再適用することになり、ハーネス挙動の再実装になる（`ccx hook worktree-edit-guard` が `git worktree list` での分類に倒して避けているのと同種の推測）。代償として**書き込みは取り消せない** — リファレンスも PostToolUse は blocking しないと明記しており、`exit 2` は書き込みを巻き戻さず同じターン内でモデルに問題を提示するだけ。名前に `-guard` を使わないのはこのため（既存の `*-guard` はいずれもブロックする PreToolUse で、上記の各項も「〜をブロックし」と書いている）。**検出ロジックはフック内に持たず `go/internal/skill` を in-process で呼ぶ**（親 Issue の one-implementation 規約。契約が同じものを 2 実装持つとドリフトし、フックは通るが検査コマンドは落ちる状態が生まれる）。`ccx skill frontmatter` が同じパッケージの CLI で、フックが案内する再実行コマンドもこれ。登録は `matcher` だけで絞り、対象ファイルの選別はフック側が行う。**フックエントリの `if: "Edit(//**/SKILL.md)"` は使わない** — permission rule の `//` アンカー（ファイルシステムルート）が `if` でも同じに解決される前提で書いたところ、リポジトリ外の新規セッションでフックが一度も発火しなかった（2026-08-25 実測。`if` を外すと同じ条件で発火する）。`if` のパスパターンに permission リファレンスのアンカー規定が及ぶとは hooks リファレンスに書かれておらず、推論が成立していない。`~/.claude/settings.json` に登録されているのでこのリポジトリ外の SKILL.md 編集でも発火する（意図的。4 種の違反は Claude Code の規約であってリポジトリ固有ではなく、ブロックしないので他所での誤検出のコストはメッセージ 1 通に留まる）。ただし **Bash 経由の編集（`sed`・heredoc 等）は PostToolUse の対象にならず素通りする** — 埋めたい穴のうち編集ツール経由の分だけを塞ぐ（対象判定・前提不成立時の扱いの詳細はフックのパッケージコメント参照）
- `ccx hook start-caffeinate` (UserPromptSubmit, PreToolUse, SubagentStart) / `ccx hook stop-caffeinate` (Stop, Notification, SessionEnd, SubagentStop) — Claude が作業中の間だけ macOS のスリープを抑止する。caffeinate は30分リース（`-t 1800`）付きで起動し、ツール呼び出しのたびに kill→再起動でリースを更新する。Esc 中断・API エラー等 Stop フックを経ない終了では更新が止まって自己失効するため、caffeinate が残留して眠らなくなる事故を防ぐ。サブエージェント（バックグラウンド実行され、親ターン終了の Stop 後も動き続ける）には SubagentStart で per-agent caffeinate（`/tmp/ccx/caffeinate/${session_id}-${agent_id}.pid`）を起動し、SubagentStop で `.done` にリネームして親の次の Stop で回収する（完了直後に親が結果を読んでいる間の抑止空白を防ぐ。稼働中の `.pid` は Stop でも殺さない）。例外として Remote Control 接続中（`CLAUDE_CODE_BRIDGE_SESSION_ID` あり、Claude Code v2.1.199+）は、ホストのスリープで約10分後にリモートセッションがタイムアウトするため、セッションの caffeinate を `-t` なしで起動し SessionEnd 以外では停止せず返信待ちの間も抑止を維持する。caffeinate は Claude 本体プロセスを `-w` で watch して起動するため、クラッシュ・SIGKILL 等フックを経由しない終了でも残留しない
- `ccx hook subagent-tracker` (SubagentStart, SubagentStop, SessionEnd) / `ccx hook idle-notify` (Notification の `idle_prompt`) — 「人間の入力が必要な時だけ通知」を実現する機構の 2 つのエントリポイント（`ccx hook slack-notify` / `terminal-bell` と合わせて 4 つが 1 パッケージ `go/internal/hooks/notify`。フックの登録単位ではなく機構の単位でパッケージを切っている）。親セッションがサブエージェントの完了待ちでターンを終えた一時的なアイドルでは `idle_prompt` が発火するが、親は完了通知で自動再開するため人間のやることが無い。tracker が稼働マーカー（`/tmp/ccx/subagents/${session_id}/${agent_id}`）を SubagentStart/Stop で管理し、idle-notify が idle_prompt 受信時にマーカーを走査して、稼働中なら通知を抑止・いなければ端末ベル + Ping 音 + Slack 通知を出す（ベルと Slack はパッケージ内の同じ関数を直接呼ぶ。`ccx` を二重に起動しない）（`permission_prompt` は無条件で通知）。caffeinate の per-agent PID file は再利用しない（ライフサイクルの所有者がスリープ抑止都合で別に変わりうる上、残留時に通知が「沈黙」側へ倒れるため通知専用に独立管理）。判定不能・マーカーの記録 PID 死亡（クラッシュ残骸）は通知する側に倒す。既知の制約: `run_in_background` の Bash・Monitor は SubagentStart を経ないため検知外、SubagentStop 直後〜親再開の隙間の idle は鳴る（いずれも「うるさい」側の漏れ）。ネイティブ通知はタイプ別フィルタ不可で本ガードを素通りするため `preferredNotifChannel: "notifications_disabled"` で停止している（プロジェクト CLAUDE.md「通知チャンネル」参照）
- `ccx hook terminal-bell`（Notification） — 端末ベルを hook JSON の `terminalSequence` フィールド（Claude Code v2.1.141+）で鳴らす。上記の通知機構と同じパッケージにあり、単体のフックとしても呼ばれる。フックは controlling terminal を持たない独自セッションで実行され（v2.1.139+）`/dev/tty` へ `\a` を直接書けないため、Claude Code に代理出力させる。tmux が BEL を受けて window の bell flag を立てる（タブ点灯。Ghostty はデフォルトでベル音を鳴らさないため音は afplay が担当）。`permission_prompt` の直付けフックと `ccx hook idle-notify` のガード通過後の 2 経路から呼ばれ、ベルのタイミングを「人間の入力が必要な時だけ」に揃える
- **編集時は必ずテストを走らせる**: 配置規約・理由・テストの設計制約は `claude/.claude/rules/script-testing.md` を参照

## 許可ルールの設計意図

`settings.json` は JSON でコメントを持てないため、ルールの形そのものが不変条件を担っている箇所をここに記録する（`permissions.allow` を編集するときはこの節を先に読む）。

- **`Bash(git push)` と `Bash(git push --force-with-lease)` は完全一致のまま維持し、`:*` を付けたり `Bash(git push:*)` に統合したりしない**。前者は「引数なしの push は現在ブランチと同名のリモートブランチを非 force で進めるだけ（無ければ作成する）で、リモート履歴は決して書き換えられない」ことに依存し、後者は `git push --force-with-lease` という argv そのものだけを許可することに依存している。`--force-with-lease` に prefix を許すと `--force` の併記・`+<refspec>`・`=<ref>:<sha>` が通り、いずれも lease を無効化してリモートを上書きできる（使い捨ての bare リポジトリで実測。3形とも `forced update` になり、素の `--force-with-lease` だけが `stale info` で拒否された）。`Bash(git push:*)` への統合は加えて `git push --force` と `git push --delete` まで自動承認する。**この設計の唯一の劣化経路がルールの拡大**である点に注意 — スキル本文の記述がずれた場合・エントリが消えた場合はいずれも permission prompt に落ちて気付けるが、ルールを広げた場合だけは無言で防御が外れる。前者の保証を成立させているのは `git/.gitconfig` の `push.default = simple` と `push.autoSetupRemote = true` で、両キーはこのルールの前提だから変更・削除するときはこの節を先に読む（本節の `paths:` が `.gitconfig` を含むのはこのため）。ただし保証は絶対ではなく、リポジトリローカルの `remote.<name>.push` に `+refs/heads/*:refs/heads/*` を置くと引数なし push でも `forced update` になる（使い捨ての bare リポジトリで実測）。それでも上記の「唯一の劣化経路」が崩れないのは、`git config` / `git remote` が許可リストに無く、仕込むには permission prompt を通る必要があるため — 無言で外れるのはルールを広げた場合だけという性質は変わらない。消費者は `/git-rebase`（`claude/.claude/skills/git-rebase/SKILL.md` のステップ16が argv をこの形に固定している）と `/git-pr`（`claude/.claude/skills/git-pr/SKILL.md` のステップ2が引数なしの形に固定している）
- **`Bash(go -C go install ./cmd/ccx)` は完全一致のまま維持し、`:*` を付けない**。`go install` は任意パスへバイナリを置ける操作で、`zsh/.zprofile` が `$(go env GOPATH)/bin` を PATH の先頭に置いているため、そこに `git` や `gh` の名前でバイナリを置かれると以降の全シェルで実コマンドが覆い隠される。`:*` を許すと `-o <任意パス>`、任意プログラムを起動する `-toolexec 'cmd args'`、リモートモジュールを取得する `pkg@version` がすべて通る。この 1 形で足りるのは、**self-rebuild が走らせる `go install` は ccx が `os/exec` で内部実行するため permission の対象外**で、許可が要るのは初回ビルドと検証時に Bash ツールから叩くときだけだから（`gh` shim を置く `GOBIN=~/.local/shims go -C go install ./cmd/gh` はユーザーが手で走らせるリリース手順で、同じく完全一致で許可する形は持たない）。`Bash(git push)` と同じく**この防御の唯一の劣化経路はルールの拡大**で、形がずれれば permission prompt に落ちて気付けるが、広げた場合だけは無言で外れる
