## コーディング・対応方針

- **ファイル形式**: ファイルの最後に改行文字を必ず追加してください（POSIX標準準拠）
- **EditorConfig**: プロジェクトに.editorconfigファイルが存在する場合は、その設定に必ず従ってください
- **コメント規約**:
  - **内容**: コードを読めば分かる内容は書かない。設計判断の理由・複雑なアルゴリズムの意図・非自明な回避策・TODO/FIXME は書く
  - 言語は下記「成果物の言語」に従う
- **成果物の言語**: すべての外向き成果物は書き込み先・投稿先の既存言語・慣例に合わせる。会話・セッションの言語に引きずられない
  - コード内（コメント・ログ/エラー文字列）: 既存コードの言語（英語/日本語）を踏襲し、コードベース全体で一貫性を保つ
  - GitHub 投稿（Issue/PR の本文・コメント）: 対象スレッド・リポジトリの既存言語に合わせる
  - コミット / PR / ドキュメント: 各既存慣例に従う（`git log`・既存 PR・既存文書）
- **シェル変数名に `path` を使わない**: Bash ツールの実行シェルは zsh で、`path` は PATH に連動する特殊配列のため代入した瞬間に PATH が破壊される（以降の全コマンドが command not found になる）。`wt_path` 等の名前を使う
- **ブランチ操作**: `git checkout` ではなく `git switch` / `git restore` を使用する
  - ブランチ作成: `git switch -c branch-name`
  - ブランチ切り替え: `git switch branch-name`
  - ファイル復元: `git restore file`
- **ghコマンド（書き込み系）**: 以下はいずれも `~/.local/shims/gh`（PATH 上の shim）が `exit 78` でブロックする。ブロック時は stderr の理由・復旧手順に従って再実行する
  - 対象リポジトリをコマンド上で明示しないこと（`gh issue` / `gh pr` / `gh release` / `gh repo` / `gh label` の create / comment / edit / close / merge / review 等。`gh repo create` / `gh repo fork` と read 系、verb の直後に置いた `--help` は対象外）。明示の形は noun ごとに異なる
    - `gh repo edit` / `delete` / `archive` / `unarchive` / `sync`: **最初の位置引数**に `owner/repo`（`host/owner/repo`・リポジトリ URL も可）を書く。フラグより前でも後ろでもよい。これらに `-R` は無く、環境変数によるリポジトリ指定も効かない
    - `gh repo rename`: 位置引数は新しいリポジトリ名なので `-R owner/repo` を付ける
    - `gh issue` / `gh pr` の selector を取る verb: `-R owner/repo` を付けるか、対象を完全な URL（`https://github.com/owner/repo/issues/1`・`.../pull/1`）で指定する。番号のみ・ブランチ名は明示にならない
    - 上記以外（`gh issue create` / `gh pr create` / `gh release` / `gh label`）: `-R owner/repo` を付ける
    - `-h` がヘルプになるかは verb 次第（`gh repo edit` の `-h` は `--homepage`）。ヘルプ参照は `--help` を使う
  - 複数行の本文をインラインの本文フラグで渡すこと（scratchpad 等へ Write してファイル代替を使う。単行の短い本文はインラインで可）。対象は GitHub が markdown としてレンダリングする本文で、誘導先は verb ごとに違う
    - `--body`/`-b`（`gh issue` の create / comment / edit、`gh pr` の create / comment / edit / merge / review / revert）→ `--body-file <path>`
    - `--notes`/`-n`（`gh release create` / `edit`）→ `--notes-file <path>`
    - `--comment`/`-c`（`gh issue close` / `reopen`、`gh pr close` / `reopen`）→ **ファイル代替が無い**ので、本文は `gh <noun> comment -R owner/repo N --body-file <path>` で別途投稿し、close / reopen は `-c` なしで実行する
    - `gh label create`/`edit` と `gh repo edit` の `--description` は対象外（プレーンテキストで、素の `#数字` が自動リンクにならないため）
  - review thread への返信・解決を `gh api` で直接叩くこと（GraphQL の `addPullRequestReviewThreadReply` / `resolveReviewThread`、REST の `POST repos/{owner}/{repo}/pulls/<n>/comments/<id>/replies`）。返信・解決は `ccx pr reply-threads` を使う（入力契約は `ccx pr reply-threads --help`、スレッド一覧は `ccx pr context`）。他人の PR では自分が起こしたスレッドしか扱えないので、それ以外は GitHub UI か対話シェルで行う。`ccx` は GitHub を in-process に叩くのでこのブロックの影響を受けない
    - GraphQL のクエリを `--input <file>` / `-F query=@<path>` で渡す場合、読めないパスはブロックされる（`-` で標準入力から渡す形のみ対象外）
  - 本文ファイル（`--body-file` / `--notes-file`）に、存在しない・読めない・通常ファイルでないパスを渡すこと（`gh` 自身も API に触れる前に読み込みで失敗するため、先にファイルを Write してから実行する。`-` で標準入力から渡す形のみ対象外）
  - 後述「マークダウン記法」の項番・closing keyword 規約への違反
- **PR/Issue 作成時は自分をアサイン**: `gh pr create` / `gh issue create` では `--assignee @me` を付けて作成者自身をアサインする（担当者が明示されないと後追いしにくいため）
- **エラーハンドリング**: 戻り値を使わないエラーは条件文内で処理する（Go: `if _, err := f(); err != nil`）、エラーオブジェクトを使わない場合は parameterless catch を使う（TypeScript）
- **マークダウン記法（GitHub）**: Issue・PR説明・コメント・README等に文章を書く際の記法
  - `@import`・`@use` 等をバッククォートで囲む（ユーザーリンク化を避けるため）
  - 項目の番号付けに素の `#数字` を使わない（Issue/PR への自動リンクになり無関係な参照通知が飛ぶため）。項番は順序リスト（`1.`）で表す。素の `#数字` は実在の Issue/PR を参照する意図があるときだけ書き、他リポや参照先が曖昧な場合は `owner/repo#数字` 形式にする
  - **例外（GitHub closing keyword）**: 自動 close の意図で書く `Closes #N` / `Fixes #N` / `Resolves #N` はバッククォートで囲まない（コードスパン内では解釈されず、マージしても Issue が open のまま残る）。引用・文書化の意図なら実番号をプレースホルダにする。なお自動 close が発火するのはデフォルトブランチへのマージ時のみ
  - 文章では伝わりにくい内容はGitHubのネイティブレンダリングを活用する（処理フロー・構造の変化 → Mermaid図、数式・アルゴリズム → LaTeX数式）。ただし変更の理解を助ける一時的な用途に限る。恒常的なアーキテクチャ図はdocsに置き、同じPRで更新する
  - 長い補足（検証記録・根拠・ログ等、読者のアクションが不要な内容）は `<details>` で折りたたむ。アクションを要求する内容（要件・修正依頼）は折りたたまない。`<summary>` 行の直後に空行を置く（無いと中身の Markdown がレンダリングされない）

## テスト開発原則

- **テストファーストの適用基準**:
  - **バグ修正**: バグを再現する失敗テストを先に書き、失敗を確認してから修正する（修正の正しさとリグレッション防止を同時に担保）
  - **入出力契約が明確な実装**（パーサー、計算ロジック、バリデーション、APIの仕様が確定している場合）: テストを先に書き、失敗を確認してから実装する
  - **探索的実装・UI・外部サービス統合**: テストファーストを強制しない。インターフェースが固まった時点で仕様ベースのテストを書く（実装を追認するテストにしない）
  - **Red確認を省略しない**: 実装前にテストが失敗することを必ず確認する。最初から通るテストは何も検証していない
- **テスト失敗時の対応順序**:
  1. 実装コードの動作確認（ブラウザ/CLI等）
  2. 根本原因の特定（実装 or テストの問題）
  3. 適切な修正
  4. 不要なモック・デバッグコードのクリーンアップ
- **禁止パターン**: テスト失敗→即座にモック設定変更
- **最小限修正**: 必要最小限の変更のみ、過度なモック化は避ける
- テストコードの品質評価3原則（無駄・抜け漏れ・可読性）の詳細は test-implementation スキルを参照

## 仕様遵守原則

仕様書・Issue・チケット等で要件が明示されている場合:
- 要件を勝手に削除・簡略化・変更しない
- 「シンプルにする」等の理由でスコープを縮めない
- スコープ変更が必要と判断したら、実装前にユーザーに確認する
- 参照要件（「Xと同等」「既存のYに準拠」等）は、参照先を実際に確認してから実装する

## 設計判断原則

設計の選択肢・推奨・計画・決定事項の要約を提示するときは、規模を問わず次を含める（聞かれてから答えない）。AskUserQuestion の選択肢も対象で、greenfield 判定は description 側に書く（label は短く保つ）:
- **greenfield 判定**: 選択肢ごとに「既存コードが無い前提で一から作るならどれか」を明示し、推奨がそれと一致するか妥協かを書く。理想設計と移行コストは別軸として併記し、1 つの推奨に混ぜない
- **理想とエコシステム慣習が食い違うとき**: 両方を並べて差を説明し、公式ドキュメント・標準ライブラリが実際に採っている形を推奨にする。この場合は慣習側を greenfield 判定とし、妥協とは書かない
- **妥協は探してから書く**: 妥協を解消する既存構造（単一の入口・書き出し口・型等）をコードベースで探し、無かった場合のみ「何を探して無かったか」と失う性質を添えて書く。ユーザーが意図的に選んだ縮小（コスト・時期等）は妥協ではなく「ユーザー決定」として別に記録する
- **Issue・規約・スコープとの衝突**: 縮小版を黙って採らない。食い違いを報告し、Issue・規約側の修正か別 Issue の起票を提案する。実行はユーザー承認後
- **慣習を根拠にするときは一次資料を読んで引用する**: 公式ドキュメント・標準ライブラリ・フレームワーク自身のリポジトリを実際に読む。記憶だけで語るときは「未確認」と明記する
- **セルフチェック**: 提示前に「既存コードが無いものとして一から実装しても同じ設計を選ぶか？」を自問し、答えが No なら両案を理由付きで提示する。外部公開契約（DB テーブルスキーマ・DDL、API/IDL 定義。spec・Issue 内の定義を含む）の新規作成・修正にも同じ判定を適用する

## 質問の原則

- **事実と判断を分ける**: 自力で検証できる事実（コードベース・ログ・`gh` 等で確認できるもの）は質問にせず自分で調べる。質問して回答を待つのは、相手（ユーザー・作者）の判断（要件の取捨・スコープ・受け入れ水準等）と、こちらから観測できない情報（運用実績・意図等）に限る

## サブエージェントのモデル選択

コスト原則: **上位ティアと結果の差が出ないタスクには下位ティアのモデルを明示する**（Sonnet で差が出ない領域は Sonnet、Opus で差が出ない領域は Opus）。この原則を適用してよいのは、下記の調査・探索系サブエージェントと、スキルが明示的に下位ティアのモデルを指定している呼び出しに限り、それ以外への一般的な許可としては読まない。

- **調査・探索系**（Explore 等、コードの所在特定・事実収集・横断 grep が目的のサブエージェント）: `model: "sonnet"` を明示する。model 未指定だと親モデル（通常 Opus）を継承し、差が出ない作業に上位単価を払うため
- **判断密度が高い批評・レビュー・計画・実装**: スキルの明示指定に従う（例: issue-handle の実装委譲は sonnet、完了時 deep-review は fable）。スキル外のアドホックな起動では親モデル継承のままで良い
  - スキルが `model` を指定していないレビュー・批評（組み込み `/simplify` のレビューエージェントを含む）は、呼び出し側の判断で下位ティアへ落とさず `model` を付けずに起動する（親継承）。モデルの選定はスキル・エージェント定義が所有し、呼び出し側がコスト都合でカバレッジのトレードオフを決めない（判断密度の高い角度 — altitude 等 — のカバレッジが静かに落ちるため）

## 計画立案原則

実装計画を立てる際（plan モード含む）、計画起案の**前**に以下を実施し、制約を思考の前提として組み込む:
- プロジェクトルートの `CLAUDE.md` を読む（`@import` 形式リンクは自動展開されるが、`[text](path)` 形式リンクは自動読込されない場合がある）
- `CLAUDE.md` からリンクされている `.md` 文書を読む（標準Markdownリンク・`@import` 両形式）
- 計画完成後の準拠検証・修正が必要な場合は /check-plan-compliance スキルを使用
- 計画完成後の設計妥当性・自己完結性の検証は /deep-plan-review スキルを使用（/check-plan-compliance と併用時は compliance 先。compliance は `--no-exit` を付けて実行する）

事後チェックではなく事前読込を原則とする。事後の準拠検証に依存しすぎると計画起案自体の質が下がるため。

## トラブルシューティング原則

- **根本原因を特定して対応する**: 症状だけを抑える対処や問題を迂回するワークアラウンドは原則採用しない（エラーの握りつぶし、テストのskip、`any`での型エラー回避、試行錯誤の継ぎ足し等）。外部制約等で根本対応が不可能な場合のみ、根本原因を特定した上で理由を明示して回避策を選ぶ
- **推測ではなく事実を確認する**: エラーメッセージや推測だけで判断せず、ログ・クエリ・実行順序の確認で現在の状態を把握する
- **デバッグログで事実を積み重ねる**: 一時的なデバッグログは積極的に追加し、問題解決後に必ず削除する
- **段階的に絞り込む**: 全体把握 → 個別確認 → データ確認 → 最小再現
- 具体的手法は troubleshooting スキルを参照

## コンテキスト管理

- **文書化のハードル**: 明文化しないと判断を誤る・同じ議論が再発するものだけを書く。文脈から判断できることは書かない（既定は「書かない」。書くと決めたときだけ分離基準で置き場所を選ぶ）
- **分離基準**（トリガーの性質で振り分ける）:
  - CLAUDE.md: 常時必要な基本方針・原則（計画段階から効くべきもの）
  - rules/: 特定ファイルを扱うときだけ必要なルール（frontmatter の `paths:` glob で遅延読込）
  - skills/: 特定タスクのときだけ必要な手順・知識（description ベースで自動ロード）
  - memory: セッションをまたいで効く判断の経緯・ユーザーの選好（auto-memory が自動保存）
    - **現在の設定状態は memory に置かない**（settings.json のキー値、どのスキルがどのモデルを使うか等）。設定を変更しても memory には伝播せず腐るため、その設定自体の近くに置く

## Compact instructions

コンパクション時は以下を優先的に保持してください：
- 現在のタスクコンテキストと目標
- エラーメッセージとテスト出力
- コード変更と修正内容
- ユーザーの指示と要件
