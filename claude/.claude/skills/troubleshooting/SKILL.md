# /troubleshooting

エラー調査・テスト失敗時のデバッグ手法。基本原則はグローバルCLAUDE.mdの「トラブルシューティング原則」を参照。本スキルはその具体的手法を提供する。

Go + RDB のテスト環境における実例（デバッグログ、Cleanup の LIFO 検証、絞り込みのコマンド例、外部キー制約・データ重複・実行順序の各パターン）は [go-db-debugging.md](go-db-debugging.md) を参照。

## 原則の適用

### 根本原因を特定して対応する

```
❌ 悪い例:
1. エラーが出た
2. とりあえずクリーンアップコードを追加
3. 別のエラーが出た
4. さらにクリーンアップコードを追加
5. ...（試行錯誤の繰り返し）

✅ 良い例:
1. エラーが出た
2. ログを入れて現在の状態を確認
3. データを直接確認
4. 実行順序を確認
5. 根本原因を特定
6. 最小限の修正で解決
```

**避けるべきパターン**:
- エラーが出る → try/catch で握りつぶす
- テストが失敗 → skip する、アサーションを緩める
- 型エラー → `any` で回避
- 試行錯誤で対処コードを継ぎ足す

**例外（理由を明示して採用可）**:
- 外部制約（サードパーティのバグ、変更不可能なAPI仕様等）で根本対応が技術的に不可能
- 根本対応のコストが著しく高く、期限等の事情で一時回避が合理的

例外に該当する場合も、まず根本原因を特定した上で、なぜ回避策を選ぶかを説明する。

### デバッグログで事実を積み重ねる

一時的なデバッグログは積極的に追加する。問題解決後に削除すればよい。

推測で書かず、**次の判断に必要な事実**を出力する:
- 分岐の入力値と、実際に通った経路
- 件数・ID 等、期待と実際を突き合わせられる具体値（「失敗した」ではなく「何件残っていたか」）
- 外部リソースの状態は、呼び出し側の変数ではなく実体（DB・ファイル・API レスポンス）を読んで出力する

`[DEBUG]` 等の固定タグを付けておくと、後で機械的に回収できる。

### 実行順序を確認する

処理の順序が重要な場合（LIFO で走る後処理、トランザクション、非同期処理、並行実行等）は、順序を推測せずログで確認する。各ステップの開始時点と実行時点の両方を出力し、登録順と実行順が一致しているかを突き合わせる。

## フィードバックループを最初に作る（難バグ向け）

一見して原因が分からないバグは、仮説を立てる前に**そのバグで red になる1コマンド**（フィードバックループ）を構築する。ループ構築前にコードを読んで原因の理論を組み立て始めるのが典型的な失敗パターン — 気づいたら停止してループ構築に戻る。ループができれば、以降の絞り込み・仮説検証はループを回すだけになる。

完了基準（すべて満たすまで仮説フェーズに進まない）:
- **red-capable**: ユーザーが報告した症状そのものを検出して red になる（「エラーなく実行できた」では不十分）
- **決定的**: 毎回同じ判定になる
- **高速**: 分単位ではなく秒単位
- **単独実行可能**: 人間の操作なしで繰り返し実行できる

構築手段は症状に届くものなら何でもよい: 失敗テスト、curl / CLI + fixture、ヘッドレスブラウザ、キャプチャした実データ（リクエスト・イベントログ）の再生、最小構成の使い捨てハーネス等。

- 非決定的なバグはクリーンな再現を求めず**再現率を上げる**（トリガーの100回ループ・並列実行・タイミング窓の圧縮等。1% の flake はデバッグ不能だが 50% なら可能）
- どうしてもループを作れない場合は、その旨と試したことを明示し、ユーザーに再現環境やキャプチャ済み成果物（ログ・HAR・ダンプ等）を求める。ループ無しのまま仮説フェーズに進まない

## 仮説は複数立ててから検証する（難バグ向け）

原因が一見して確定しない場合、検証を始める前に**反証可能な仮説を3〜5個**生成してランク付けする（最初に思いついた1つへのアンカリングを防ぐ）。各仮説は予測の形で書く: 「Xが原因なら、Yを変えればバグが消える / Zを変えれば悪化するはず」。予測を言えない仮説は捨てるか、言えるまで研ぐ。

検証は1回に1変数だけ変え、各プローブ（ログ・ブレークポイント）がどの仮説の予測を確かめるものかを対応づける。

## 段階的な問題の絞り込み

各段で「何を確定させるか」を意識して進める。前の段の結論が出ないまま次へ行かない。

1. **全体像の把握** — 問題の範囲を確定する。全体を実行し、どこが失敗するか／単独では通るかを見る
2. **個別の確認** — 失敗箇所を 1 つに絞る。詳細出力・並行処理検出等のオプションを付けて再実行する
3. **データの確認** — エラーメッセージではなく実体を確定する。DB・ファイル・レスポンスを直接読む
4. **最小再現ケースの作成** — 再現に必要な最小の条件を確定する。関係ない要素を削り、それでも再現するかを見る

## デバッグログの削除

問題解決後は必ず削除する。固定タグを付けておけば機械的に回収できる。

```bash
grep -rn "\[DEBUG\]" .   # 残骸の検出
git diff                 # コミット前に目視確認
```

**残すべき**:
- 本番環境でも役立つ情報（エラー、警告、重要な状態変化）
- パフォーマンス監視用のログ

**削除すべき**:
- `[DEBUG]` タグ付きの一時的なログ
- 状態確認のための追加クエリ・追加出力
- 開発中の試行錯誤コード
