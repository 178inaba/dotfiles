# /deep-plan-review

実装計画を、会話コンテキストを持たない読み取り専用サブエージェントに検証させ、blocker が無くなり decision がすべて回答・反映されるまで計画を修正する。

## 使用方法
```
/deep-plan-review                     # 現在の plan モードの計画ファイルを検証
/deep-plan-review path/to/plan.md     # 計画ファイルを明示指定
```

## 実行内容

### 1. 対象計画の特定
- 引数でファイルパスが指定されていればそれを使用
- 省略時は現在の plan モードの計画ファイル（plan モード開始時に指定されたパス）
- どちらも無い場合はエラーで停止し、計画ファイルの指定を促す

### 2. 読者の起動と計画の提示

Skill ツールで `fresh-reader-verification` を起動し、そのプロトコルに従う（起動・分類基準・指摘への対処。収束は手順 3 の同期点で行う）。実地検証の範囲は同スキルの「依頼文」が定める既定をそのまま使う（本スキルは絞り込まない）。修正の反映先は計画ファイル。

同スキルの「依頼文」に差し込む役割と検証観点:

> あなたはこの計画で実装を任された実装者で、計画起案時の議論は一切読めない。計画ファイルを Read し、計画単体で実装に着手できるかを以下の観点で評価せよ。
> - 参照実在性: 存在しないファイル・関数・設定・コマンドを参照していないか
> - 前提と実コードの一致: 計画が前提とする既存コードの構造・挙動が実物と一致しているか
> - 設計妥当性: 手順が計画の目的・要件と整合しているか、見落としているリスクはないか
> - 自己完結性: この計画単体で迷わず実装可能か

**plan モード中は、読者の 1 周を待たずに計画を承認へ出す**。以下を 1 ターンで行う:

1. 計画ファイルの末尾に、読者の検証が実行中であること・blocker は承認後に反映すること・意味が変わる修正は再提示することを、1 行のマーカーとして追記する（`fresh-reader-verification` の言う処理メタデータの行）。計画の言語で書く（日本語の計画なら例: `> 新規読者検証は実行中。blocker は承認後に反映し、意味が変わる修正は再提示する。`）。既にマーカー行があれば追記せず置換する（同じパスの計画ファイルを再利用しても二重にならない）
2. 上記の読者を起動する（Agent ツールは即座に返り、完了は通知で届く）
3. 直ちに `ExitPlanMode` を呼ぶ

マーカーの宛先は承認するユーザーなので、`ExitPlanMode` を呼ぶ直前にそれが計画の最後の行であることを確認し、末尾に節が足されて押し下げられていたら末尾へ移す（承認が差し戻されて計画を編集し、再度 `ExitPlanMode` を呼ぶ場合も同じ）。

読者の起動が失敗した場合の扱いは `fresh-reader-verification` の「起動」が定める。本スキルはあわせてマーカー行を削除する（同期点で来ない通知を待たないため）。

plan モード外では読者を起動するだけで、マーカーも `ExitPlanMode` も無い。

### 3. 同期点（承認後の収束）

**本スキルの同期点**（`fresh-reader-verification` が消費者に名指しを求めるもの）は、**承認が返った後の最初の行動の直前**。呼び出し側の最初の行動もここを待つ。plan モード外で起動された場合の同期点は手順 4 の報告の直前。

- 読者を起動できていて完了通知がまだ届いていなければ**ターンを終える**（通知でセッションが再開する。`sleep` によるポーリングは `ccx hook no-op-wait-guard` が塞ぐ）。バックグラウンドのサブエージェントが走っている間は `ccx hook issue-handle-guard` が素通しするので、ここでターンを終えても停止扱いにならない
- `fresh-reader-verification` のプロトコルで収束させる（blocker の調査と修正、decision の 1 ラウンド、集合の変化ごとの差し戻し、予算）
- **承認済み計画への修正は 2 つに分ける**（承認を経ていない plan モード外の起動には適用されない）:
  - **意味が変わる修正**（手順・スコープ・設計判断・decision への回答）→ `AskUserQuestion` で再提示する。承認された計画から何が変わったかを変更箇所の前後だけで示し（計画ファイル自体が記録なので全文は出さない）、選択肢は「修正後の計画で続行」と「打ち切り」。同じ同期点で decision のラウンドが立つなら同じ呼び出しにまとめる（その質問がその回答の再提示を兼ねるので、回答を反映した後にもう一度出さない）
  - **訂正**（パス・識別子・件数・コマンドの引数）→ ターンのテキストで報告して続行する
  - 迷ったら再提示に倒す
- **「打ち切り」が選ばれたら、呼び出し側の run をそこで終える**（その時点の成果物の扱いは呼び出し側が定める）。呼び出し側のいない単独起動なら手順 4 の報告で終える
- **収束と参照・コマンドチェックは 1 つの版で揃える**。同期が終わるのは、その版が `ccx plan check` clean かつ読者に検証済みになったとき。**編集の有無にかかわらず同期点で 1 回は `ccx plan check <計画ファイルパス>` を実行し、clean になるまで再実行する**（finding を直した編集が新しい finding を生むことがある）。指摘を反映する編集があるときは**差し戻しを書く前に**チェックを済ませ、その finding も同じ編集群に畳んでから 1 通で差し戻す（別々に送ると読者の周が 1 つ増える）。finding は本スキルが解消する: 参照を直す / これから作る成果物に `(new)`・`（新規）` を注記する / コマンドを実行して結果を記録する（実行できないならその理由を記録する）
  - 呼び出し側が計画フェーズで同じチェックを済ませていても省略しない。そのチェックは本スキルが計画を編集する前に走っており、**読者の指摘を反映した編集はどのチェックも通っていない**。差し戻しでも埋まらない: 読者は計画に新しく足された検証コマンドを実行しないので、結果が記録されていないコマンドはこのチェックでしか見つからない
- **マーカー行を置いた場合は、それを最後の編集として削除する**。処理メタデータの行なので判定を無効にせず（`fresh-reader-verification` の「判定は渡したファイルに束縛される」の例外）、blockquote 1 行の削除は参照もコマンドの記録も動かさないのでチェックの結果も変えない
- ここまで済ませてから呼び出し側へ返る

### 4. 報告
- 呼び出し側のいない単独起動、または plan モード外で起動された場合は、レビュー結果と反映内容を報告して終了する

## 注意事項
- `/check-plan-compliance`（プロジェクト規約への準拠検証）と併用する場合は **compliance 先 → 本スキル後** の順で実行する（高コストな検証は最終形の計画に 1 回だけ充てるため）。その場合 compliance は `--no-exit` を付けて実行し、ExitPlanMode は本スキル側が担う
- **例外**: 設計妥当性の批評を厚くしたい場合のみ、共有プロトコルの起動時に `model: "fable"` を明示指定する（Agent ツールの `model` 指定はエージェント定義より優先される）。既定は fresh-reader 定義の opus で、その選定理由は `~/.claude/agents/fresh-reader.md` を参照
- 検証サブエージェントは読み取り専用（fresh-reader の tools 設定で Edit/Write 不可を機械的に強制）で、計画の修正は本スキル（親セッション）が行う
