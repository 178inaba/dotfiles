# /skill-authoring

`~/.claude/skills/` 配下のスキルを作成・編集する際の規約。

構成例（基本構成テンプレート・良い例・悪い例）は [examples.md](references/examples.md) を参照。

## フロントマターの設定

| フィールド | 必須 | 説明 |
|-----------|------|------|
| `name` | ✅ | スキル名（ディレクトリ名と一致） |
| `description` | ✅ | 「何をするか + いつ使うか」を1行で書く（スキル解決・自動トリガーの一致精度に直結。用途を明記しないと、名前・機能が近い別スキルへの誤解決を招く — 組み込み `review` への deep-review 誤解決事故の教訓） |
| `argument-hint` | - | 引数のヒント（ヘルプ表示用）。値が `[` / `{` で始まる場合は引用符で囲む |
| `disable-model-invocation` | - | `true`: 手動のみ、`false`: 自動トリガー可能 |
| `user-invocable` | - | `false`: ユーザーメニュー非表示（モデル起動・自動ロードのみ）。他スキルから起動される共有知識スキル向け（例: `worktree-resolution`） |

引用符が要るのは、`[` / `{` で始まる値を YAML が flow sequence / flow mapping として読むため（`argument-hint: [--yes]` は文字列ではなく1要素の配列になる）。1行に複数並ぶと値として解釈しようがなくなり、frontmatter 全体が解析不能になる。

### `disable-model-invocation` の判断基準
- **`true`（手動のみ）**: Git操作、ファイル編集、外部API呼び出しなど副作用があるスキル
- **`false`（自動トリガー可能）**: 読み取り専用、分析・レビュー系のスキル
- **例外**: 副作用ありでも他スキル（特に `issue-handle` 等のワークフロー系）から呼び出される場合、または `/loop` 常駐運用を想定する場合は未設定（`false` 相当）にする
  - 理由: 連鎖呼び出しも `/loop`（即時実行・cron 発火とも）もモデル経由の起動であり、`true` だと全経路がブロックされるため。**他スキルから起動される側では例外ではなく禁止**（「スキル間参照」）— Skill ツールもサブエージェントの `skills:` プリロードも塞ぐ
  - 例: `git-commit`, `git-pr` は `issue-handle` から呼ばれるため未設定。`review-assigned-prs`, `review-response` は `/loop` 常駐運用のため未設定
- **例外（安全経路への誘導）**: 破壊的操作でも、スキルが承認フローを内蔵する場合は未設定にする — `true` はモデルのスキル一覧から消すため、自然文の依頼にスキル外の即興コマンドで応じることになり、誤発動ではなく安全経路の方を抑止してしまう。例: `cleanup-merged`, `issue-draft`
- **副作用で決まらない場合の補助線（負荷トレードオフ）**: モデル起動可は description が毎ターン常駐するコンテキスト負荷を払い、手動のみは「ユーザーが存在を覚え続ける」認知負荷を払う（忘れると在庫化する）。どちらの負荷が軽いかで決める

## 設計原則

1. **シンプル性**: 既存スキル（git-commit等）と一貫した構成
2. **必要最小限**: 関連コマンド・更新履歴等の冗長なセクションは避ける
3. **実用性**: 実際の使用時に必要な情報のみを含める
4. **一貫性**: 全スキル間でフォーマットを統一
5. **サイズ上限の目安**: SKILL.md 本文は500行以下（[Anthropic の Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 準拠）。超えそうなら分離する — 決定的配管は `ccx` のサブコマンドへ（「配管の分離」）、条件付き詳細は参照ファイルへ。ただし参照ファイルには読み飛ばしリスク（公式も "missed connections" として既知の失敗モードに挙げる）があるため、常時必要な判断規律は本文に置く

## 配管の分離（コード処理とAI処理の分離）

決定的な処理はスクリプトに落とし、判断が必要な処理だけを SKILL.md の指示（AI処理）として残す。モデルが毎回コマンドを組み立て直すことによる揺れ・遅さ・トークン消費を排除するため。公式ベストプラクティスの degrees of freedom 原則と同型 — 一歩間違うと壊れる脆弱な手順ほど低自由度（コード）に、文脈が形を決める判断ほど高自由度（プロンプト）に置く。

### スクリプト化の判断基準

**スクリプト化する**（すべて満たす場合）:
- 判断が不要な決定的処理（収集・判定・正規化・整形）
- 複数コマンドの組み立て・出力の突き合わせがあり、プロンプトで長文の念押しが必要になっている
- 出力を後段の AI 判断が使う

**スクリプト化しない**:
- AI 判断そのもの（コミット分割、文章生成、修正要否の判断）
- 組み立てが揺れようのない単純コマンド（`git branch -d` 等）
- ユーザー承認・対話を挟むフロー制御（会話に残す）

### 配置規約
- 起動口は `ccx <group> <name>` のサブコマンド。実装コードの置き場所は `~/.claude/rules/script-testing.md` にある
- **ドメインで切る**（`issue` / `pullrequest` / `worktree` / `reviewprs` / `skill` / `plandocs`）。スキルごとではない — 同じ対象を触るコマンドは 1 パッケージに収め、スキル間で共有するものも同じ場所に置く
- `skills/<skill-name>/scripts/` は使わない。frontmatter 検査はスキルディレクトリ直下に置いてよいものを知り続ける必要があるため、ここに規約が残っている

### 出力契約
- stdout には JSON のみを出力する（AI がそのまま解析できる形）
- 警告・縮退はエラーにせず JSON のフィールドで返し（例: `degraded`, `warnings`）、フォールバック判断は AI に委ねる
- 前提不成立（リポジトリ外・依存欠如・対象不在）は非ゼロ exit + stderr メッセージ
- stderr のエラーメッセージは英語で書く（git・gh 等の英語のエコシステム出力と同じ流れに混ざって表示され、CI 等の別文脈への流用にも英語が無難なため。JSON 内の表示用文字列はレポートの言語に合わせてよい）
- 上記3点の配管は `internal/cmd` が担う。実装パッケージは型付きの値を返し、`io.Writer` を受け取らない — JSON への変換と `ccx: <msg>` の stderr 描画は 1 箇所に閉じる
- **契約は書かず、型から生成する**。フィールドの意味はそのフィールドの doc comment に、値の意味はその定数の doc comment に書く。`ccx <cmd> --help` がそれを描画するので、契約は二度書かれない。フィールドを改名すればヘルプが同時に変わる
  - doc comment は `--help` の読者にも読まれる。他のフィールドは JSON 名で呼び、Go の識別子やソースファイル名を書かない
  - 入力を取るコマンドは、その wire 形状も名前付きの型にする。パーサ関数の中の匿名 struct は描画できない
- **SKILL.md に書くのは「実行コマンド + 自スキルの解釈」だけ**。出力の形・フィールドの意味・exit status は書かない。読者には `ccx <cmd> --help` を案内する
  - フィールド名を書いてよいのは、そこで実際に作用する手順の中だけ。出力の目録は持たない
  - `ccx skill contract` が、どのコマンドも公開していない snake_case の名前を違反として報告する（SKILL.md 編集時に実行し、`violations` が空になるまで直す。違反の型は `ccx skill contract --help` にある。リポジトリ自身の skills/ に対して CI でも走る）
- **スキルは `ccx` をコマンド名で指す**。実装のパスで指さない — スキルはリポジトリの外から起動されるので、リポジトリ相対のパスは読者に解決できない

### テスト必須
- 配置・理由・設計制約（実環境に触れない・注入での差し替え）の正は `~/.claude/rules/script-testing.md` — この文書に複製しない

### frontmatter の検査

`ccx skill frontmatter [<target>]`（SKILL.md 編集時に実行し、`violations` が空になるまで直す）。`<target>` はディレクトリか単一の SKILL.md で、省略時は自身が属する skills/。検出する違反とその条件は `ccx skill frontmatter --help` にある。Edit / Write / NotebookEdit で SKILL.md を保存すると `ccx hook skill-frontmatter-check`（PostToolUse フック）が同じ検査をそのファイルに走らせる。手で実行するのは、skills/ 全体をまとめて検査するときと、Bash 経由（`sed`・heredoc 等）で書き換えたとき（フックが発火しない）。

## スキル間参照

他スキルに届く手段は Skill ツールでの起動だけで、公式ドキュメントが示す連鎖機構もこれ 1 つ。用途で書き分けるのは「起動する」か「名前を出すだけ」かの 2 つ:

| 用途 | 書き方 | 条件 |
|---|---|---|
| **起動する** — その時点で他スキルの本文が要る（手順として実行する・共有知識をその場で適用する、のいずれも） | 「Skill ツールで `<skill>` を起動する」 | 起動時にそのスキル本文と、そのスキルが起動する先が just-in-time で載る。手順スキルと知識スキルで機構を分けない |
| **言及する** — 名前を出すだけ（併用順序・準拠先の案内等） | `/<skill>` または `` `<skill>` `` | その時点で本文が要らない場合に限る。ルールの持ち主を指すだけの引用がこれ。どちらとも読める場合は起動に倒す |

起動文の書き方:

- 名前は**ディレクトリ名で、先頭のスラッシュは付けない**（プラグイン提供のスキルは `plugin:skill`）
- 引数があるときは「Skill ツールで `<skill>` を引数 `<args>` で起動する」と、**そのまま渡せる文字列**で書く。呼ばれた側が解釈する散文に残さない
- caller が特定の節に依存しているなら「…を起動し、その『PR worktree 解決手順』に従う」のように節名を 1 節添える。**節を起動することはできない**ので、載るのは常に本文全体
- **必要な地点で無条件に起動する**。同じ実行の手前に条件付きの起動があっても、その条件を書き写さない（読み込み済みのスキルの再起動は「既に文脈にある」と返るだけで費用がかからないため、二重起動を避ける必要はない）
- **起動される側は `disable-model-invocation: true` を持たない**（Skill ツールもサブエージェントの `skills:` プリロードも塞ぐため。判断基準は上記「`disable-model-invocation` の判断基準」）

**スキルを部分的に起動することはできない**。手順スキルの一部だけが欲しい場合は、呼ばれる側にフラグを足す（`check-plan-compliance --no-exit`）か、共有部分を知識スキルとして切り出す（`finding-severity`）。呼ばれる側の判断・手順を caller にコピーするのは選択肢ではない（2 つの写しが 2 人の持ち主を持つとドリフトする）。**例外は、その手順が caller 自身の責務としても要求されている場合**（issue-handle の計画前の文書読込は、グローバル CLAUDE.md「計画立案原則」がすべての計画者に課している）。このとき caller は自分の責務として手順を書き、呼ばれる側を指さない — 起動したときにその手順が重複して走ることは受け入れる。

本節の規約に機械検査は無い（`@` 添付を取り締まっていた検査は機構ごと廃止した。Anthropic 自身も同種の検査を持たず、遵守はレビューが担保する）。`ccx skill contract` が検査するのは下記「出力契約」の識別子だけで、本節とは別の話。

## ディレクトリ構造
```
~/.claude/skills/
├── skill-name/
│   ├── SKILL.md          # メイン定義（必須）
│   └── references/       # 条件付き詳細・例示の参照ファイル（オプション）
│       └── <topic>.md    # 内容が分かる名前を付ける
└── ...
```

参照ファイルは `references/` 配下に置く。ファイル数が 1 つでもスキル直下には置かない。各参照ファイルは SKILL.md 本文から直接リンクし、参照ファイルから別の参照ファイルへ辿らせない（参照の連鎖が部分読みを誘発するため。`references/` 配下でディレクトリを分けるのは連鎖ではないので可）。ここでの参照ファイルは自スキル内の markdown を指す（他スキルへの到達は「スキル間参照」が扱う）。100 行を超える場合は先頭に目次を付ける。

## 命名規則
- ディレクトリ名: 小文字とハイフンのみ使用: `git-commit`
- 関連スキルとファミリーを成す場合は 対象-操作 形式でグルーピング: `git-commit`, `git-pr`, `issue-handle`, `issue-draft`（一覧で並び、`/issue` まで打てば補完で揃うため）
- それ以外は内容が伝わる簡潔な名前: `deep-review`, `cleanup-merged`, `troubleshooting`
