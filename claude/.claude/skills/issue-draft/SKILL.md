# /issue-draft

壁打ちで固めた内容を「迷わず実装できる」GitHub Issue として構造化・作成する。`--refine` では既存 Issue を素材に、同じ品質基準へブラッシュアップして本文を更新する。

## 使用方法
```
/issue-draft                                    # 直前の会話から要件を抽出して新規作成
/issue-draft <トピック>                         # 会話のうち指定トピックに絞って抽出
/issue-draft --refine <番号>                    # 既存 Issue をブラッシュアップして本文を更新
/issue-draft --refine <番号> [<番号>...] [追加指示]  # 複数 Issue を 1 セットとしてブラッシュアップ
/issue-draft --refine <番号> [<番号>...] --check  # 評価だけ行い、書き換えずに判定を報告
/issue-draft --refine <番号> <番号> <指示: 会話で合意した X を 1 つ目の Issue の Sub として新規起票>  # 追加指示で新規起票を求める
```

`--` で始まるトークンは、**引数文字列のどこに現れても**既知のフラグ（現在は `--refine` と `--check`）でなければエラーで停止する。トピックにも追加指示にも落とさない（typo が意図しない新規作成や指示文への埋没になるのを防ぐ）。

**トピック引数と `--refine` は併用できない**。`--refine` より前のトークンはすべてエラーで停止する（既知のフラグは 2 つだけで、`--refine` より前の `--check` は下記のとおり既にエラーなので、`--refine` の前に置けるものは何も無い）。会話で合意した作業のうち対象 Issue に属さないものを起票したい場合は、トピックを添えるのではなく `--refine` の後ろの追加指示で求める（手順 4 の「会話 → 新規 Issue」）。

`--check` は手順 2.5 の評価だけを行って停止するフラグ:

- `--refine` より後であればどこに現れてもよく、**残りの引数を解釈する前に取り除く**（番号リスト・追加指示の境界判定に影響させない）
- `--refine` を伴わない `--check`、および `--refine` より**前**に現れた `--check` はエラーで停止する（`--check` は `--refine` モードの修飾子で、モードが決まっていない位置では意味を持たないため。既知のフラグでも黙って受理しない）
- 実行するのは手順 1 → 手順 2 の「対象の確定」→ 手順 2.5 で、素材の蒸留と手順 3 以降は行わない（追加指示は判定の上書きに使うため読む）
- 名前が `--dry-run` でないのは、本リポジトリの他スキル（`review-response`）の `--dry-run` が「書き込み以外はすべて行う」を意味し、issue-draft ではドラフト作成まで含んでしまうため。`--check` は評価だけを行いドラフトを作らない

`--refine` の引数は「番号リスト + 追加指示」として読む:

- **番号リスト**: `--refine` の直後に続く Issue 番号トークンの並び。空白区切りが正準形で、`12,15`（カンマ区切り）・`#12 #15`（`#` 付き）も同じリストとして読む。列挙した Issue だけが書き換え対象で、それ以外は対象にしない（親を挙げても Sub は自動展開しない。加わるのは手順 2 でユーザーが承諾した Sub だけ）
- **番号リスト内の** `owner/repo#N` 形式のトークンはエラーで停止する（対象はカレントリポジトリの Issue のみ）。追加指示の文中に現れた同形式は指示テキストの一部であり、エラーにしない
- **境界の曖昧性**: 助数詞・助詞が続いて文の一部と読める数字（`2 回目`・`3 件`・`1 つ目`）はそこで番号リストが終わる。リスト継続中の `#` 付きトークンは常に Issue 番号として読む（追加指示の文中に現れた `#N` は指示テキストの一部で、対象には加えない）。**追加指示が数字で始まる場合**は、番号に `#` を付けるか、指示を改行して渡す
- **追加指示**: 番号リストより後の自由文。番号でも `--` でもないトークンはエラーではなく指示として扱う。これは手順 2 の「会話コンテキストがあれば補完に使う」を明示化したもので、スキルが Issue から推測した内容より優先し、手順 5 の判断のギャップの回答にもなる。指示が Issue のスコープを変える場合、その変更は他の変更と同様に手順 8 の変更点と手順 9 の編集通知コメントに載せる
- **番号の異常系**: 番号リストが空（`--refine` の直後が番号でない）ならエラーで停止、存在しない番号もエラーで停止、closed の番号はユーザーに続行可否を確認、重複した番号は黙って重複排除する

以降の手順は新規作成を基本フローとし、`--refine` 時の差分のみ各手順内に「`--refine` 時」として示す。差分が適用されるのは refine の対象 Issue のみで、フローの途中で新規作成する Issue には新規作成のルール（ロケール・ラベル選定）をそのまま適用する。これを**この実行で作成する Issue**と呼び、以降この名前で参照する（分割時の Sub-Issues・親 Issue 化時の新規の親・手順 4 の「会話 → 新規 Issue」で起票する Issue。経路を足すときに更新するのはこの 1 箇所）。対象が複数のときは同じ差分をセット全体に適用する（単一対象は N = 1 の場合であり、別のフローではない）。

## 前提条件
- Git リポジトリ内で実行すること（対象リポジトリの判定に使用）
- `gh` CLI がインストール・認証済みであること

## 実行内容

### 1. 対象リポジトリ確定
- `gh repo view --json nameWithOwner -q .nameWithOwner` で取得し、以降の書き込み系で `-R` に渡す

### 2. 素材の蒸留
- 会話コンテキスト（トピック引数があればそのトピックに絞る）から要件を抽出する
- **`--refine` 時**: 素材は既存 Issue の本文とコメント欄の議論。取得と素材の扱いは対象ごとに行い、提示と確認はセット全体で 1 回にまとめる（単一対象は N = 1）
  - **対象の確定（refine の他の作業より先に行う）**: `gh issue view <番号> --json title,body,labels,assignees,author,comments,updatedAt` で各対象を取得し、後続手順（ロケール・ラベル判定、変更点の提示、編集通知の要否判断、手順 7 のマニフェスト）でもこのスナップショットを再利用する（コンパクション等でコンテキストから欠落した場合のみ再取得する）。あわせて `ccx issue tree <番号>` を各対象に実行する（出力の読み方は `ccx issue tree --help`）。非ゼロ exit した場合は stderr を提示して停止する（親・Sub・依存の照会が 1 つでも読めなければ以降の親子判定が立たないため。「取得できなかったので飛ばす」は選ばない）。対象ごとの取得はいずれも独立のため並列実行する。取得できたら「対象: #12 <title> / #15 <title>、指示: <追加指示>」を**常に**提示する（指示が無ければその旨）。続けて以下の 2 つを、該当する場合のみ AskUserQuestion で**実行あたり各 1 回だけ**確認する（対象ごとではない。該当する対象が複数あっても 1 回にまとめる）:
    - **境界が曖昧だった場合**（番号リスト直後のトークンが数字で始まり、境界の曖昧性ルールで追加指示と判定した場合）: 解決した対象リストで合っているかを、以降の作業に費用をかける前に確認する。該当するトークンが無ければ確認せず進む
    - **Sub を挙げていない親が対象に含まれる場合**（`kind` が `parent` / `parent_and_sub` で、その Sub の一部が対象リストに無い）: それらの Sub も対象に加えるかを確認する
  - 対象が Sub（`parent` あり）なら親の本文も素材に含め、親に書かれた横断ルールを対象 Sub に複製しない（手順 4「仕様の配置」）。対象が親（`kind` が `parent` / `parent_and_sub`）なら Sub 一覧を把握し、親本文の書き直しが Sub の分担と矛盾しないようにする
  - **セット外の関連 Issue は読み取り専用素材**: 対象になっていない親・対象になっていない兄弟は、その本文をドラフトの材料にするだけで、書き換えない
  - 会話コンテキストがあれば補完に使う（追加指示があればそちらを優先する）
- **「会話の要約」ではなく「要件の蒸留」**: 経緯・試行錯誤は捨て、合意した結論のみを残す
- 合意事項を**番号付きリスト**として書き出す（手順 7 の突き合わせに使う）。**`--refine` 時**は、どの Issue も配置先にならない項目（列挙した対象でも、手順 2.5 で `不要` と判定した対象でも、セット外の読み取り専用の親・兄弟でもない）に印を付ける — 手順 4 の「会話 → 新規 Issue」と手順 7 の合意網羅チェックが同じ 1 本のリストからこれを読む。以下を漏らさず含める:
  - やらないと決めたこと（スコープ外）
  - 採用しなかった案と、採用しなかった理由（設計判断の再検討を防ぐ）
  - `~/.claude/CLAUDE.md`「設計判断原則」の greenfield 判定（一致 / 妥協と失う性質 / ユーザー決定）
  - 意図的に保留した判断（TBD）と、誰が・いつ決めるか
- セルフチェック: 会話で暗黙に合意したが明文化していない判断の拾い漏れがないか確認する

### 2.5. 評価（`--refine` 時のみ）

対象が現状のままで品質基準を満たしているかを判定し、満たしている対象は書き換えずにフローから外す（良い Issue に churn 編集と編集通知コメントを出さないため）。対象ごとに評価し（対象間の矛盾・重複の伝播だけが例外。下記「対象間の矛盾・重複の扱い」）、対象数に依らず同じ手順を踏む。

- **入力は現行本文**（ドラフトではない）。手順 2 の「対象の確定」で取得したスナップショットを使う。新規読者は現行本文を、`fresh-reader-verification` の「2. 依頼文」が定める既定範囲で、手順 7 と同じ対象の絞り込みのもとで実地検証する。起案者はここではギャップ調査もドラフト作成も行わない
- **品質基準チェック**（判定が開いている対象にのみ行う。下記「追加指示による上書き」）: 「品質基準」の各項目を現行本文に当てはめ、満たさない項目を挙げる。手順を参照している項目（「自己完結」→ 手順 7、「粒度」→ 手順 4）は**その手順の観点**を現行本文に当てはめて判定し、手順自体を実行していないことを不満足としない（literal に読むと全対象が常に `必要` になり、本手順の存在意義が消える）。「自己完結」の判定には下記の新規読者チェックの結果を使う
- **新規読者チェック**: 現行本文を scratchpad にスナップショットし（`gh issue view <番号> --json body -q .body`。手順 2 で本文を取得済みでもコマンドで書き出すのは、新規読者にはパスのみを渡す規約があり、かつ本文をモデル出力として再送しないため）、手順 7 の新規読者チェックと**同じ役割文・観点**で検証させる。**現行本文のスナップショットは全対象で書き出す**（下記の見出しの検査と、他の対象の読者が使う）が、**読者を起こすのは判定が開いている対象だけ**とする（下記「追加指示による上書き」）
  - **対象が Sub の場合**: 親の現行本文も同じ方法でスナップショットしてそのパスも渡し、役割文も手順 7 の分割時変種（親と合わせて読む版）に合わせる。親のスナップショットを使うのはその Sub 自身の読者だけなので、書き出すのは読者を起こす対象の親に限る
  - **他の対象の本文も渡す**: **列挙した他の全対象の現行本文のスナップショット**を渡し、依頼文では「同じセットでブラッシュアップする他の対象 Issue の現行本文」とラベルする。関係（親子・`depends_on`・明示参照）で絞らない — 互いに言及しないまま同じ値を別々に直している対がまさに動機で、関係で絞るとその対を落とす。渡すのは、対象間の矛盾が手順 4 の「対象間の重複」でしか解消できず、そのためには両者がフローに残っている必要があるため（片方が `不要` で抜けた後では移動・統合ができない）
  - **役割文への追加**: 手順 7 の `--refine` 変種と同じ「他の対象 Issue と重複・矛盾している記述も blocker として挙げよ」に加えて、次の 2 つを添える
    1. 「その blocker では相手の Issue 番号を明記せよ」（下記の伝播が番号に依存するため）
    1. 「他の対象の本文は重複・矛盾の検出にのみ使い、対象自身が単体で自己完結しているかの判定には使うな」（渡した本文を補助文脈にして自己完結性を過大評価させないため。分割時の親本文は「合わせて読む」前提なので扱いが異なる）
  - **実行順序**: 全対象のスナップショットを先に取得し、その後の対象ごとの検証は並列実行する（親を共有する対象が複数でも親のスナップショットは 1 つ）
  - **ここでの検証は 1 周のみ**とし、読者は読者台帳に載せない。ここでの判定は `必要` / `不要` の判定に消費されてそこで終わり、以降のドラフトに束縛されないため、`fresh-reader-verification` の無効化の対象になる判定を持たない（同スキルの 2 周収束も「指摘を反映したドラフト」を前提とするが、評価には修正対象のドラフトが無い）
- **見出しの検査**: 品質基準の「節の見出し」項を判定するため、対象ごとに現行本文のスナップショット（上記で書き出したもの）へ「本文の節」の検査を実行する。`--locale` は手順 6 の `--refine` 規定で決めた多数言語、`--kind` は `ccx issue tree` の `kind` を `standalone` → `leaf` / `sub` → `sub` / `parent`・`parent_and_sub` → `parent` に対応させる。リポジトリの issue テンプレートがあれば「本文の節」の対応付けを先に作って `--mapping` で渡す（テンプレート由来の見出しで落ちないようにするため。ここで決めたテンプレート選定と対応付けは手順 6 でそのまま使う）。本文の見出し違反をこの項目の不満足として扱い、他の品質基準ミスと同じく対象を `必要` にする（前提不成立は本文ではなく mapping ファイルか呼び出しの誤りなので判定に数えない — 直して再実行する。どの exit status が何かは `ccx issue sections check --help`）。対象ごとの検査は独立のため並列実行する
- **判定**: blocker または decision が 1 件以上、または品質基準の項目が 1 つでも満たされないなら `必要`。minor しか無ければ `不要`（手順 7 の収束条件と minor を反映しない既定を、ドラフトではなく現行本文に当てはめたもの）。decision が `必要` を作るのは、ユーザーの回答で本文が変わるため
- **decision の扱い**: ここで挙がった decision は、手順 5 の「判断のギャップ」と**同じ 1 ラウンド**でユーザーに聞く（プロトコルのラウンドを 2 回に分けない）。回答は blocker と同じくドラフトの入力として手順 5 へ引き継ぐ。`--check` は評価で停止するため、decision は報告するだけで聞かない
- **対象間の矛盾・重複の扱い**: 新規読者が報告した対象間の矛盾・重複は**両方の対象の blocker**として扱い、両方を `必要` にする（どちらの本文が持つかを手順 4 で決められるようにするため）。両者の新規読者が独立に気づくことは当てにせず、一方が報告した blocker を名指しされた対象へ**伝播**する。伝播の前に、名指しされた記述が両方のスナップショットに実在し、矛盾の主張ならその 2 つが実際に食い違うこと・重複の主張なら同じ内容が両方に置かれていることを**2 つのスナップショットの突き合わせで裏取りする**（コードベースの実地検証はしない）。裏取りできない主張は伝播せず、報告元の blocker としても採用しない（誤検知は良い Issue 2 つに書き換えと編集通知コメントを出すことになり、本手順が防ぐはずの churn そのものになる）。同じ矛盾が両側の新規読者から報告された場合は 1 件として扱う（裏取りも報告も 1 回）。名指しされた番号が列挙した対象でない場合（Sub の親・無関係な Issue）は伝播しない（対象でない Issue はフローに入らず編集できない）。報告元自身の blocker としては通常どおり数え、その対象は `必要` になる
- **追加指示による上書き**: 追加指示が対象への変更を求めているなら（「〜を追加して」「〜にしたい」等）、現行本文の判定に関わらずその対象は `必要` とする。明示的な要求を `不要` の判定で握り潰さないため。読み方を方向づけるだけの指示（「〜を前提にして」等）は `必要` にしない。`不要` を覆す手段は指示を添えた再実行のみで、別途の上書き確認は設けない
  - **評価は走らせない**: 判定が先に決まっているこの対象については、新規読者チェックも品質基準チェックも行わない（**この対象を検証する読者を起こさない** — スナップショットを渡す先は他の対象の読者だけになる。品質基準チェックの唯一の消費者は判定で、その「自己完結」項は読者の結果を読む）。書き換えると決まった本文への指摘は置き換わる記述にしか届かず、残る記述は手順 7 の読者がドラフトごと読むため。**見出しの検査は行う**（検査には現行本文のスナップショットが要り、ここで決めたテンプレートの対応付けを手順 6 が使う）
  - **報告**: `必要` と、その根拠として「追加指示による」と見出しの検査の結果を示す。自前の読者を持たないので blocker・decision・minor の一覧は無い（他の対象の読者から伝播した blocker は上記「対象間の矛盾・重複の扱い」どおり報告する）。指示自体は手順 2 で提示済みなので再掲しない
  - **他の対象の読者にはスナップショットを渡す**: この対象もセットの一員なので、その現行本文のスナップショットは上記「他の対象の本文も渡す」どおり他の対象の読者へ渡す。相手側から報告された矛盾・重複はこの対象へ伝播し、上記「対象間の矛盾・重複の扱い」どおり扱う（読者を起こさないことはセットからの除外ではない）
- **報告**: 対象ごとに、判定・blocker・decision・minor の一覧・満たさなかった品質基準の項目を提示する（判定が先に決まっていた対象の行の形は上記「追加指示による上書き」）。ドラフト作成に進む前に必ず提示する。`必要` と判定した対象の blocker と decision は手順 5 のギャップ調査・確認ラウンドの入力として引き継ぐ（手順 7 で再発見させると同じ調査が二重になる）。**例外は対象間の矛盾・重複の blocker**で、これは事実の欠落ではなく本文の配置の決定なので、手順 5 ではなく手順 4 の「対象間の重複」の入力として引き継ぐ（ギャップ調査は事実を集める手順で、どちらの Issue が持つかを決められない）
- **`不要` の対象はここでフローを抜ける**: ドラフト作成も本文の更新も編集通知コメントも行わず、手順 7 のマニフェストにも載せない。全対象が `不要` なら `--refine` は報告で終了する
- **以降の手順（3 以降）が扱う「対象」は `必要` と判定した対象を指す**。各手順に除外句を撒くと同じ規則が分散してドリフトするため、ここで 1 度だけ宣言する。宣言が語るのは**引数に列挙した対象**で、フローの途中でセットに加わる Issue（手順 3 の重複検索でヒットして加えたもの・手順 4 の「会話 → 新規 Issue」の配置で加えた親）は各手順の規定に従う。例外は次の 2 つ:
  - **例外 1（手順 3 の重複検索）**: 除外リストには `不要` を含む列挙した全対象を載せる（引数に挙げた Issue どうしが互いの類似 Issue として報告されるのを防ぐため）
  - **例外 2（手順 4 の親 Issue 化）**: リリース単位判定と、それに基づく親 Issue 化の提案は、`不要` を含む列挙した全対象を母集団とする（現行本文が単体では十分でも、親の Sub になれば「仕様の配置」により本文が変わるため）
    - 提案が承認されたら、**親 Issue 化で本文が変わる対象だけを `必要` に昇格**する: 親（`composition` 節に新しい Sub が載る）と、新たにリンクされる単独 Issue（`sub` の節構成で書き直す）
    - 既にその親の Sub で本文が変わらない対象は `不要` のまま据え置く（書き直しも本文の更新も編集通知コメントも行わない。本手順の churn 抑止の目的を保つ）
    - 昇格した対象は以降、手順 7〜9 を通常どおり通り、据え置きの対象は手順 7 のスナップショット扱いを維持する
    - 全対象が `不要` なら本例外は発火しない（手順 4 に進まないため、親 Issue 化の提案も行われない）
- **`--check` 指定時**: 判定に関わらず全対象がここで終了する（報告のみで、書き込みは一切行わない）

### 3. 重複検索
- `gh issue list --search "<キーワード>" --state all` で類似 Issue を確認（実装済み・wontfix の closed も重複検出の対象）
- 類似があればユーザーに提示し、続行可否を確認する
- **`--refine` 時**: 対象 Issue 自身（複数なら全対象）は検索結果から除外する（ブラッシュアップ対象が別の Issue と重複している可能性は新規作成時と同様にある）。対象どうしの重複は「重複あり、続行するか」の停止にはせず、手順 4 で解消する所見として扱う（どちらが持つかを決めて内容を移動・統合する）
  - 手順 4 の「会話 → 新規 Issue」の候補があれば、そのキーワードも新規作成時と同様に検索する。**ヒットは停止にしない**: 一致した Issue を提示し、扱いを選ばせる（セットに加える / その項目はその Issue に任せて新規作成しない）。セットに加えた Issue は手順 2 の取得（スナップショットと `ccx issue tree`）を行い、遅れて加わるので**手順 2.5 の評価をその時点で受け**、以降は対象として扱う。「セットに加える」の選択はその Issue へその項目を書く明示的な要求なので、手順 2.5 の「追加指示による上書き」と同じく判定に関わらず `必要` とする（そうしないと、現行本文が良い Issue で `不要` と判定され、項目がどこにも入らないまま消える）。**その時点で受けるのは見出しの検査だけで、新規読者チェックと品質基準チェックは行わない**（同項の「評価は走らせない」）。見出しの検査には現行本文のスナップショットが要るので、この Issue についても手順 2.5 と同じ方法で書き出す。キーワードが似ているだけの誤検知だった場合は候補のままで、手順 3 冒頭の続行可否の確認に戻る

### 4. 粒度判定

Issue と PR の対応は、Skill ツールで `github-sub-issues` を起動し、その「運用規約」（葉 Issue = 1 PR、親 = リリース単位、仕様の配置、PR 本文の規則）に従う。本手順はその規約の下で「分けるか・どこで分けるか」を判断する。

- **リリース単位の確定**: 機能として価値を出すために一緒にリリースすべき範囲を確定する。この範囲が 1 PR に収まるなら単一 Issue、収まらなければ**親 Issue（リリース単位）+ Sub-Issues（各 1 PR）**に分ける。1 Issue に複数 PR を示唆する散文（「PR 分割の目安」等）は書かない
- **分割トリガー（定性基準 + 承認）**: 実装が「単独でベースブランチにマージしても壊れない複数の段階」に自然に分かれ、1 PR にまとめるとレビュー困難と判断した場合に分割を提案し、ユーザー承認で確定する。数値閾値は置かない。ドラフト中に段階の一覧を書きたくなった時点が分割シグナル
- **Sub の境界**:
  - 独立してリリース可能で単体で価値が完結する縦切りがあればそれを優先する
  - 無ければ工程分割（schema → API → バッチ等）でよい。価値の完結（atomicity）は親 Issue が担保するため、Sub には要求しない
  - いずれも必須条件: **各 Sub は単独でベースブランチにマージしても壊れない**（運用規約の「Sub の必須条件」。最後の Sub まで配線しない設計と、親の `release_manual_steps` 節でリリースを揃える）
  - 時間的に必然分離される作業（デプロイ完了後の互換コード除去等、PR が別になることが確定しているもの）も Sub 境界になる
  - 各 Sub に依存（先行マージが必要な Sub）を添え、並列実装の可否を提示する
  - **`--refine` 時（対象 → 親 + 新規 Sub）**: 対象 Issue を親とし、その本文を親用に書き直した上で Sub-Issues を新規作成する
  - **`--refine` 時（既存の対象 → 既存/新規の親の Sub）**: 上と逆向きに、既に存在する対象たちを 1 つの親の Sub にする経路。上記「リリース単位の確定」でセット全体が 1 つのリリース単位だと結論した場合に限り、下記 2 変種のいずれかを**提案**し、既存の分割トリガーと同じ場所・同じ流れでユーザー承認により確定する（自動では行わない）。母集団は `不要` を含む全対象で、承認後の昇格は手順 2.5 の例外 2 に従う。**順序依存があるだけでは親を作らない**（その場合は下記「対象間の順序依存」）
    - **新規の親**: どの対象も親を持たず、どれも親でない（全対象が `kind: standalone`）→ 親 Issue を新規作成し、全対象をその Sub としてリンクすることを提案する
    - **既存の親**: 対象のうちちょうど 1 つが親（`kind` が `parent` / `parent_and_sub`）で、他に同じリリース単位に属する単独 Issue がある → それらをその親にリンクすることを提案する（既にその親の Sub である対象がセットに含まれていてもよい）
    - **既存の親の変種は、親になる対象の Sub 一覧が不完全な場合は発火させない**: `sub_issues_summary.total` と `sub_issues[]` の件数が食い違っていれば全部は届いていないので（`warnings[]` に count mismatch の行も載る）、手順 7 が求める `composition` 節の全 Sub 列挙を確定できない
    - **親が 2 つ以上ある場合**はどちらの変種にも当たらない → 提案せず通常の refine を続ける
    - **ユーザーが提案を辞退した場合**は対象を単独 Issue として refine する（新しい Issue は作成しない）。下記「対象間の順序依存」が通常どおり適用される
  - **`--refine` 時（会話 → 新規 Issue）**: 合意した作業のうち**どの Issue も配置先にならないもの**を新規 Issue として起票する経路。候補は手順 2 の合意事項リストで印を付けた項目と、追加指示が明示的に新規起票を求めた項目（「〜を新規起票して」等。印の有無に関わらず候補になる）。上記「粒度判定」を候補にも適用するので、1 つの提案が複数の Issue になることがある。上記の分割トリガー・親 Issue 化と**同じ場所・同じ流れ**で AskUserQuestion により確認し、承認なしには何も作成しない。確認が決めるのは「その Issue を作ること」と「どこに置くか」で、ドラフトの承認は手順 8 の 1 回の承認ラウンドで対象のドラフトと一緒に得る（セット全体が承認されるまで書き込まないという手順 8 の規則がそのまま効く）
    - 配置は**この順に判定**する:
      1. **列挙した対象に親がいる**（`kind` が `parent` / `parent_and_sub`。手順 2.5 で `不要` と判定した親も見る）→ 各新規 Issue をその親の Sub として提案し、親の `composition` 節へ依存とともに親のロケールで載せる。`不要` の親は `composition` 節が変わるので、手順 2.5 の例外 2 と同じく `必要` へ昇格する（ユーザーが引数に挙げた親なので、追加の確認はしない）。**親が 2 つ以上ある場合**は同じ AskUserQuestion でどの親に付けるかも聞く
      2. **対象がセット外の親を持つ Sub** → 同じ AskUserQuestion で、その親をセットに加えるかを聞く。加えるなら手順 2 の取得を行い、手順 2.5 の例外 2 が `composition` の変わる親を昇格させるのと同じく、個別の評価なしに `必要` へ昇格する。辞退されたらその親の Sub にはせず（編集できない `composition` 節が陳腐化するため）、単独の葉 Issue として提案する
      3. **全対象が単独** → 新規 Issue も単独の葉 Issue にする。対象との間のマージ順序は下記「対象間の順序依存」の規定どおりに表す
    - セット外の親を持つ Sub と単独の対象が**混在**する場合は、親を加えるかの質問を先に行い、その回答で 1 と 3 のどちらになるかが決まる
- **`--refine` 時（対象間の重複）**: 対象どうしの重複・矛盾は、**検出元を問わず**（手順 3 の重複検索・手順 2.5 の評価で挙がった blocker のいずれも）ここで、どちらの Issue が持つかを決めて内容を移動・統合する（両方に残さない — 「仕様の配置」と同じ理由）。新規 Issue が対象と重複していた場合も同じ規則で解消する
- **`--refine` 時（対象間の順序依存）**: 対象が 1 つの親の Sub ではなく、セットがリリース単位でもないが、マージ順序が決まっている場合は、その順序を GitHub の `blocked_by` リンク（手順 9 で登録）と本文の `depends_on` 節の**両方**で表す。順序の根拠は追加指示、無ければ各本文の記述。作成するリンクは手順 8 の承認で一覧提示し、ユーザーの確認を得る（運用規約どおりリンクが順序の正で、散文は読者のために残す）
- **仕様の配置**: 運用規約の「仕様の配置」に従い、横断ルールは親にだけ、段階固有のスコープ・受け入れ条件は Sub にだけ書く（複製はドリフトの元）。Sub の自己完結基準は「親と合わせて読めば迷わず実装できる」
- 分割とは別に、**価値の取捨チェック**を行う: Issue 内に「削っても残りの機能が成立する、相対的に価値の薄い部分」が無いか確認する。見つかった場合はスコープ外へ移す・後続 Issue に切り出す選択肢を理由とともに提示し、ユーザーの判断を仰ぐ（勝手に削らない — 仕様遵守原則）。手順 7 のデッドスペックチェックが検出するのは「消費者の無い構成要素」であり、消費者はいるが価値の薄い機能はこのチェックでしか拾えない（分割判定は「1 PR に収まるか」で決まり低価値部分を落とす契機を含まないため、その機会をここで直接確保する）

### 5. ギャップ調査
- 「本文の節」の各節を埋める観点で、会話に無い・未確定の情報を列挙し（壁打ちが薄い場合も全節を確認）、事実か判断かで扱いを分ける:
  - **事実のギャップ** → コードベース・CI ログ・`gh` 等の追加調査で埋める（独立した調査は並列実行する）。特に:
    - **原因・現状認識**: 仮説のままにせず、コードや記録を読んで裏付ける
    - **参照コード**: 実装者が読みに行く前提にせず、短い該当箇所は本文に引用する。参照はファイルパス + 関数名・型名等の grep 可能な識別子で示し、**行番号は書かない**（起票から実装までにズレて誤参照になる上、手順 7 の検証で行番号の突き合わせ・軽微なズレ指摘にコストを浪費するため）
    - **再現・検証手順**: 実際に機能することを確認する
  - **判断のギャップ**（要件の取捨・スコープ・受け入れ水準等）→ 調査では埋まらないため、ドラフト前にユーザーに確認する
- 合理的な調査で埋まらない事実は、隠さず「未確認」と明示し、確認方法とともに本文に残す（判断は「未確認」のまま実装者に渡さない）
- 節スキーマに対応するキーが無い情報（再現手順等）は最も近い節に含める
- 調査結果が重複・粒度の前提を変えた場合は手順 3〜4 を再評価する
- **`--refine` 時**: ギャップ調査はセットで 1 回にまとめる（対象ごとに独立して回さない。同じ調査の重複と、対象間で矛盾する結論が出るのを防ぐ）

### 6. ロケール・ラベル判定
以下の2コマンドは独立のため並列実行する:
- `gh issue list --limit 5` で既存 Issue の言語慣例を確認し、**ロケールを `ja` / `en` のいずれかに決める**。以降のすべて（タイトル・見出し・本文・「なし」等の固定文字列・手順 9 の編集通知コメント）がこのロケールに従う
  - 慣例がどちらでもない場合は `ccx issue sections list --locale <その言語> --kind leaf` を実行し、**stderr のエラーをそのまま提示して停止する**
- `gh label list` で既存ラベルを取得し、内容に合うものを選定（合うものが無ければ付けない。新規ラベルは作らない）
- **`--refine` 時**: 言語確認（`gh issue list`）はスキップし、ロケールは**対象 Issue の現行本文の多数言語**で決める（対象ごとに決める。この実行で作成する Issue は素材となった対象のロケールに従い、置き先の親があるならその親のロケールを使う）。多数言語はフェンス付きコードブロックを除いてから字種を数える（日本語の Issue が英語のコード引用を大量に含むことがあるため）。手順 2.5 で既に算出している場合はその値を再利用し、再計算しない。どちらのロケールでもないときの停止は上と同じ。`gh label list` のみ実行し、既存ラベルは維持した上で内容に合う追加候補があればドラフト提示時に提案する
- リポジトリの issue テンプレートがあれば「本文の節」の対応付けをここで行う（`--refine` は手順 2.5 で決めた選定と対応付けをそのまま使い、選び直さない）

### 7. 自己完結検証（ドラフト提示前に必須）

ドラフトは会話に直接書かず、**最初から scratchpad 直下のファイルとして Write する**（分割時は親・各 Sub-Issue で 1 ファイルずつ、`--refine` では 1 対象につき 1 ファイル。この実行で新規作成する Issue にも 1 ファイルずつ起こす）。以降の修正はすべてこのファイルへの Edit で行い、手順 9 では同じファイルをマニフェストが名指す。理由: 承認済み文面を作成時に再転記することによるドリフトと、長い会話のコンパクションによる細部欠落を防ぐ。scratchpad 直下に置くのは、`ccx issue publish` がドラフト・編集通知コメント・`<ドラフトファイル名>.mapping` をマニフェストと同じディレクトリで裸のファイル名として解決するため。

**番号プレースホルダー**: まだ採番されていない Issue 番号は `#{NAME}` と書く。`NAME` はそのドラフトでの役割を表す大文字とアンダースコアの名前（`#{PARENT}`・`#{SUB_A}`）。置換前の本文が GitHub に届く経路が実在するため（親は Sub より先に作成され、`composition` 節を後から埋める）、レンダリングに耐える形が要る。山括弧で名前を囲む形（`#` の直後に `<` を置く形）は GitHub の renderer が HTML タグとして落とすため使わない — 置換までの間ずっと素の `#` だけが表示される。フェンス付きコードブロックとインラインのコードスパンの中は置換されないので、Ruby・Elixir の文字列補間をそのまま引用してよい。

**マニフェスト（`--refine` 時、およびこの実行で作成する Issue があるとき）**: ドラフトファイルとは別に、セッションの scratchpad 直下へ固定名 `publish-manifest.json` で書き、フローの進行に合わせて更新する。単一対象でも、新規作成フローの分割で親 + Sub を作るだけのときも同じ形で作る（手順 9 が経路に依らずこの 1 ファイルを渡すため）。書き方は `ccx issue publish --help` が持つ。固定名で持つ目的は 2 つ: コンテキストのコンパクション後にパスを知らなくても再発見できること、手順 9 の書き込みが途中で止まった場合に同じファイルを渡し直せば続きから走ること（どこまで書き込み済みかはコマンドが自分の記録で持つので、状態を手で管理しない）。

**この実行で初めてマニフェストを Write するときは、隣の記録ファイル（`publish-manifest.json.published`）が残っていれば削除する**。固定名なので前の実行の記録が残っており、プレースホルダー名（`PARENT`・`SUB_A` 等）は実行をまたいで同じになるため、消さないと前の実行の続きとして読まれる。鮮度拒否からの再実行では消さない（そこは同じ実行の続きで、記録が要る）。コマンド側も食い違いを検出して拒否するが、それは取りこぼしへの網であって、消すのはこちらの責任。

行に載せる判断はこのスキルが持つ:

- **`updated_at`** には手順 2 で取得したスナップショットの値を使う（コマンドはこれと現状を突き合わせ、動いていたら書き込まずに拒否する）
- **ラベル**はその Issue が最終的に持つ集合を書く（追加分だけではない。既存 Issue なら手順 2 のスナップショットのラベルに手順 6 で足すものを足した集合）
- **`parent`** と **`blocked_by`** に既存 Issue を素の番号で書くときは、その Issue に行は要らない（この実行で本文を書き換えない Issue にドラフトを起こす必要はない）。プレースホルダーで書くときだけ、その行が要る
- **`blocked_by`** に載るのは、手順 4 で決めた対象間の順序依存、親 Issue 化で親本文の `composition` 節が新たに示す依存（既存の親に元から張られている依存は再登録しないので載せない）、この実行で作成する Issue 自身の依存、および既存対象のその Issue への依存。ここが一覧の単一の宣言で、手順 8 の提示も手順 9 の登録もこの宣言を使う
- **`comment`** は手順 8 で承認を得た編集通知コメントのファイル名（要否の判断は手順 8）

**読者台帳（`reader-manifest.md`）**: `fresh-reader-verification` が起動時の記録を消費者に求めるので、新規読者チェックで起動した読者を 1 行ずつ持つ表を、固定名 `reader-manifest.md` で置く。配置と固定名の目的はマニフェスト（上記）と同じ。この実行で最初に書くときは Write で上書きし、前の実行の残骸へ Edit で行を足さない（残骸の行を引いて存在しない読者へ差し戻すのを防ぐ）。

```markdown
| 対象 | 渡したファイル | 消化した周 |
|---|---|---|
| #12 | 12-draft.md, 15-draft.md | 1 |
| #{SUB_A} | sub-a-draft.md, parent-draft.md | 2 |
```

対象は検証させる Issue（既存なら番号、この実行で作成するならプレースホルダー名）、渡したファイルはその読者の**現在の**集合の裸のファイル名（差し戻しで集合に加えたら書き足す）、消化した周とその数え方は同スキルの上限規則が持つ。手順 2.5 の評価の読者は載せない（除外の根拠は同手順が持つ）。

**親 Issue 化時（手順 4 で承認された場合）**: 親は「本文の節」の `parent` の節構成で起こし、`composition` 節は**既存の対象を Sub にする分を実番号**で列挙する（対象は既に存在するため、その分に「Sub 作成後の番号埋め」は要らない。同じ実行で作成する Issue もその親の Sub にする場合、その行はプレースホルダーになる）。既存の親の変種では、対象リストに無いその親の既存 Sub も `composition` 節に載せる（手順 2 で把握済み。一覧から漏らすと運用規約の読み取り事故になる）。

- **新規の親**: 親ドラフトは新規 Issue なので新規作成のルールに従う。言語は手順 6 の `--refine` の規定（対象本文の言語）。タイトルはリリース単位の名前として起案者が決める（追加指示、無ければ対象の共通テーマから）。マニフェストの行は上記のとおりプレースホルダーをキーに置く
- **既存の親**: 親は対象の 1 つなので、そのドラフトは refine 後の本文（`parent` の節構成・`--refine` のルール）で、`composition` 節に新しくリンクする Sub を加えた形になる
- 新たにリンクする単独 Issue は `sub` の節構成で書き直す（`background` 節は親を参照し、`depends_on` 節を持ち、親の横断ルールを複製しない — 「仕様の配置」）。新規の親の変種では親番号を `#{PARENT}` と書き、親の作成後に置換する（既存の分割パスと同じ機構）
- 新規読者チェックは下記の分割時の規定どおり（親ドラフト単体と、各 Sub ドラフト + 親ドラフト）

ドラフト作成者自身のチェックは「会話を知っているから読めてしまう」バイアスで穴を見逃すため、作成者自身のチェック（1・2）に加えて、会話コンテキストを持たない読者による検証（3）を必ず行う:

1. **合意網羅チェック（会話 → 本文）**: 手順 2 の合意事項リストの全項目を、ドラフト本文と 1 項目ずつ突き合わせる。本文に無い項目は追記する（分割時はどの Sub-Issue が担うかも確認。配置先が書き換えない Issue — セット外・`不要` 判定 — になる項目は追記せず、突き合わせだけ行う）。**どの Issue も配置先にならない項目**のうち手順 2 の印付けが取りこぼしたものは、手順 5 の「調査結果が前提を変えた場合は手順 3〜4 を再評価する」機構で手順 3〜4 に戻し、候補の重複検索を経て手順 4 の「会話 → 新規 Issue」の提案にかける（手順 4 で既にユーザーが起票を辞退した項目は戻さない — 決着済みの判断を問い直さない）
2. **デッドスペックチェック（構成要素 → 消費者）**: 本文が指定する具体的な構成要素（構造体フィールド・環境変数・引数・設定値・ファイル等）それぞれについて、それを消費する要件・受け入れ条件を確認する。消費者が無い要素は削除するか、維持する理由と消費者（後続 Issue・外部システム等）を本文に明記する。参考実装からのパターン踏襲で紛れ込みやすく、「既存との一貫性」は消費者の代わりにならない（実装者は仕様遵守原則に従い本文の要素を勝手に削除できないため、消費者の無い要素はデッドコードとしてそのまま実装され、レビュー指摘に対しても「Issue に明記」を根拠に防衛された事例あり）
3. **新規読者チェック（本文 → 読者）**: Skill ツールで `fresh-reader-verification` を起動し、そのプロトコルに従って**ドラフトファイルのパスのみ**を渡して検証させる。読者を起動したら、渡したファイルとともに上記の読者台帳へ 1 行書く。同スキルの「依頼文」に差し込む役割と検証観点:
   > あなたはこの Issue にアサインされた実装者で、起案時の議論は一切読めない。この Issue 単体で実装に着手できるか評価せよ。
   >
   > 実地検証の対象は評価対象の本文に限る（あわせて渡された親・他の対象の本文の主張は実地検証しない。それらは役割文の指示どおりに読む）。

   渡すドラフトに `#{NAME}` プレースホルダーが含まれる場合は、**どの変種の役割文にも**次の 1 文を添える: それらは同じ実行で作成する Issue を指し作成後に実番号へ置換されるので、プレースホルダーであること自体は指摘しなくてよい。ただしプレースホルダーが指す先の矛盾（`depends_on` 節が親の `composition` 節と異なる順序を示す等）は通常どおり報告する。

   分割時は Sub ごとに検証し、**Sub ドラフトのパスに加えて親ドラフトのパスも渡す**（役割文は「この Sub にアサインされた実装者。親 Issue と合わせて読んで着手できるか評価せよ。親と Sub で重複・矛盾している記述も blocker として挙げよ」）。親ドラフト単体も検証する（横断ルール・`composition` 節の一覧・`release_manual_steps` 節が Sub を知らない読者に読めるか）。

   **`--refine` 時**: 対象ごとに検証し、その対象のドラフトに加えて**他の全対象のドラフトのパスを渡す**。関係で絞らないのは手順 2.5 の「他の対象の本文も渡す」と同じ理由で、互いに言及しないまま同じ値を別々に直している対を落とすため（同項のもう 1 つの理由 — 両者がフローに残っている必要がある — は手順 7 では既に成立している）。ドラフトが参照する先がセット外の読み取り専用の親等、または手順 2.5 で `不要` と判定した対象であれば、その現行本文を scratchpad にスナップショットしてそのパスを渡す（後者はドラフトを持たないため）。役割文に「他の対象 Issue と重複・矛盾している記述も blocker として挙げよ」を加え、手順 2.5 の「役割文への追加」と同じ 2 つを添える（「その blocker では相手の Issue 番号を明記せよ」「他の対象のドラフトは重複・矛盾の検出にのみ使い、対象自身が単体で自己完結しているかの判定には使うな」）。渡したドラフトは役割文でラベルし、**合わせて読む親のドラフト**（上記分割時変種の扱い）と**重複・矛盾の検出にのみ使う他の対象のドラフト**（「同じセットでブラッシュアップする他の対象 Issue のドラフト」）を区別する。ここでの「対象」は手順 2.5 の宣言どおりで、この実行で作成する Issue のドラフトは含まない（それは上記の親子関係の規定で渡る）。

指摘への対処は同スキルの規定に従い、本スキル固有の扱いを 3 点加える:
- **blocker（事実の不足）** → 手順 5 のギャップ調査で埋めて本文に追記する
- **decision** → プロトコルの 1 ラウンドで確認し、回答は手順 8 の承認前に本文へ反映する。現状維持と決めた回答は `deferred` 節に「質問・回答・理由」の 1 行として残す（記録されない回答は反映済みにならない — プロトコルの収束条件）
- **minor** → 原則本文に反映しないが、実装者が「見落とし」と誤解しそうな項目のみ、`deferred` 節に推奨・判断基準つきの 1 行で吸収する
- **編集したら台帳を引く** → ドラフトまたはスナップショットを編集したら `reader-manifest.md` を読み、そのファイルを集合に持つ読者を引いて、同スキルの「判定は渡したファイルに束縛される」を適用する。**この手順の同期点は手順 8 の提示の直前**で、提示はそこで送った差し戻しがすべて返ってから行う。差し戻しを送ったら台帳のその行（消化した周、集合に加えたファイルがあればそれも）を更新する

過剰詳細化ガード: 対象リポジトリの既存慣習・参照ドキュメントから一意に決まる内容は追記しない（本文が長いほど実装成功率が下がる。「〜の既存パターンに従う」の一文と参照先で足りる）。

### 8. ドラフト提示 → ユーザー承認
- タイトル・本文・ラベル（分割時・親 Issue 化時は親子構成と親・各 Sub-Issue の本文すべて）を提示し、承認を得てから作成・更新する
- **`ccx issue publish <マニフェスト> --dry-run` を実行し、その出力もドラフトと並べて提示する**（何が作られ・リンクされ・書き換えられ・登録されるかを、承認の対象に含めるため）。非ゼロ exit なら停止し、stderr が挙げる違反をすべて直して再実行する。直す先は違反ごとに違う（ドラフト本文・マニフェストの行・`.mapping` ファイル）。握り潰し・スキップはしない
- リポジトリの issue テンプレートに従った場合は、選んだテンプレート・選定理由・キー → テンプレート見出しの対応付けも提示に含める（テンプレート無しで進めた場合はその判断と理由）
- 承認対象は**ファイルの最終版全文**とする（修正を重ねた場合、差分の積み重ねだけで承認させない）
- **編集通知コメント**（`--refine` 時、既存 Issue の起案者・コメント参加者に自分以外がいる場合。自分のログイン名は `gh api user -q .login` で確認）: 提示する変更点を本文とするコメントを起案し、同じ承認ラウンドで承認を得る（既読者が黙った書き換えに気付けないままになるのを防ぐ）。承認できたら scratchpad 直下にファイルとして Write し、マニフェストのその行の `comment` に置く（投稿は手順 9 が行う）。対象が複数でもコメントは Issue ごとに起案し、同じ実行でブラッシュアップした他の Issue の番号も本文に添える。この実行で作成する Issue には既読者がいないので起案しない
- **`--refine` 時**: 全文に加えて現行本文からの主な変更点を添えて提示する（追加指示によるスコープ変更も変更点に含める）。対象が複数なら:
  - 全対象のドラフト全文と各々の変更点を **1 回の承認ラウンド**で提示する（この実行で新規作成する Issue のドラフトも同じラウンドに含める）。マニフェストの `blocked_by` の一覧も添える
  - 対象ごとの修正指示を受け付ける（当該ファイルへの Edit。編集後の扱いは下記の共通ルールと同じ）
  - **セット内の全ドラフトが承認されるまで手順 9 の書き込みに進まない**（承認済みの一部だけ先に書き込むと、まだ書き込まれていない相手を参照する本文が公開される）
  - 関連の無い Issue を 1 セットにしても、単一対象の refine を順に実行するのと比べて得るものは無い（セット化の価値は対象間の重複・矛盾・順序の解消にあるため）
- Issue は外向き公開物のため、承認は省略しない
- ユーザー修正はファイルへの Edit で反映する（編集後の扱いは手順 7 の「編集したら台帳を引く」）

### 9. 作成・更新

```bash
ccx issue publish <マニフェスト>
```

これが書き込みの全部で、経路（新規作成・`--refine`・親 Issue 化・分割）による違いは無い。作成・リンク・プレースホルダーの置換・本文とラベルの更新・編集通知コメントの投稿・`blocked_by` の登録を、その順で行う。承認済みのドラフトファイルはそのまま渡す（承認後に本文を書き直さない）。

- **非ゼロ exit なら停止する**。何も書かれていないか、どこまで書かれたかがコマンドの記録に残っているかのどちらかで、stderr がどちらかを言う。直したら**同じマニフェストをもう一度渡す**（済んだ分は飛ばして続きから走る）。握り潰し・部分的な手作業での代替はしない
- **鮮度で拒否された場合**（既存 Issue がドラフト作成後に動いていた）: その対象を手順 2 に戻す。現行本文とコメントを取り直し、入った変更をドラフトへ取り込み、手順 7 を再実行し、手順 8 でそのセットの再承認を得る。ここだけは「編集したら台帳を引く」ではなく手順 7 の全体をやり直すのは、入った変更が自分の編集ではなく外から来たもので、既存の読者が持つ文脈の外にあるため（新しい読者に初読させる価値がある）。マニフェストのその行の `updated_at` を取り直した値に更新してから `publish` を再実行する
- マニフェストの組み立て（どの行を置くか・`blocked_by` に何を載せるか）は手順 7 の規定に従う。経路ごとの判断はそこに閉じている:
  - **親 Issue 化時**: 新規の親は行を 1 つ増やす（キーはプレースホルダー）。既存の親は対象の 1 つなので既に行がある。新たにその親の Sub にする対象は、その行の `parent` に親のキーを置く。既にその親の Sub である対象と、手順 4 の除外規則で外した対象には置かない。対象が Sub になった以上「対象間の順序依存」は `blocked_by` に載せない
  - **分割時・「会話 → 新規 Issue」時**: 作成する Issue の行を置き、Sub には `parent` を置く。単独の葉として提案したものは `parent` を持たない
  - **`--refine` 時**: アサインは変更されない（`publish` は作成時にしかアサインしない）。「リンク後の親Issue本文同期」を別の編集として行わない — 親の `composition` 節は承認済みドラフトに既に載っており、同じ更新で書かれる
- Sub 間の順序は `blocked_by` の登録が正で、`depends_on` 節の文面は可読性のためそのまま残す（運用規約）

### 10. 完了報告
- 作成・更新した Issue の URL（`publish` の出力が持つ）を提示し、次アクションとして `/issue-handle <番号>` を案内する
- `publish` が縮退を報告した場合（ラベル・アサインが適用されなかった）は、その内容も報告する
- **`--refine` 時**: 対象が複数なら全対象の URL を提示する。手順 2.5 で `不要` と判定した対象は URL を提示せず、判定を再掲する（親 Issue 化時の扱いは次項が優先する）。手順 4 の「会話 → 新規 Issue」でユーザーが起票を辞退した合意事項は、ここで列挙する — どの対象の本文にも書かない（最寄りの対象へ書けば仕様の置き違いになる）
- この実行で Issue を作成した場合: 作成した全 Issue の URL を提示し、`/issue-handle` の対象は依存の無いものから順に着手することを案内する。親がいるなら親と各 Sub をまとめて示し、親は全 Sub 完了後に `/issue-handle <親番号>` で充足検証 → close できることを添える。親 Issue 化時は `不要` のまま据え置いた対象も Sub の一覧に URL 付きで含め（構成として欠けると読み取り事故になるため）、本文は据え置きである旨を添える

## 本文の節

本文の節は**意味キー**で識別する。キー ↔ 見出しの対応・kind ごとの必須条件・「なし」の固定文字列を持つのは `ccx issue sections` だけで、**この SKILL.md に表を複製しない**（複製はドリフトの元）。

### 見出しの取得

```bash
ccx issue sections list --locale <ja|en> --kind <leaf|sub|parent>
```

`--locale` は手順 6 で決めたロケール、`--kind` は Issue の種別（単独 Issue = `leaf`、分割時の親 = `parent`、Sub = `sub`）。出力の読み方は `ccx issue sections list --help` にある。

**節の並びは下の kind ごとの一覧が正**（`sections[]` の並びはレンダリング順ではない）。

### kind ごとの節と書き方

各節の見出しは `heading`（決定したロケールの canonical 見出し）を `## ` に続けてそのまま書く。`required` が false のキーは、内容が無ければ節ごと削除する。逆に、一覧に無い既知キーが既存本文にある場合（parent の `requirements` 等）は、内容があるかぎり残す（検査は既知の見出しとして通す）。

**`leaf`（単独 Issue）**:

1. `background` — なぜこの作業が必要か。担当者が判断に迷ったとき立ち返る基準。末尾に設計判断原則の greenfield 判定
2. `depends_on` — 先行マージが必要な Issue。GitHub の `blocked_by` リンクが順序の正で、この節は読者向け
3. `requirements` — must の列挙。曖昧語は具体化する — 「速くする」ではなく「0.5秒以内」
4. `acceptance` — `- [ ]` のチェックリスト。観測可能な振る舞いで書き、実装詳細は書かない。エッジケースを明記する
5. `affected_code` — ファイルパス・grep 可能な識別子（関数名・型名等。行番号は書かない）・関連 Issue/PR リンク
6. `impl_notes` — 断定せず「案」として。複数案あるなら推奨案とその理由を明示する。検討して採用しなかった案は不採用理由も書く — 実装者による再検討・逆行を防ぐ
7. `deferred` — 意図的にオープンにする判断の列挙。各項目に推奨と判断基準を添える。見落としではなく意図的な保留であることを読者に示す。**確定した現状維持の回答**（手順 7 の decision の扱い）もここに置く — 保留と決着のどちらも「この問いは検討済みで、実装者が蒸し返す必要はない」を示す点で同じ働きをするため
8. `out_of_scope` — 壁打ちで「やらない」と決めたことの明記

**`parent`（分割時の親 Issue。リリース単位であり、実装対象ではなく Sub の束と横断ルールの置き場。各節の意味は運用規約）**:

1. `background` — リリース単位として何を届けるか。Sub 共通の判断基準。末尾に設計判断原則の greenfield 判定のうちリリース単位に効くもの
2. `composition` — 依存順の一覧。Sub 作成後に番号を埋める。`1. #{SUB_A} — <一言> — 依存: なし` / `2. #{SUB_B} — <一言> — 依存: #{SUB_A} のマージ後` の形で 1 行 1 Sub（節本文なのでこの散文も決定したロケールで書く。en なら `— depends on: none` / `— depends on: #{SUB_A} merged`）
3. `cross_cutting` — 全 Sub に効く要件。エラーコード等の確定値・トランザクション順序・共通の参照文書等。Sub には複製しない
4. `acceptance` — `- [ ]` のチェックリスト。「上記 Sub-Issues がすべて close されている」に加え、リリース単位として観測可能な条件があれば書く（個々の Sub の条件は各 Sub に書く）
5. `release_manual_steps` — `none_markers` の「なし」マーカー、または手動マイグレーション・インフラ設定・スケジューラ有効化等のチェックリスト
6. `out_of_scope`

**`sub`（1 PR で完結する段階。タイトルは接頭辞なし — 運用規約「Sub のタイトル」）**:

1. `background` — 1〜2 行。親 `#{PARENT}` のどの段階かと、この Sub 固有の目的。親の背景を再掲しない。末尾に設計判断原則の greenfield 判定のうちこの段階固有のもの（横断的な判定は親に置く — 運用規約「仕様の配置」）
2. `depends_on` — 先行マージが必要な Sub。無ければ `none_markers` の「なし」マーカー
3. `requirements` — この段階の must。横断ルールは親を参照し、複製しない
4. `acceptance` — `- [ ]` のチェックリスト。この段階だけで観測可能な振る舞い。単独マージで壊れないことも条件に含める — 未配線・未スケジュールの扱いを明記
5. `affected_code` — `leaf` と同じ
6. `impl_notes` — `leaf` と同じ
7. `deferred` — `leaf` と同じ
8. `out_of_scope` — この Sub で扱わず他の Sub が担う範囲

### リポジトリの issue テンプレートへの対応付け

対象リポジトリに `.github/ISSUE_TEMPLATE/` があるときだけ実施する（無ければ canonical 見出しのまま書く）:

1. **選定**: 内容適合でテンプレートを 1 つ選ぶ。YAML フォーム（`.yml` / `.yaml`）は `body[].attributes.label` の値をそのテンプレートの見出しとして数え、markdown テンプレート（`.md`）は本文の `## ` 見出しを見る。内容に合うテンプレートが無ければテンプレート無しで進める（canonical 見出しのまま）
2. **対応付け**: `template_mappable: true` のキーをテンプレートの節へ意味で対応させ、対応先の見出し・順序・言語をそのまま使う。対応先の無い必須キーは末尾に canonical 見出しで追加する。`template_mappable: false` のキーは対応付けず、canonical 見出しのまま置く（他スキルが機械的に探す節のため）
3. **記録**: 対応付けは**対象ファイルと同じディレクトリに `<対象ファイル名>.mapping`** として書く（対象は手順 2.5 では現行本文のスナップショット、手順 7 のドラフト以降はドラフトファイル。ドラフトは手順 7 まで存在しないので、この名前だけが両方の時点で決まる。決め打ちの名前にするのは、コンパクション後にパスを知らなくても再発見するため）。下記の検査には `--mapping` で渡し、`ccx issue publish` はドラフトの隣にあるものを自分で見つける。テンプレートの選定と対応付けの内容は実行あたり 1 回決め、対象が複数あれば同じ内容を各ファイルに書く。形式は 1 行 1 件 `<key> <テンプレートの見出し>`（`ccx issue sections check --help` 参照）

実施タイミングは新規作成が手順 6、`--refine` が手順 2.5（非 canonical な見出しの検出に mapping が要るため。手順 6 では選び直さない）。

**`--refine` のリライト時**: 見出しを決定したロケールの canonical に揃える。ただしテンプレートに対応付いた見出しは維持し、canonical 化の対象は対応先の無い見出しだけにする。

### 検査

```bash
ccx issue sections check <検査対象ファイル> --locale <ja|en> --kind <leaf|sub|parent> [--mapping <mapping ファイル>]
```

非ゼロ exit なら**停止**し、stderr に 1 行 1 件で出る理由に従って直して再実行する。直す先は exit status で分かれ、本文の見出し違反は検査対象ファイル、前提不成立は mapping ファイルか呼び出し（どの exit status が何かは `ccx issue sections check --help`）。いずれも握り潰し・スキップ・上書きはしない。

呼ぶのは手順 2.5（現行本文のスナップショットを評価する）。書き込む直前のゲートとしては呼ばない — `ccx issue publish` が同じ検査を全ドラフトに対して自分で行い、通らなければ何も書かずに拒否する。

## 品質基準

ドラフト提示前に以下を自己チェックする（共通原則: 未解決の判断や裏付けの無い主張をそのまま実装者に渡さない）:
- [ ] タイトル: 命令形の具体的な一文（後から見て文脈がわかる）
- [ ] 自己完結: 壁打ちの会話を読まなくても Issue 単体で実装可能 — 手順 7 の検証（合意網羅チェック・デッドスペックチェック・新規読者チェック）を完了し、blocker が無く decision がすべて回答・反映済みの状態に到達している
- [ ] 節の見出し: 決定したロケールの canonical 見出し（リポジトリの issue テンプレートに対応付けた節はテンプレート側の見出し）になっており、「本文の節」の検査が通る
- [ ] 粒度: 手順 4 の判定（葉 Issue = 1 PR、分割時は Sub の必須条件・仕様の配置・親の必須節）を通過している
- [ ] concise but complete: 冗長化させない（本文が長いほど AI エージェントの実装成功率が下がる）
- [ ] 受け入れ条件の完全性: 全項目が満たされたら、かつその時のみ完了と言える
- [ ] 事実と仮説の区別: 裏付けの無い記述を検証済みであるかのように書いていない
