# /issue-draft

壁打ちで固めた内容を「迷わず実装できる」GitHub Issue として構造化・作成する。`--refine` では既存 Issue を素材に、同じ品質基準へブラッシュアップして本文を更新する。

## 使用方法
```
/issue-draft                                    # 直前の会話から要件を抽出して新規作成
/issue-draft <トピック>                         # 会話のうち指定トピックに絞って抽出
/issue-draft --refine <番号>                    # 既存 Issue をブラッシュアップして本文を更新
/issue-draft --refine <番号>[,<番号>...] [追加指示]  # 複数 Issue を 1 セットとしてブラッシュアップ
/issue-draft --refine <番号>[,<番号>...] --check  # 評価だけ行い、書き換えずに判定を報告
/issue-draft --refine <番号>,<番号> <指示: 会話で合意した X を 1 つ目の Issue の Sub として新規起票>  # 追加指示で新規起票を求める
```

`--` で始まるトークンは、**引数文字列のどこに現れても**既知のフラグ（現在は `--refine` と `--check`）でなければエラーで停止する。トピックにも追加指示にも落とさない。

**トピック引数と `--refine` は併用できない**。`--refine` より前のトークンはすべてエラーで停止する。会話で合意した作業のうち対象 Issue に属さないものを起票したい場合は、`--refine` の後ろの追加指示で求める（手順 4 の「会話 → 新規 Issue」）。

`--check` は手順 2.5 の評価だけを行って停止するフラグ:

- 番号リストより後であればどこに現れてもよい
- `--refine` を伴わない `--check`、および `--refine` より**前**に現れた `--check` はエラーで停止する
- 実行するのは手順 1 → 手順 2 の「対象の確定」→ 手順 2.5 で、素材の蒸留と手順 3 以降は行わない（追加指示は判定の上書きに使うため読む）。合意事項リストが無いので**内側 / 外側の判定は適用せず**、読者の decision をそのまま数える（この 1 点で判定が本実行と食い違うことがある）

`--refine` の引数は「番号リスト + 追加指示」として読む:

- **番号リスト**: `--refine` の直後の 1 トークン。1 つ以上の Issue 番号をカンマで連結した形で、空白も `#` も含まない（`12`・`12,15`）。列挙した Issue だけが書き換え対象で、それ以外は対象にしない（親を挙げても Sub は自動展開しない。加わるのは手順 2 でユーザーが承諾した Sub だけ）
- **追加指示**: 番号リストより後の、フラグでないすべてのトークンを順に並べたもの。数字だけのトークンも指示テキストとして読む（`--refine 12 15 を統合` は対象 12・指示「15 を統合」）。フラグに触れるときはダッシュを外して書く。追加指示はスキルが Issue から推測した内容より優先し、手順 5 の判断のギャップの回答にもなる。指示が Issue のスコープを変える場合、その変更は手順 8 の変更点と手順 9 の編集通知コメントに載せる
- **番号の異常系**: `--refine` の直後にトークンが無い、またはそのトークンが番号リストの形でない（`#12`・`owner/repo#12`・`12,`・`--check` 等）ならエラーで停止、存在しない番号もエラーで停止、closed の番号はユーザーに続行可否を確認、重複した番号は黙って重複排除する

以降の手順は新規作成を基本フローとし、`--refine` の差分は references/refine.md が手順番号ごとに持つ。差分が適用されるのは refine の対象 Issue のみで、フローの途中で新規作成する Issue には新規作成のルール（ロケール・ラベル選定）をそのまま適用する。これを**この実行で作成する Issue**と呼ぶ（分割時の親と Sub-Issues・親 Issue 化時の新規の親・手順 4 の「会話 → 新規 Issue」で起票する Issue）。対象が複数のときは同じ差分をセット全体に適用する（単一対象は N = 1 の場合）。

## 前提条件
- Git リポジトリ内で実行すること（対象リポジトリの判定に使用）
- `gh` CLI がインストール・認証済みであること

## 実行内容

### 1. 対象リポジトリ確定
- `gh repo view --json nameWithOwner -q .nameWithOwner` で取得し、以降の書き込み系で `-R` に渡す

### 2. 素材の蒸留

`--refine` 時は、この手順の前に [references/refine.md](references/refine.md) を読む。

- 会話コンテキスト（トピック引数があればそのトピックに絞る）から要件を抽出する
- **「会話の要約」ではなく「要件の蒸留」**: 経緯・試行錯誤は捨て、合意した結論のみを残す
- 合意事項を**番号付きリスト**として書き出す（手順 7 の突き合わせに使う）。以下を漏らさず含める:
  - やらないと決めたこと（スコープ外）
  - 採用しなかった案と、採用しなかった理由
  - `~/.claude/CLAUDE.md`「設計判断原則」の greenfield 判定（一致 / 妥協と失う性質 / ユーザー決定）
  - 意図的に保留した判断（TBD）と、誰が・いつ決めるか
- セルフチェック: 会話で暗黙に合意したが明文化していない判断の拾い漏れがないか確認する

### 2.5. 評価（`--refine` 時のみ）

対象リポジトリに `.github/ISSUE_TEMPLATE/` があるときは [references/templates.md](references/templates.md) を読み、見出しの検査より前に対応付けを行う。

[references/refine.md](references/refine.md) の手順 2.5 に従う。

### 3. 重複検索
- `gh issue list --search "<キーワード>" --state all` で類似 Issue を確認（実装済み・wontfix の closed も重複検出の対象）
- 類似があればユーザーに提示し、続行可否を確認する
- `--refine` の差分は references/refine.md の手順 3

### 4. 粒度判定

Issue と PR の対応は、Skill ツールで `github-sub-issues` を起動し、その「運用規約」（葉 Issue = 1 PR、親 = リリース単位、仕様の配置、PR 本文の規則）に従う。本手順はその規約の下で「分けるか・どこで分けるか」を判断する。

- **リリース単位の確定**: 機能として価値を出すために一緒にリリースすべき範囲を確定する。この範囲が 1 PR に収まるなら単一 Issue、収まらなければ**親 Issue（リリース単位）+ Sub-Issues（各 1 PR）**に分ける。1 Issue に複数 PR を示唆する散文（「PR 分割の目安」等）は書かない
- **分割トリガー（定性基準 + 承認）**: 実装が「単独でベースブランチにマージしても壊れない複数の段階」に自然に分かれ、1 PR にまとめるとレビュー困難と判断した場合に分割を提案し、ユーザー承認で確定する。数値閾値は置かない。ドラフト中に段階の一覧を書きたくなった時点が分割シグナル
  - 分割を提案する実行、または他の理由（新規の親による親 Issue 化・会話 → 新規 Issue）で Issue を作成する実行は [references/split.md](references/split.md) を読む
- **対象間の重複**: この実行が公開する文書どうし、およびそれらが読み合わされる本文との間の重複・矛盾は、**検出元を問わず**（手順 3 の重複検索・手順 2.5 の横断読者・手順 7 の横断読者のいずれも）ここで、どちらが持つかを決めて内容を移動・統合する（両方に残さない）。親と Sub の対なら「仕様の配置」が配置を決め、葉どうしなら一方が持つ
  - **裏取り**（適用する時点は消費者が決める）: 名指しされた記述が両方の文書に実在し、矛盾の主張ならその 2 つが実際に食い違うこと・重複の主張なら同じ内容が両方に置かれていることを**2 つの文書の突き合わせで確かめる**。裏取りできない主張は採用しない。読者が争点になったコードベースの主張を実地検証して示した結論は、この突き合わせの入力として使う
  - 読み取り専用の本文どうしを名指した指摘は、報告するだけで動かさない
- **仕様の配置**: 運用規約の「仕様の配置」に従い、横断ルールは親にだけ、段階固有のスコープ・受け入れ条件は Sub にだけ書く。Sub の自己完結基準は「親と合わせて読めば迷わず実装できる」
- 分割とは別に、**価値の取捨チェック**を行う: Issue 内に「削っても残りの機能が成立する、相対的に価値の薄い部分」が無いか確認する。見つかった場合はスコープ外へ移す・後続 Issue に切り出す選択肢を理由とともに提示し、ユーザーの判断を仰ぐ（勝手に削らない）。消費者はいるが価値の薄い機能はこのチェックでしか拾えない
- `--refine` の差分は references/refine.md の手順 4

### 5. ギャップ調査
- 「本文の節」の各節を埋める観点で、会話に無い・未確定の情報を列挙し（壁打ちが薄い場合も全節を確認）、事実か判断かで扱いを分ける:
  - **事実のギャップ** → コードベース・CI ログ・`gh` 等の追加調査で埋める（独立した調査は並列実行する）。特に:
    - **原因・現状認識**: 仮説のままにせず、コードや記録を読んで裏付ける
    - **参照コード**: 短い該当箇所は本文に引用する。参照はファイルパス + 関数名・型名等の grep 可能な識別子で示し、**行番号は書かない**
    - **再現・検証手順**: 実際に機能することを確認する
    - **波及の掃き出し**: 既存の規則・用語・契約・共有の振る舞いを**変える** Issue（加えるだけの Issue は対象外。迷ったら検索する）では、それに依存する箇所をリポジトリ全体から grep で洗い出す — 変更前後の用語、変わるものの名前、他の文書が引用している言い回し。変更後に誤って読める hit を既知の依存箇所として列挙する。**Issue が他の理由では触れないファイルの hit こそがこの検索の目的**
    - **パスを支配するルールの読込**: `ccx plan docs` を、この Issue が触るパス（`affected_code` に書くことになるファイル）を引数にして実行し、`documents[]` の各パスを Read で読む。読んだ内容は要件と受け入れ条件への制約として扱う（テストの書き方を定めるルールがあれば、この Issue のテスト要件はそれに従う）。`loaded[]` は読み直さず、`warnings[]` は報告して続行する。path-scoped rule は、シェル越しにコードを読む起案者には自動でロードされない
  - **判断のギャップ**（要件の取捨・スコープ・受け入れ水準等）→ ドラフト前にユーザーに確認する。事実のギャップを埋めた後に — 読者の blocker からでも、この手順の調査からでも — 設計（起案者がそこから選ぶことになるコード要素・構造）が複数残るなら、その選択も判断のギャップとして扱う。ただし**そのギャップを埋めても手順 2 の合意事項リストのどの項目も達成に近づかないなら外側**とし（項目そのものと、その実現のために決まる下位の判断は内側。上記の掃き出しが挙げる依存箇所は内側）、出どころを問わず decision として扱わずに下記の記録へ回す。外側は**手順 2.5 の判定にも読者の予算にも数えない**
    - **記録先はその発見が隣接する要件を持つ対象のドラフトの `out_of_scope` 節**に 1 行（何を見つけたか・なぜこの Issue の範囲外か）。分割時、リリース単位の外にある発見は親の `out_of_scope` に置く
    - **隣接する対象がドラフトを持たない発見と、隣接先が決まらない発見はどの本文にも書かず**、手順 10 で列挙する
    - **調査が合意事項の前提を覆した場合**、事実の訂正は本文に反映したうえで、訂正の結果として範囲が広がる分だけをこの記録へ回す
    - 記録した一覧の提示と引き込みは手順 8 が持つ
- 合理的な調査で埋まらない事実は、隠さず「未確認」と明示し、確認方法とともに本文に残す（判断は「未確認」のまま実装者に渡さない）
- 節スキーマに対応するキーが無い情報（再現手順等）は最も近い節に含める
- 調査結果が重複・粒度の前提を変えた場合は手順 3〜4 を再評価する
- `--refine` の差分は references/refine.md の手順 5

### 6. ロケール・ラベル判定
以下の2コマンドは並列実行する:
- `gh issue list --limit 5` で既存 Issue の言語慣例を確認し、**ロケールを `ja` / `en` のいずれかに決める**。以降のすべて（タイトル・見出し・本文・「なし」等の固定文字列・手順 9 の編集通知コメント）がこのロケールに従う
  - 慣例がどちらでもない場合は `ccx issue sections list --locale <その言語> --kind leaf` を実行し、**stderr のエラーをそのまま提示して停止する**
- `gh label list` で既存ラベルを取得し、内容に合うものを選定（合うものが無ければ付けない。新規ラベルは作らない）
- 新規作成の実行で、対象リポジトリに `.github/ISSUE_TEMPLATE/` があるときは [references/templates.md](references/templates.md) を読み、ここで対応付けを行う
- `--refine` の差分は references/refine.md の手順 6

### 7. 自己完結検証（ドラフト提示前に必須）

ドラフトは会話に直接書かず、**最初から scratchpad 直下のファイルとして Write する**（分割時は親・各 Sub-Issue で 1 ファイルずつ、`--refine` では 1 対象につき 1 ファイル。この実行で新規作成する Issue にも 1 ファイルずつ起こす）。以降の修正はすべてこのファイルへの Edit で行い、手順 9 では同じファイルをマニフェストが名指す。`ccx issue publish` はドラフト・編集通知コメント・`<ドラフトファイル名>.mapping` をマニフェストと同じディレクトリで裸のファイル名として解決する。

**マニフェスト（`--refine` 時、およびこの実行で作成する Issue があるとき）**: ドラフトファイルとは別に、セッションの scratchpad 直下へ固定名 `publish-manifest.json` で書き、フローの進行に合わせて更新する。単一対象でも、分割で親 + Sub を作るだけのときも同じ形で作る。書き方は `ccx issue publish --help` が持つ。書き込みが途中で止まった場合は同じファイルを渡し直せば続きから走る（どこまで書き込み済みかはコマンドが記録で持つので、状態を手で管理しない）。

**この実行で初めてマニフェストを Write するときは、隣の記録ファイル（`publish-manifest.json.published`）が残っていれば削除する**。消さないと、同じプレースホルダー名を持つ前の実行の続きとして読まれる。鮮度拒否からの再実行では消さない。

行に載せる判断:

- `updated_at`: 手順 2 で取得したスナップショットの値
- ラベル: 手順 2 のスナップショットのラベルに手順 6 で足すものを足した最終集合
- `blocked_by`: 手順 4 で決めた対象間の順序依存、親 Issue 化で親本文の `composition` 節が新たに示す依存（既存の親に元から張られている依存は載せない）、この実行で作成する Issue 自身の依存、および既存対象のその Issue への依存。ここが一覧の単一の宣言で、手順 8 の提示も手順 9 の登録もこの宣言を使う

**読者台帳（`reader-manifest.md`）**: 新規読者チェックで起動した読者を 1 行ずつ持つ表を、scratchpad 直下に固定名 `reader-manifest.md` で置く。この実行で最初に書くときは Write で上書きし、前の実行の残骸へ Edit で行を足さない。

```markdown
| 対象 | 渡したファイル | 予算消費 |
|---|---|---|
| #12 | 12-draft.md | 0 |
| #{PARENT} | parent-draft.md | 0 |
| #{SUB_A} | sub-a-draft.md, parent-draft.md | 2 |
| 横断 | 12-draft.md, parent-draft.md, sub-a-draft.md | 1 |
```

対象は検証させる Issue（既存なら番号、この実行で作成するならプレースホルダー名）で、下記の横断読者の行だけは `横断` と書く。渡したファイルはその読者の**現在の**集合の裸のファイル名（加わったファイルは書き足し、抜けたファイルは消す。揃えるタイミングは下記「集合が変わったら台帳を引く」が持つ）、予算消費とその数え方は `fresh-reader-verification` の予算規則が持つ。手順 2.5 の評価の読者は載せない。

作成者自身のチェック（1・2）に加えて、会話コンテキストを持たない読者による検証（3）を必ず行う:

1. **合意網羅チェック（会話 → 本文）**: 手順 2 の合意事項リストの全項目を、ドラフト本文と 1 項目ずつ突き合わせる。本文に無い項目は追記する（分割時はどの Sub-Issue が担うかも確認。配置先がこの実行で書き換えない本文 — セット外の Issue・`不要` のまま残る対象等 — になる項目は追記せず、突き合わせだけ行う）。リストのうち**判断**（採用しなかった案・やらないと決めたこと・greenfield 判定）は、本文に現れているだけでなく**回答と理由の対**になっていることまで確認する。理由を欠くと、決着済みの問いが読者から decision として再び上がる
2. **デッドスペックチェック（構成要素 → 消費者）**: 本文が指定する具体的な構成要素（構造体フィールド・環境変数・引数・設定値・ファイル等）それぞれについて、それを消費する要件・受け入れ条件を確認する。消費者が無い要素は削除するか、維持する理由と消費者（後続 Issue・外部システム等）を本文に明記する。「既存との一貫性」は消費者の代わりにならない
3. **新規読者チェック（本文 → 読者）**: Skill ツールで `fresh-reader-verification` を起動し、そのプロトコルに従って**ドラフトファイルのパスのみ**を渡して検証させる。読者を起動したら、渡したファイルとともに上記の読者台帳へ予算消費 0 で 1 行書く。同スキルの「依頼文」に差し込む役割と検証観点:
   > あなたはこの Issue にアサインされた実装者で、起案時の議論は一切読めない。この Issue 単体で実装に着手できるか評価せよ。
   >
   > 実地検証の対象は評価対象の本文に限る（あわせて渡された親の本文と、参照先の読み取り専用のスナップショットの主張は実地検証しない。それらは役割文の指示どおりに読む）。

   渡すドラフトに `#{NAME}` プレースホルダーが含まれる場合は、**どの変種の役割文にも**次の 1 文を添える: それらは同じ実行で作成する Issue を指し作成後に実番号へ置換されるので、プレースホルダーであること自体は指摘しなくてよい。ただしプレースホルダーが指す先の矛盾（`depends_on` 節が親の `composition` 節と異なる順序を示す等）は通常どおり報告する。

   分割時は Sub ごとに検証し、**Sub ドラフトのパスに加えて親ドラフトのパスも渡す**（役割文は「この Sub にアサインされた実装者。親 Issue と合わせて読んで着手できるか評価せよ」）。親ドラフト単体も検証する（横断ルール・`composition` 節の一覧・`release_manual_steps` 節が Sub を知らない読者に読めるか）。

   **横断読者（実行につき 1 人、経路を問わない）**: 上記の対象ごとの読者とは別に、**この実行でドラフトを持つすべての Issue のドラフトに、それらと読み合わされる、この実行で書き換えない本文を加えた集合**を 1 人の読者へまとめて渡す。**書き換えない本文も数に入れて集合が 2 つ以上のときだけ起こす**（1 つなら起こさず、その旨も報告しない）。役割と検証観点:
   > あなたは同じ実行でまとめて扱われる複数の Issue の本文を一緒に読む読者である。渡された文書のうち **2 つの間で重複している記述・矛盾している記述だけ**を、双方の Issue 番号（まだ採番されていないものはプレースホルダー名）を明記した blocker として報告せよ。どの文書が単体で実装に着手できるかは判定しなくてよい。
   >
   > 実地検証の対象は渡された全文書だが、検証するのは**文書どうしが食い違っている主張に限る**。そこではどちらが正しいかを確かめて blocker に併記せよ（一致している主張は各対象の読者が見る）。
   >
   > この実行では書き換えないと示された本文どうしの対は見なくてよい。

   `#{NAME}` プレースホルダーの 1 文は他の読者と同じく添える。横断読者は読者台帳に 1 行持ち、差し戻しも予算も同スキルの規則どおりに扱う。

指摘への対処は同スキルの規定に従い、本スキル固有の扱いを 5 点加える:
- **blocker（事実の不足）** → 手順 5 のギャップ調査で埋めて本文に追記する
- **横断読者の blocker（文書間の重複・矛盾）** → 手順 5 の「調査結果が重複・粒度の前提を変えた場合は手順 3〜4 を再評価する」機構で手順 4 の「対象間の重複」へ回す
- **decision** → 何が decision かの判定は手順 5 の「判断のギャップ」が持つ（読者の指摘ごとに手順 5 の調査へ戻るのではない）。残ったものはプロトコルの 1 ラウンドで確認し、回答は手順 8 の承認前に本文へ反映する。現状維持と決めた回答は `deferred` 節に「質問・回答・理由」の 1 行として残す
- **minor** → 原則本文に反映しないが、実装者が「見落とし」と誤解しそうな項目のみ、`deferred` 節に推奨・判断基準つきの 1 行で吸収する
- **集合が変わったら台帳を引く** → ドラフト・スナップショットを含む集合に同スキルの言う集合の変化が起きたら `reader-manifest.md` を読み、そのファイルを集合に持つ読者を引いて、同スキルの「判定は渡したファイルに束縛される」を適用する。**この手順の同期点は手順 8 の提示の直前**で、提示はそこで送った差し戻しがすべて返ってから行う。差し戻しを送ったら、台帳のその行を現在の集合に揃える。予算消費は周の結果が返ったときに、その結果（初読を含む）が blocker または decision を含むなら 1 進める

過剰詳細化ガード: 対象リポジトリの既存慣習・参照ドキュメントから一意に決まる内容は追記しない（「〜の既存パターンに従う」の一文と参照先で足りる）。

- `--refine` の差分は references/refine.md の手順 7

### 8. ドラフト提示 → ユーザー承認
- タイトル・本文・ラベル（分割時・親 Issue 化時は親子構成と親・各 Sub-Issue の本文すべて）を提示し、承認を得てから作成・更新する
- **`ccx issue publish <マニフェスト> --dry-run` を実行し、その出力もドラフトと並べて提示する**。非ゼロ exit なら停止し、stderr が挙げる違反をすべて直して再実行する。直す先は違反ごとに違う（ドラフト本文・マニフェストの行・`.mapping` ファイル）。握り潰し・スキップはしない
- リポジトリの issue テンプレートに従った場合は、選んだテンプレート・選定理由・キー → テンプレート見出しの対応付け（references/templates.md）も提示に含める（テンプレート無しで進めた場合はその判断と理由）
- 承認対象は**ファイルの最終版全文**とする（差分の積み重ねだけで承認させない）
- **スコープ外として記録した発見**（手順 5）の一覧を同じラウンドで提示し、引き込むかを選ばせる。引き込まれた項目は合意事項リストに加え、手順 5 の「調査結果が重複・粒度の前提を変えた場合は手順 3〜4 を再評価する」機構に載せてから要件へ移す
- 承認は省略しない
- ユーザー修正はファイルへの Edit で反映する（編集後の扱いは手順 7 の「集合が変わったら台帳を引く」）
- `--refine` の差分は references/refine.md の手順 8

### 9. 作成・更新

```bash
ccx issue publish <マニフェスト>
```

これが書き込みの全部で、経路（新規作成・`--refine`・親 Issue 化・分割）による違いは無い。作成・リンク・プレースホルダーの置換・本文とラベルの更新・編集通知コメントの投稿・`blocked_by` の登録を、その順で行う。承認済みのドラフトファイルはそのまま渡す（承認後に本文を書き直さない）。

- **非ゼロ exit なら停止する**。stderr が、何も書かれていないか、どこまで書かれたかがコマンドの記録に残っているかを言う。直したら**同じマニフェストをもう一度渡す**（済んだ分は飛ばして続きから走る）。握り潰し・部分的な手作業での代替はしない
- **鮮度で拒否された場合**（既存 Issue がドラフト作成後に動いていた）: その対象を手順 2 に戻す。現行本文とコメントを取り直し、入った変更をドラフトへ取り込み、手順 7 を再実行し、手順 8 でそのセットの再承認を得る。ここは「集合が変わったら台帳を引く」ではなく手順 7 の全体をやり直す。マニフェストのその行の `updated_at` を取り直した値に更新してから `publish` を再実行する
- マニフェストの組み立て（どの行を置くか・`blocked_by` に何を載せるか）は手順 7 の規定に従う。分割時・「会話 → 新規 Issue」時は作成する Issue の行を置き、Sub には `parent` を置く。単独の葉として提案したものは `parent` を持たない
- 「リンク後の親Issue本文同期」を別の編集として行わない — 親の `composition` 節は承認済みドラフトに既に載っており、同じ更新で書かれる
- Sub 間の順序は `blocked_by` の登録が正で、`depends_on` 節の文面はそのまま残す（運用規約）
- `--refine` の差分は references/refine.md の手順 9

### 10. 完了報告
- 作成・更新した Issue の URL（`publish` の出力が持つ）を提示し、次アクションとして `/issue-handle <番号>` を案内する
- `publish` が縮退を報告した場合（ラベル・アサインが適用されなかった）は、その内容も報告する
- この実行で Issue を作成した場合: 作成した全 Issue の URL を提示し、`/issue-handle` の対象は依存の無いものから順に着手することを案内する。親がいるなら親と各 Sub をまとめて示し、親は全 Sub 完了後に `/issue-handle <親番号>` で充足検証 → close できることを添える
- 手順 5 が記録先を持てなかったスコープ外の発見は、経路を問わずここで列挙する（どの本文にも書かない）
- `--refine` の差分は references/refine.md の手順 10

## 本文の節

本文の節は**意味キー**で識別する。キー ↔ 見出しの対応・kind ごとの必須条件・「なし」の固定文字列を持つのは `ccx issue sections` だけで、**この SKILL.md に表を複製しない**。

### 見出しの取得

```bash
ccx issue sections list --locale <ja|en> --kind <leaf|sub|parent>
```

`--locale` は手順 6 で決めたロケール、`--kind` は Issue の種別（単独 Issue = `leaf`、分割時の親 = `parent`、Sub = `sub`）。出力の読み方は `ccx issue sections list --help` にある。

**節の並びは kind ごとの参照ファイルの一覧が正**（`sections[]` の並びはレンダリング順ではない）。

### kind ごとの節と書き方

各節の見出しは `heading`（決定したロケールの canonical 見出し）を `## ` に続けてそのまま書く。`required` が false のキーは、内容が無ければ節ごと削除する。一覧に無い既知キーが既存本文にある場合（parent の `requirements` 等）は、内容があるかぎり残す。

kind に応じて [references/sections-leaf.md](references/sections-leaf.md) / [sections-sub.md](references/sections-sub.md) / [sections-parent.md](references/sections-parent.md) のうち起草する kind のものを読む。

## 品質基準

ドラフト提示前に以下を自己チェックする（共通原則: 未解決の判断や裏付けの無い主張をそのまま実装者に渡さない）:
- [ ] タイトル: 命令形の具体的な一文（後から見て文脈がわかる）
- [ ] 自己完結: 壁打ちの会話を読まなくても Issue 単体で実装可能 — 手順 7 の検証（合意網羅チェック・デッドスペックチェック・新規読者チェック）を完了し、blocker が無く decision がすべて回答・反映済みの状態に到達している
- [ ] 節の見出し: 決定したロケールの canonical 見出し（リポジトリの issue テンプレートに対応付けた節はテンプレート側の見出し）になっており、「本文の節」の検査が通る
- [ ] 粒度: 手順 4 の判定（葉 Issue = 1 PR、分割時は Sub の必須条件・仕様の配置・親の必須節）を通過している
- [ ] concise but complete: 冗長化させない
- [ ] 受け入れ条件の完全性: 全項目が満たされたら、かつその時のみ完了と言える
- [ ] スコープの述べ方: 変える規則に依存する箇所が、要件の列挙ではなく規則の側で範囲に入っている
- [ ] 事実と仮説の区別: 裏付けの無い記述を検証済みであるかのように書いていない
