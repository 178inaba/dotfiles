# 分割・Issue 作成時の規則

分割を提案する実行と、他の理由（新規の親による親 Issue 化・会話 → 新規 Issue）で Issue を作成する実行が読む。

## 手順 4: Sub の境界

- 独立してリリース可能で単体で価値が完結する縦切りがあればそれを優先する
- 無ければ工程分割（schema → API → バッチ等）でよい。価値の完結（atomicity）は Sub には要求しない（親 Issue が担保する）
- いずれも必須条件: **各 Sub は単独でベースブランチにマージしても壊れない**（運用規約の「Sub の必須条件」。最後の Sub まで配線しない設計と、親の `release_manual_steps` 節でリリースを揃える）
- 時間的に必然分離される作業（デプロイ完了後の互換コード除去等、PR が別になることが確定しているもの）も Sub 境界になる
- 各 Sub に依存（先行マージが必要な Sub）を添え、並列実装の可否を提示する

## 手順 7: 番号プレースホルダーとマニフェストの行

**番号プレースホルダー**: まだ採番されていない Issue 番号は `#{NAME}` と書く。`NAME` はそのドラフトでの役割を表す大文字とアンダースコアの名前（`#{PARENT}`・`#{SUB_A}`）。山括弧で名前を囲む形（`#` の直後に `<` を置く形）は使わない — GitHub の renderer が HTML タグとして落とし、置換までの間ずっと素の `#` だけが表示される。フェンス付きコードブロックとインラインのコードスパンの中は置換されないので、Ruby・Elixir の文字列補間をそのまま引用してよい。

`parent` と `blocked_by` にプレースホルダーで書く Issue は、マニフェストに自分の行が要る。既存 Issue を素の番号で書くときは行は要らない。
