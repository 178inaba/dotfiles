# `leaf`（単独 Issue）の節と書き方

1. `background` — なぜこの作業が必要か。担当者が判断に迷ったとき立ち返る基準。末尾に設計判断原則の greenfield 判定
2. `depends_on` — 先行マージが必要な Issue。GitHub の `blocked_by` リンクが順序の正で、この節は読者向け
3. `requirements` — must の列挙。曖昧語は具体化する — 「速くする」ではなく「0.5秒以内」。**手順 5 の波及の掃き出しが対象とする Issue では、要件は変えるものと、それに依存するすべての箇所**: 手順 5 の既知の依存箇所に加えて、掃き出しの一文「同種の箇所を全数直す — 実装者が grep し、読んで残した箇所を PR に列挙する」を書く
4. `acceptance` — `- [ ]` のチェックリスト。観測可能な振る舞いで書き、実装詳細は書かない。エッジケースを明記する。上記の掃き出しを書いた Issue では、対応する条件（実装者が読んで残した hit を PR に列挙している）も入れる
5. `affected_code` — ファイルパス・grep 可能な識別子（関数名・型名等。行番号は書かない）・関連 Issue/PR リンク。既知の依存箇所も、変更が及ぶファイルとしてここに挙げる
6. `impl_notes` — 断定せず「案」として。複数案あるなら推奨案とその理由を明示する。検討して採用しなかった案は不採用理由も書く
7. `deferred` — 意図的にオープンにする判断の列挙。各項目に推奨と判断基準を添える。**確定した現状維持の回答**（手順 7 の decision の扱い）もここに置く
8. `out_of_scope` — 壁打ちで「やらない」と決めたことの明記。**変えるものの依存箇所は単に除外しない** — この Issue の `requirements` に入れるか、名指しの Issue（手順 4 の価値の取捨チェック等でユーザーが合意した別 Issue。1 PR に収まらない変更は手順 4 で分割し、`sub` の `out_of_scope` で兄弟に渡す）に渡すかのどちらかで、この節の行はその Issue を名指す
