# `parent`（分割時の親 Issue）の節と書き方

親はリリース単位であり、実装対象ではなく Sub の束と横断ルールの置き場。各節の意味は運用規約。

1. `background` — リリース単位として何を届けるか。Sub 共通の判断基準。末尾に設計判断原則の greenfield 判定のうちリリース単位に効くもの
2. `composition` — 依存順の一覧。Sub 作成後に番号を埋める。`1. #{SUB_A} — <一言> — 依存: なし` / `2. #{SUB_B} — <一言> — 依存: #{SUB_A} のマージ後` の形で 1 行 1 Sub（節本文なのでこの散文も決定したロケールで書く。en なら `— depends on: none` / `— depends on: #{SUB_A} merged`）
3. `cross_cutting` — 全 Sub に効く要件。エラーコード等の確定値・トランザクション順序・共通の参照文書等。Sub には複製しない。**変えるものとそれに依存するすべての箇所という不変条件も横断ルール**なので、ここに書く
4. `acceptance` — `- [ ]` のチェックリスト。「上記 Sub-Issues がすべて close されている」に加え、リリース単位として観測可能な条件があれば書く（個々の Sub の条件は各 Sub に書く）
5. `release_manual_steps` — `none_markers` の「なし」マーカー、または手動マイグレーション・インフラ設定・スケジューラ有効化等のチェックリスト
6. `out_of_scope`
