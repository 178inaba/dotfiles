# `sub`（1 PR で完結する段階）の節と書き方

タイトルは接頭辞なし（運用規約「Sub のタイトル」）。

1. `background` — 1〜2 行。親 `#{PARENT}` のどの段階かと、この Sub 固有の目的。親の背景を再掲しない。末尾に設計判断原則の greenfield 判定のうちこの段階固有のもの（横断的な判定は親に置く — 運用規約「仕様の配置」）
2. `depends_on` — 先行マージが必要な Sub。無ければ `none_markers` の「なし」マーカー
3. `requirements` — この段階の must。横断ルールは親を参照し、複製しない。掃き出しのうち**この Sub が担う依存箇所**はここに書く
4. `acceptance` — `- [ ]` のチェックリスト。この段階だけで観測可能な振る舞い。単独マージで壊れないことも条件に含める — 未配線・未スケジュールの扱いを明記。依存箇所を担う Sub では、掃き出しの条件（実装者が読んで残した hit を PR に列挙している）も入れる（grep はリポジトリ全体に掛け、担当外の hit は `out_of_scope` で兄弟に渡す）
5. `affected_code` — ファイルパス・grep 可能な識別子（関数名・型名等。行番号は書かない）・関連 Issue/PR リンク。既知の依存箇所も、変更が及ぶファイルとしてここに挙げる
6. `impl_notes` — 断定せず「案」として。複数案あるなら推奨案とその理由を明示する。検討して採用しなかった案は不採用理由も書く
7. `deferred` — 意図的にオープンにする判断の列挙。各項目に推奨と判断基準を添える。**確定した現状維持の回答**（手順 7 の decision の扱い）もここに置く
8. `out_of_scope` — この Sub で扱わず他の Sub が担う範囲（**担う Sub を名指す**。残りの依存箇所も単に除外せずここで兄弟に渡す）
