## 入口条件と報告の形

手順 2.5 は対象が現状のままで品質基準を満たしているかを判定し、満たしている対象は書き換えずにフローから外す。

- **評価が走るのは判定が開いている対象だけ**で、判定が先に決まっている対象は見出しの検査しか受けない（手順 2.5「追加指示による上書き」）。評価する対象は対象ごとに評価し（対象間の矛盾・重複だけは横断読者が 1 人でまとめて見る）、対象数に依らず同じ手順を踏む
- **報告**: 対象ごとに、判定・blocker・decision・minor の一覧・満たさなかった品質基準の項目と、手順 5 の判定で外側とした発見の一覧を、ドラフト作成に進む前に必ず提示する。下記の 2 つの終了経路では、この報告が唯一の提示の場になる。評価が走らなかった対象の行の形は手順 2.5「追加指示による上書き」の「報告の形」
  - `必要` と判定した対象の blocker と decision は手順 5 のギャップ調査・確認ラウンドの入力として引き継ぐ
  - **例外は横断読者が挙げた対象間の矛盾・重複の blocker**で、手順 5 ではなく手順 4 の「対象間の重複」の入力として引き継ぐ
- **`不要` の対象はここでフローを抜ける**: ドラフト作成も本文の更新も編集通知コメントも行わず、手順 7 のマニフェストにも載せない。全対象が `不要` なら `--refine` は報告で終了する
- **`--check` 指定時**: 判定に関わらず全対象がここで終了する（報告のみで、書き込みは一切行わない）

## 手順 2

- 素材は既存 Issue の本文とコメント欄の議論。取得と素材の扱いは対象ごとに行い、提示と確認はセット全体で 1 回にまとめる（単一対象は N = 1）
  - **対象の確定（refine の他の作業より先に行う）**: `gh issue view <番号> --json title,body,labels,assignees,author,comments,updatedAt` で各対象を取得し、後続手順（ロケール・ラベル判定、変更点の提示、編集通知の要否判断、手順 7 のマニフェスト）でもこのスナップショットを再利用する（コンパクション等でコンテキストから欠落した場合のみ再取得する）。あわせて `ccx issue tree <番号>` を各対象に実行する（出力の読み方は `ccx issue tree --help`）。非ゼロ exit した場合は stderr を提示して停止する（「取得できなかったので飛ばす」は選ばない）。対象ごとの取得は並列実行する。取得できたら「対象: #12 <title> / #15 <title>、指示: <追加指示>」を**常に**提示する（指示が無ければその旨）。続けて、**Sub を挙げていない親が対象に含まれる場合**（`kind` が `parent` / `parent_and_sub` で、その Sub の一部が対象リストに無い）に限り、それらの Sub も対象に加えるかを、該当する対象が複数あっても AskUserQuestion **1 回**にまとめて確認する
  - 対象が Sub（`parent` あり）なら親の本文も素材に含め、親に書かれた横断ルールを対象 Sub に複製しない（手順 4「仕様の配置」）。対象が親（`kind` が `parent` / `parent_and_sub`）なら Sub 一覧を把握し、親本文の書き直しが Sub の分担と矛盾しないようにする
  - **セット外の関連 Issue は読み取り専用素材**: 対象になっていない親・対象になっていない兄弟は、その本文をドラフトの材料にするだけで、書き換えない
  - 会話コンテキストがあれば補完に使う（追加指示があればそちらを優先する）
- 合意事項リストでは、どの Issue も配置先にならない項目（列挙した対象でも、手順 2.5 で `不要` と判定した対象でも、セット外の読み取り専用の親・兄弟でもない）に印を付ける。手順 4 の「会話 → 新規 Issue」と手順 7 の合意網羅チェックが同じ 1 本のリストからこれを読む

## 手順 2.5

- **入力は現行本文**（ドラフトではない）。手順 2 の「対象の確定」で取得したスナップショットを使う。新規読者は現行本文を、`fresh-reader-verification` の「依頼文」が定める既定範囲で、手順 7 と同じ対象の絞り込みのもとで実地検証する。起案者はここではギャップ調査もドラフト作成も行わない
- **品質基準チェック**: 「品質基準」の各項目を現行本文に当てはめ、満たさない項目を挙げる。手順を参照している項目（「自己完結」→ 手順 7、「粒度」→ 手順 4）は**その手順の観点**を現行本文に当てはめて判定し、手順自体を実行していないことを不満足としない。「自己完結」の判定には下記の新規読者チェックの結果を使う
- **新規読者チェック**: 現行本文を scratchpad にスナップショットし（`gh issue view <番号> --json body -q .body`。手順 2 で本文を取得済みでもコマンドで書き出す）、手順 7 の新規読者チェックと**同じ役割文・観点**で検証させる。スナップショットは下記「実行順序」のとおり全対象で書き出し（見出しの検査と横断読者が使う）、読者を起こすのは評価が走る対象だけとする
  - **対象が Sub の場合**: 親の現行本文も同じ方法でスナップショットしてそのパスも渡し、役割文も手順 7 の分割時変種（親と合わせて読む版）に合わせる。**評価が走らない対象（下記「追加指示による上書き」）の親についても書き出す**
  - **横断読者**: 全対象の現行本文のスナップショット（評価が走る対象・追加指示で `必要` と決まった対象の両方）と、Sub である対象のセット外の親のスナップショットを**1 人の読者にまとめて渡し**、対象間の重複・矛盾だけを報告させる。この読者の定義 — 役割文・実地検証の範囲・findings の形・起こす閾値 — は手順 7 の横断読者が持つ（渡す集合だけが違う）。返った blocker は名指しされた対象の判定に数える（扱いは下記「対象間の矛盾・重複の扱い」）
  - **実行順序**: 全対象のスナップショットを先に取得し、その後の対象ごとの検証と横断読者は並列実行する（親を共有する対象が複数でも親のスナップショットは 1 つ）
  - **ここでの検証は 1 周のみ**とし、読者は読者台帳に載せない（横断読者も同じ）
- **見出しの検査**: 対象ごとに現行本文のスナップショットへ「本文の節」の検査を実行する（`ccx issue sections check <検査対象ファイル> --locale <ja|en> --kind <leaf|sub|parent> [--mapping <mapping ファイル>]`）。`--locale` は手順 6 の `--refine` 規定で決めた多数言語、`--kind` は `ccx issue tree` の `kind` を `standalone` → `leaf` / `sub` → `sub` / `parent`・`parent_and_sub` → `parent` に対応させる。リポジトリの issue テンプレートがあれば SKILL.md 手順 2.5 の対応付けを先に作って `--mapping` で渡す（ここで決めたテンプレート選定と対応付けは手順 6 でそのまま使う）。本文の見出し違反を品質基準「節の見出し」の不満足として扱い、対象を `必要` にする。前提不成立は mapping ファイルか呼び出しの誤りなので判定に数えず、直して再実行する（exit status の意味は `ccx issue sections check --help`）。対象ごとの検査は並列実行する。書き込む直前のゲートとしては呼ばない — `ccx issue publish` が同じ検査を全ドラフトに対して行う
- **判定**: blocker または decision が 1 件以上、または品質基準の項目が 1 つでも満たされないなら `必要`。minor しか無ければ `不要`
- **decision の扱い**: 何が decision かの判定は手順 7 と同じく手順 5 の「判断のギャップ」が持つ。残った decision は、手順 5 の「判断のギャップ」と**同じ 1 ラウンド**でユーザーに聞く（プロトコルのラウンドを 2 回に分けない）。回答は blocker と同じくドラフトの入力として手順 5 へ引き継ぐ。`--check` は decision を報告するだけで聞かない
- **対象間の矛盾・重複の扱い**: 横断読者が報告した対象間の矛盾・重複は**名指しされた両方の対象の blocker**として扱い、両方を `必要` にする。**裏取りの規則は手順 4 の「対象間の重複」が持ち、適用するのはここ** — 裏取りが通った主張だけを blocker として数える。名指しされた番号が列挙した対象でない場合（セット外の親・無関係な Issue）はその Issue を `必要` にしない（セット外の親をセットに加える経路は手順 4 の「会話 → 新規 Issue」の配置 2、読み取り専用の本文と食い違ったときの経路は手順 4 の「相手が読み取り専用の本文の場合」が持つ）。名指しの片方だけが列挙した対象の場合も、**列挙した側は `必要` になる**
- **追加指示による上書き**: 追加指示が対象への変更を求めているなら（「〜を追加して」「〜にしたい」等）、現行本文の判定に関わらずその対象は `必要` とする。読み方を方向づけるだけの指示（「〜を前提にして」等）は `必要` にしない。`不要` を覆す手段は指示を添えた再実行のみで、別途の上書き確認は設けない
  - **評価は走らせない**: 手順 3 で合流し、受けるものは下記「評価を経ない `必要`」に従う。スナップショットは上記「横断読者」どおりその読者へ渡す（読者を起こさないことはセットからの除外ではない）
  - **報告の形**: `必要` と、その根拠として「追加指示による」と見出しの検査の結果を示す。blocker・decision・minor の一覧は無い（横断読者がこの対象を名指しした blocker は上記「対象間の矛盾・重複の扱い」どおり報告する）
- **以降の手順（3 以降）が扱う「対象」は `必要` と判定した対象を指す**。宣言が語るのは**引数に列挙した対象**で、フローの途中でセットに加わる Issue は下記「評価を経ない `必要`」に従う。例外は次の 3 つ:
  - **例外 1（手順 3 の重複検索）**: 除外リストには `不要` を含む列挙した全対象を載せる
  - **例外 2（手順 4 の親 Issue 化）**: リリース単位判定と、それに基づく親 Issue 化の提案は、`不要` を含む列挙した全対象を母集団とする
    - 提案が承認されたら、**親 Issue 化で本文が変わる対象だけを `必要` に昇格**する: 親（`composition` 節に新しい Sub が載る）と、新たにリンクされる単独 Issue（`sub` の節構成で書き直す）
    - 既にその親の Sub で本文が変わらない対象は `不要` のまま据え置く（書き直しも本文の更新も編集通知コメントも行わない）
    - 昇格した対象は手順 5 で合流し、受けるものは下記「評価を経ない `必要`」に従う。据え置きの対象は手順 7 のスナップショット扱いを維持する
    - 全対象が `不要` なら本例外は発火しない
  - **例外 3（手順 4 の「対象間の重複」からの昇格）**: 横断読者がドラフトと `不要` 対象のスナップショットの食い違いを挙げ、裏取りで**公開済みの本文の側が誤っている**と分かった場合に限り、ユーザーがセットに加えると答えたその対象を `必要` へ昇格する（判断を聞く場所と辞退時の扱いは手順 4 の「相手が読み取り専用の本文の場合」が持つ）。昇格は手順 4 で起きるので手順 5 で合流し、受けるものは下記「評価を経ない `必要`」に従う
- **評価を経ない `必要`**: 評価ではなくトリガーによって `必要` になった Issue が受けるもの（引数に列挙した対象が昇格した場合も、フローの途中でセットに加わった場合も同じ）。各トリガーが持つのはいつ・誰の確認で昇格するか、辞退時の扱い、合流する手順で、受けるものはこの項に従う:
  - **手順 2 の取得**（マニフェストの `updated_at` とラベルの出どころになる `gh issue view` のスナップショットと `ccx issue tree`）: 列挙した対象でなかった Issue（手順 3 の重複検索でヒットした Issue・セット外の親）は受ける。列挙した対象は取り直さない
  - **手順 2.5 の本文のスナップショット**: 無ければ書き出し、既にあれば取り直さない。セット外の親は上記「対象が Sub の場合」の規定でスナップショットだけを先に持つことがあり、手順 2 の取得とは別物として扱う
  - **見出しの検査**: そのスナップショットでまだ走っていなければ受ける
  - **評価の新規読者チェックと品質基準チェック**: 受けない（`不要` から昇格した対象で 1 度済んでいるものも走らせ直さない）
  - **手順 2.5 の横断読者**: この読者が起動した後に合流した Issue では起こし直さない。起動より前に `必要` になった対象は初めからその集合にいる
  - **以降は対象として扱う**: 合流した時点以降の手順を通常どおり通る。ドラフトを持ち、手順 7 のマニフェストに行を持ち、手順 7 の読者を持って読者台帳に 1 行を持ち、そのドラフトは手順 7 の横断読者の集合に入る

## 手順 3

- 対象 Issue 自身（複数なら全対象）は検索結果から除外する。対象どうしの重複は「重複あり、続行するか」の停止にはせず、手順 4 で解消する所見として扱う（どちらが持つかを決めて内容を移動・統合する）
- 手順 4 の「会話 → 新規 Issue」の候補があれば、そのキーワードも新規作成時と同様に検索する。**ヒットは停止にしない**: 一致した Issue を提示し、扱いを選ばせる（セットに加える / その項目はその Issue に任せて新規作成しない）。「セットに加える」を選んだ Issue は判定に関わらず `必要` とする。加えた Issue は手順 4 で合流し、受けるものは手順 2.5 の「評価を経ない `必要`」に従う。キーワードが似ているだけの誤検知だった場合は候補のままで、手順 3 冒頭の続行可否の確認に戻る

## 手順 4

- **対象 → 親 + 新規 Sub**: 対象 Issue を親とし、その本文を親用に書き直した上で Sub-Issues を新規作成する
- **既存の対象 → 既存/新規の親の Sub**: 既に存在する対象たちを 1 つの親の Sub にする経路。「リリース単位の確定」でセット全体が 1 つのリリース単位だと結論した場合に限り、下記 2 変種のいずれかを**提案**し、分割トリガーと同じ場所・同じ流れでユーザー承認により確定する（自動では行わない）。母集団は `不要` を含む全対象で、承認後の昇格は手順 2.5 の例外 2 に従う。**順序依存があるだけでは親を作らない**（その場合は下記「対象間の順序依存」）
  - **新規の親**: 全対象が `kind: standalone` → 親 Issue を新規作成し、全対象をその Sub としてリンクすることを提案する
  - **既存の親**: 対象のうちちょうど 1 つが親（`kind` が `parent` / `parent_and_sub`）で、他に同じリリース単位に属する単独 Issue がある → それらをその親にリンクすることを提案する（既にその親の Sub である対象がセットに含まれていてもよい）
  - **既存の親の変種は、親になる対象の Sub 一覧が不完全な場合は発火させない**: `sub_issues_summary.total` と `sub_issues[]` の件数が食い違っていれば（`warnings[]` に count mismatch の行も載る）、手順 7 が求める `composition` 節の全 Sub 列挙を確定できない
  - **親が 2 つ以上ある場合**はどちらの変種にも当たらない → 提案せず通常の refine を続ける
  - **ユーザーが提案を辞退した場合**は対象を単独 Issue として refine する（新しい Issue は作成しない）。下記「対象間の順序依存」が通常どおり適用される
- **会話 → 新規 Issue**: 合意した作業のうち**どの Issue も配置先にならないもの**を新規 Issue として起票する経路。候補は手順 2 の合意事項リストで印を付けた項目と、追加指示が明示的に新規起票を求めた項目（「〜を新規起票して」等。印の有無に関わらず候補になる）。「粒度判定」を候補にも適用するので、1 つの提案が複数の Issue になることがある。分割トリガー・親 Issue 化と**同じ場所・同じ流れ**で AskUserQuestion により確認し、承認なしには何も作成しない。確認が決めるのは「その Issue を作ること」と「どこに置くか」で、ドラフトの承認は手順 8 の 1 回の承認ラウンドで対象のドラフトと一緒に得る
  - 配置は**この順に判定**する:
    1. **列挙した対象に親がいる**（`kind` が `parent` / `parent_and_sub`。手順 2.5 で `不要` と判定した親も見る）→ 各新規 Issue をその親の Sub として提案し、親の `composition` 節へ依存とともに親のロケールで載せる。`不要` の親は `必要` へ昇格する（追加の確認はしない）。昇格した親は手順 5 で合流し、受けるものは手順 2.5 の「評価を経ない `必要`」に従う。**親が 2 つ以上ある場合**は同じ AskUserQuestion でどの親に付けるかも聞く
    2. **対象がセット外の親を持つ Sub** → 同じ AskUserQuestion で、その親をセットに加えるかを聞く。加えるならその親を `必要` とする。昇格はここで起きるので手順 5 で合流し、受けるものは手順 2.5 の「評価を経ない `必要`」に従う。辞退されたらその親の Sub にはせず、単独の葉 Issue として提案する
    3. **全対象が単独** → 新規 Issue も単独の葉 Issue にする。対象との間のマージ順序は下記「対象間の順序依存」の規定どおりに表す
  - セット外の親を持つ Sub と単独の対象が**混在**する場合は、親を加えるかの質問を先に行い、その回答で 1 と 3 のどちらになるかが決まる
- **対象間の重複 — 相手が読み取り専用の本文の場合**（`不要` 対象のスナップショット・セット外の親のスナップショット）は**ドラフト側で解消する** — 公開済みの本文が正で、こちらの記述を動かすか合わせる。裏取りで公開済みの本文の側が誤っていると分かったときに限り、手順 5 の decision のラウンドでその Issue をセットに加えるかをユーザーに聞く。`不要` 対象なら手順 2.5 の例外 3 が昇格を持ち、セット外の親なら上記「会話 → 新規 Issue」の配置 2 が持つ質問「その親をセットに加えるか」をここから聞く。どちらも昇格後に受けるものは手順 2.5 の「評価を経ない `必要`」に従う。辞退されたらドラフト側でその食い違いを明記するか、その主張を落とす
- **対象間の順序依存**: 対象が 1 つの親の Sub ではなく、セットがリリース単位でもないが、マージ順序が決まっている場合は、その順序を GitHub の `blocked_by` リンク（手順 9 で登録）と本文の `depends_on` 節の**両方**で表す。順序の根拠は追加指示、無ければ各本文の記述。作成するリンクは手順 8 の承認で一覧提示し、ユーザーの確認を得る

## 手順 5

- ギャップ調査はセットで 1 回にまとめる（対象ごとに独立して回さない）

## 手順 6

- 言語確認（`gh issue list`）はスキップし、ロケールは**対象 Issue の現行本文の多数言語**で決める（対象ごとに決める。この実行で作成する Issue は素材となった対象のロケールに従い、置き先の親があるならその親のロケールを使う）。多数言語はフェンス付きコードブロックを除いてから字種を数える。手順 2.5 で既に算出している場合はその値を再利用する。どちらのロケールでもないときの停止は SKILL.md と同じ
- `gh label list` のみ実行し、既存ラベルは維持した上で内容に合う追加候補があればドラフト提示時に提案する

## 手順 7

- ドラフトは 1 対象につき 1 ファイル
- **親 Issue 化時（手順 4 で承認された場合）**: 親は `parent` の節構成で起こし、`composition` 節は**既存の対象を Sub にする分を実番号**で列挙する（同じ実行で作成する Issue もその親の Sub にする場合、その行はプレースホルダーになる）。既存の親の変種では、対象リストに無いその親の既存 Sub も `composition` 節に載せる（手順 2 で把握済み）
  - **新規の親**: 親ドラフトは新規 Issue なので新規作成のルールに従う。言語は手順 6 の規定（対象本文の言語）。タイトルはリリース単位の名前として起案者が決める（追加指示、無ければ対象の共通テーマから）。マニフェストの行はプレースホルダーをキーに置く
  - **既存の親**: 親は対象の 1 つなので、そのドラフトは refine 後の本文（`parent` の節構成・`--refine` のルール）で、`composition` 節に新しくリンクする Sub を加えた形になる
  - 新たにリンクする単独 Issue は `sub` の節構成で書き直す（`background` 節は親を参照し、`depends_on` 節を持ち、親の横断ルールを複製しない — 「仕様の配置」）。新規の親の変種では親番号を `#{PARENT}` と書き、親の作成後に置換する
  - 新規読者チェックは分割時の規定どおり（親ドラフト単体と、各 Sub ドラフト + 親ドラフト）
- **合意網羅チェック**: **どの Issue も配置先にならない項目**のうち手順 2 の印付けが取りこぼしたものは、手順 5 の「調査結果が重複・粒度の前提を変えた場合は手順 3〜4 を再評価する」機構で手順 3〜4 に戻し、候補の重複検索を経て手順 4 の「会話 → 新規 Issue」の提案にかける（手順 4 で既にユーザーが起票を辞退した項目は戻さない）
- **新規読者チェック**: 対象ごとに検証し、渡すのは**その対象のドラフト**と、対象が Sub ならその親、そしてドラフトが参照する先が**この実行で書き換えない本文**（セット外の読み取り専用の親・兄弟等、および `不要` のまま残る対象）であればその現行本文に限る。親も参照先も、ドラフトを持つならそのドラフト、持たないなら現行本文のスナップショットを渡す（`不要` のまま残る対象・例外 2 で据え置いた親・セット外の Issue はいずれもドラフトを持たない）。スナップショットは既に書き出されていればそれを使い、無ければ scratchpad へ書き出す。役割文は、対象が Sub なら分割時変種（親と合わせて読む版）、そうでなければ素の変種。**参照先の本文を渡す場合はどちらの変種にも 1 文を添える**（合わせて読む親には添えない）: それは参照先の現行の記述であり、参照の突き合わせにのみ使い、対象自身が単体で自己完結しているかの判定には使うな。ここでの「対象」は、引数に列挙して `必要` と判定した対象と、手順 2.5 の「評価を経ない `必要`」で `必要` になった Issue で、この実行で作成する Issue のドラフトは含まない
- **横断読者の集合**: 書き換えない本文は、`不要` のまま残る対象のスナップショットと、セット内の Sub が持つセット外の親のスナップショット。昇格した対象はドラフトを持つので書き換えない本文の側には入らず、ドラフトとして渡す。この読者を起こした後に昇格が起きた場合は、下記の昇格の規則が横断読者にもそのまま適用される
- **昇格**（手順 2.5 の例外 2・例外 3、手順 4 の配置 1・2 等、`不要` の対象やセット外の親が `必要` になる経路すべて）は何も編集しないが、集合は変わる: 昇格した Issue のスナップショットが、**それを集合に持つ読者すべて**でそのドラフトに置き換わる（参照でも、合わせて読む親でも、横断読者の一員でも同じ）。該当する読者には、他のファイルを 1 つも編集していなくても手順 8 の提示の直前の同期点で差し戻す。そのスナップショットを集合に持たない読者には何も送らない

## 手順 8

- **編集通知コメント**（既存 Issue の起案者・コメント参加者に自分以外がいる場合。自分のログイン名は `gh api user -q .login` で確認）: 提示する変更点を本文とするコメントを起案し、同じ承認ラウンドで承認を得る。承認できたら scratchpad 直下にファイルとして Write し、マニフェストのその行の `comment` に置く（投稿は手順 9 が行う）。対象が複数でもコメントは Issue ごとに起案し、同じ実行でブラッシュアップした他の Issue の番号も本文に添える。この実行で作成する Issue には起案しない
- 全文に加えて現行本文からの主な変更点を添えて提示する（追加指示によるスコープ変更も変更点に含める）。対象が複数なら:
  - 全対象のドラフト全文と各々の変更点を **1 回の承認ラウンド**で提示する（この実行で新規作成する Issue のドラフトも同じラウンドに含める）。マニフェストの `blocked_by` の一覧も添える
  - 対象ごとの修正指示を受け付ける（当該ファイルへの Edit。編集後の扱いは SKILL.md 手順 8 の共通ルールと同じ）
  - **セット内の全ドラフトが承認されるまで手順 9 の書き込みに進まない**
  - 関連の無い Issue を 1 セットにしても、単一対象の refine を順に実行するのと比べて得るものは無い

## 手順 9

- **親 Issue 化時**: 新規の親は行を 1 つ増やす（キーはプレースホルダー）。既存の親は対象の 1 つなので既に行がある。新たにその親の Sub にする対象は、その行の `parent` に親のキーを置く。既にその親の Sub である対象と、手順 4 の除外規則で外した対象には置かない。対象が Sub になった以上「対象間の順序依存」は `blocked_by` に載せない
- アサインは変更されない（`publish` は作成時にしかアサインしない）。「リンク後の親Issue本文同期」を別の編集として行わない — 親の `composition` 節は承認済みドラフトに既に載っており、同じ更新で書かれる

## 手順 10

- 対象が複数なら全対象の URL を提示する。この実行で本文を書き換えなかった対象（`不要` のまま残った対象）は URL を提示せず、判定を再掲する（親 Issue 化時の扱いは次項が優先する）
- 親 Issue 化時は `不要` のまま据え置いた対象も Sub の一覧に URL 付きで含め、本文は据え置きである旨を添える
- 手順 4 の「会話 → 新規 Issue」でユーザーが起票を辞退した合意事項は、ここで列挙する — どの対象の本文にも書かない
