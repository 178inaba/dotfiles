# fresh-reader-verification

起案者自身のチェックは「議論を知っているから読めてしまう」バイアスで穴を見逃す。会話コンテキストを持たない新規読者に文書を単体で読ませ、blocker が無くなるまで修正する手順を定める。

検証観点は消費者スキルが与える（何を読ませ、何を評価させるか）。本スキルは起動・分類基準・収束の型を持つ。

## 1. 起動

- Agent ツールで `subagent_type: "fresh-reader"` のサブエージェントを起動する（`model` は渡さない。消費者スキルが明示的に上書きを定めている場合を除く）
- **検証対象のファイルパスのみ**を渡す。会話コンテキストを渡さないことが新規読者性の担保そのもの
- `fork` は使わない（親コンテキストを継承するため目的に反する）

## 2. 依頼文

消費者スキルが与える役割と検証観点を冒頭に置き、以下を続ける。実地検証（Read/Grep での参照の裏取り）を求めるかは消費者が決める。

> 指摘を次の 2 分類で列挙せよ:
> - **blocker**: 事実誤認（存在しない関数・ファイル・実物と異なる参照や引用）／間違った実装を招く複数解釈／実装に着手できないレベルの情報欠落
> - **minor**: 参照先のコード・ドキュメントを読めば解決できる詳細／実装者の合理的裁量で決められる事項／「あると良い」レベルの改善提案
>
> 分類に迷う指摘は minor に倒せ。blocker が無ければ、minor の有無にかかわらず冒頭で「blocker なし」と明言せよ。

## 3. 指摘への対処

- **blocker（事実の不足・誤り）** → 調査して文書を修正する
- **blocker（判断の不足）** → ユーザーに確認する（勝手に決めない）
- **minor** → 原則反映しない（過剰詳細化を防ぐ。実装中の裁量に委ねる）

消費者スキルが blocker・minor の扱いを独自に定めている場合はそれに従う（例: blocker の埋め方を自スキルの調査手順に紐づける、minor の一部を特定の節に吸収する）。

## 4. 収束

収束条件は「blocker なし」（minor が残っていても収束とする）。

1 周目で blocker が出た場合のみ 2 周目を実行する。2 周目は新しいサブエージェントを起動せず、`SendMessage` で 1 周目のサブエージェントに差し戻す。新規読者性が必要なのは初読の 1 周目のみで、2 周目の職務は「指摘した blocker が修正で解消されたか」の検証だから、自分の指摘と読了済みの文書を保持した同一レビュアーが適任である（再読込がキャッシュ読取になりコストも下がる）。

差し戻しの依頼文には次を含め、職務を絞る:

> 文書へ次の修正を反映した: \<blocker への修正点の要約>。文書を再度 Read し、検証対象は (a) あなたが指摘した blocker がこの修正で解消され、全体と矛盾なく反映されているか、(b) 修正が新たに生んだ blocker、のみ。それ以外の箇所への新規指摘は blocker 基準を満たす場合に限り報告せよ。網羅的な再検証は行わない。分類基準と「迷ったら minor」は初回と同じ。blocker が無ければ冒頭で「blocker なし」と明言せよ。

初回依頼で実地検証を求めた場合は、上記に「Read/Grep による実地検証は修正が触れた参照に限る」を添える。

`SendMessage` で 1 周目のエージェントに到達できない場合（エージェント終了・セッション断絶等）のみ、フォールバックとして新しいサブエージェントを起動し、初回と同じ役割・分類基準に上記の職務限定を加えて 2 周目を実行する（初回の検証観点と実地検証の指示は渡さない）。

検証は**最大 2 周**。2 周目でも blocker が残る場合は 3 周目へ自律的に入らず、未収束である旨・残る blocker の内容・続行/打ち切りの選択肢をユーザーに提示して判断を仰ぐ（続行を選んだ場合の 3 周目以降も同一エージェントへの `SendMessage` 差し戻しで行う）。
