## 1. リソース指向とメッセージの抽象（中核）

### 1メッセージ = 1つの名詞

メッセージは1つの概念（名詞）を表し、**全フィールドがその概念の属性**である。この不変条件が守られていれば、後述のスメルの多くは自動的に避けられる。

破れているサインは、フィールドの説明に「〜する前の」「〜した場合の」「〜のときだけ入る」といった条件が要るとき。条件が要る = 1つのメッセージに概念が2つ以上ある。

リソース指向設計（[AIP-121](https://google.aip.dev/121)）は、この不変条件を API 全体に適用したもの — サーフェスを**名詞（リソース）の集合 + 少数の標準メソッド**として設計し、動詞は標準メソッドに寄せる。標準メソッドで表現できない操作にだけカスタムメソッドを使い、その理由を書く（[AIP-136](https://google.aip.dev/136)）。

### API はストレージスキーマの写しではない

**データベースのスキーマと同一の API はアンチパターン**（[AIP-121](https://google.aip.dev/121)）。API はクライアントが必要とする概念を表し、ストレージは永続化の都合を表す。両者は違う速度で変わるため、写すと片方の変更がもう片方を壊す。

**API 用のメッセージとストレージ用の型は別に定義する**（[protobuf.dev, Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/)）。同じ proto メッセージを両方に使い回すと、DB のカラム追加が API の破壊的変更に化け、API のフィールド廃止がマイグレーションを要求するようになる。共有したくなるのはボイラープレートを嫌ってのことだが、変換コードの重複は、契約が結合するコストより安い。

### スメル: 同一メッセージ内の接頭辞の対

`old_status` / `new_status`、`before_price` / `after_price` のような対が同じメッセージにあるのは、**「変化」を1つのメッセージとして具象化してしまった**サイン。これは要件（「変更を記録したい」「変更を返したい」）を、そのままの語彙でインターフェースに写した結果。

正しい形は、**同種のデータの異なる時点を1つの共有型で表し、時点はフィールドの配置（フィールド名）で表す**こと。型は「その対象」という名詞のままにする。こうすると:

- 型は1つの概念だけを表し続けるので、利用箇所が増えてもコメントと不変条件が壊れない
- 「一方だけが要る」利用箇所（現在値だけを返す API 等）で同じ型を再利用できる
- 時点が3つ以上に増えても、型を作り直さずにフィールドを足せば済む

### スメル: 一方の利用箇所で常に空になるフィールド

共有型に置いたフィールドが、その型のある利用箇所では**必ず空になる**なら、それはその型の属性ではない。典型は**イベントの属性**（変更が確定した時刻、変更を行った主体、変更の理由）で、「変更後の値」には付くが「変更前の値」には決して付かない。

こうしたフィールドは**共有型の外**に置く — 変更を表すメッセージ側、あるいはレスポンスのトップレベルに持たせる。型の中に残すと、読み手はどの利用箇所で空になるかを型の外の知識で補うことになり、7節のコメント規律も同時に破れる。

### スメル: ストレージのテーブルを写したレスポンス形状

レスポンスがテーブルの行そのものの形（正規化された ID の羅列、内部用のフラグ、更新時刻の類）をしているなら、永続化の都合が漏れている。クライアントが必要とする形から設計し直す。

### スメル: 他フィールドの有無で意味が変わるフィールド

「`type` が A のときだけ `detail` は X を意味する」形は、1つのメッセージに複数の状態が同居しているサイン。プロトコルが持つ排他的な表現（proto の `oneof` 等）を使うか、メッセージを分ける。

### 論争: レスポンスメッセージの形

RPC ごとに専用の request / response メッセージを定義するか、標準メソッドがリソース自体を返すか。決着していない論点で、判断軸は次のとおり:

| 選択肢 | 適する条件 | 代償 |
|---|---|---|
| RPC ごとの専用 request / response メッセージ（[Buf Style Guide](https://buf.build/docs/best-practices/style-guide/)） | メソッドごとに独立して進化させたい。1つのメソッドにだけフィールドを足す場面が想定される | メッセージの数が増える。同じリソースの表現が複数箇所に散る |
| 標準メソッドがリソースメッセージ自体を返す（[AIP-121 の標準メソッド](https://google.aip.dev/121)） | リソース指向で一貫させたい。リソースの表現を1箇所に集約したい | あるメソッドにだけ必要なフィールドを足すと、他の全メソッドのレスポンスにも現れる |

**同一サーフェス内で混在させない**ことが、どちらを選ぶかより重要。既存サーフェスがあるならその形に従う（SKILL.md のステップ5）。

## 2. 互換性と進化

一度クライアントに配ったフィールド番号・フィールド名・型は、こちらの都合で変えられない。破壊的変更の一覧は [AIP-180](https://google.aip.dev/180) と [protobuf.dev, Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/) が正。

### 決して破ってはならないもの

プロトコルに依らず成立する:

- **フィールドの型を変えない**。表現が互換でも、生成コードの型が変わってクライアントのビルドが壊れる
- **rename は削除 + 追加**であり破壊的変更。「識別子（番号）が同じなら安全」ではない — 名前はワイヤ上の JSON にも生成コードにも現れる
- **新しい required なフィールドを足さない**。古いクライアントは送れないので、必ず失敗する
- **意味の変更も破壊的**。既定値をシリアライズするかどうか、空とは何を意味するか、単位、タイムゾーンの扱い — 表現が変わらなくてもクライアントの挙動は変わる

proto の罠（フィールド番号という追加の識別子を持つため）:

- **フィールド番号を再利用しない**。削除したフィールドの番号を別の意味で使い回すと、古いクライアントが送ったバイト列が新しい意味で解釈される（型が偶然一致すると、エラーにもならず値が化ける）
- **削除したフィールドと enum 値は `reserved` にする**（番号と名前の両方）。将来の誰かが再利用するのを、コンパイラに止めさせるため

### 進化は加算的に

**将来を見越した先回りの一般化をしない**。「いつか複数値になるかもしれない」を理由に `repeated` で始めると、単数で足りる全クライアントに配列の取り回しを強い、「1件だけのはず」という不変条件をコードで守り続けることになる。**必要が実在してから新しいフィールドを足す** — 単数から複数への移行は、新フィールドの追加 + 旧フィールドの廃止という加算的な手順で扱える。

### List 操作は最初からページネーションする

コレクションを返す操作には、**最初のバージョンからページネーションを入れる**（[AIP-158](https://google.aip.dev/158)）。後から足すのは破壊的変更になる — 既存クライアントは「全件返る」前提で書かれており、途中で打ち切られると静かに欠落したデータで動く。

形は **cursor / page token 方式**にし、**トークンは不透明**にする。クライアントがトークンの中身に依存しなければ、サーバー側は実装（オフセット、キーセット、スナップショット ID）を後から変えられる。オフセット方式は、ページング中の挿入・削除で行の重複と欠落が起きる。

### 論争: バージョニング

| 選択肢 | 適する条件 | 代償 |
|---|---|---|
| package / URI にメジャーバージョンを埋める（[AIP-185](https://google.aip.dev/185)） | 公開プロダクト API。クライアントのロールアウトを支配できず、廃止を強制できない。破壊的変更を新バージョンとして併存させる必要がある | 複数バージョンの並行運用コスト。バージョン間の移行がクライアント側の作業になる |
| バージョニングを避け、互換性のある進化だけを行う（メディアタイプでのバージョニングを例外とする。[Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/)） | 内部サーフェス。全クライアントを把握でき、協調してロールアウトできる | 破壊的変更が必要になった場合の逃げ道が細い。互換性の規律を全変更で守り続ける必要がある |

判断軸は3つ — **公開プロダクト API か内部サーフェスか**、**クライアントのロールアウトを支配できるか**、**廃止を強制できるか**。3つとも「支配できる」側なら、バージョンを増やさずに加算的な進化で回せる。

## 3. フィールド設計と型

### presence（「未設定」と「既定値」の区別）を設計で決める

`0`・`false`・`""` が「設定された既定値」なのか「未設定」なのかを、契約として区別できるようにする。「今は区別が要らない」で省くと、必要になったときには presence を足す変更が意味の変更（2節）になっている。

- **proto3**: 基本型（数値・bool・string）は `optional` を付けないと**明示的な presence を持たない**。`optional` を付けることが公式の推奨で、ワイヤ互換性を保ったまま presence を得られる（[protobuf.dev, Field Presence](https://protobuf.dev/programming-guides/field_presence/)）
- **REST/JSON**: キーの不在（`undefined`）と `null` が別の状態になりうる。OpenAPI の `required` と null 許容の指定で、どちらが何を意味するかを明示する

### enum の 0 値は「未設定」に予約する

中立の意図は、**未設定・未知を表す値を予約し、それを既定にする**こと。ここに意味のある値（`ACTIVE` 等）を置くと「未設定」と「その値」が区別できず、後から区別を足せない。古いクライアントが未知の値を受け取ったときの受け皿も無くなる。

proto では 0 番の値がこれにあたり、`<ENUM 名>_UNSPECIFIED` と命名する（[AIP-126](https://google.aip.dev/126)、[Buf Style Guide](https://buf.build/docs/best-practices/style-guide/)）。例外は「未知」そのものが有用な値である場合で、`_UNSPECIFIED` と `UNKNOWN` を両方持つより `UNKNOWN` を 0 値にする方が明快になる。

### 状態が増えうるなら bool より enum

`is_enabled` のような bool は、3つ目の状態（「保留中」「不明」「一部有効」）が必要になった瞬間に破綻する。bool から enum への変更は型の変更（2節）なので破壊的で、移行は「新しい enum フィールドを追加して旧 bool を廃止」になる。**将来 3 状態以上がありうるなら最初から enum** にする。

これが「先回りの一般化をしない」（2節）と逆を向いて見えるのは、**前払いコストが非対称**だから。2値の enum を最初から置くコストはほぼゼロ（クライアントは値を1つ分岐するだけ）なのに対し、先回りの `repeated` は「1件だけのはず」という不変条件を全クライアントに恒久的に背負わせる。判断は移行手段の有無ではなく、この前払いコストで決める。

### well-known / common types を使う

時刻・期間・日付・金額を独自のメッセージや文字列で表さない。`Timestamp`・`Duration`・`Date`・`Money` といった well-known / common types を使う（[protobuf.dev, Dos and Don'ts](https://protobuf.dev/best-practices/dos-donts/)）。独自定義は、タイムゾーン・精度・単位の解釈をクライアントごとにばらけさせ、既存のライブラリ・ツールの支援も失う。

### フィールドの振る舞いを明示宣言する

そのフィールドが必須なのか、出力専用なのか、作成後に変更できないのかを**契約として宣言する**。宣言しないと、この知識はサーバー実装とドキュメントに散り、クライアントは試行錯誤で発見することになる。

proto では [AIP-203](https://google.aip.dev/203) の `REQUIRED` / `OPTIONAL` / `OUTPUT_ONLY` / `IMMUTABLE` 等、OpenAPI では `required` / `readOnly` / `writeOnly` が対応する。

### 1つの「不在」に複数の意味を持たせない

フィールドが空・未設定であることが、「未入力」「該当なし」「未確定」「権限が無くて返せない」を兼ねていると、クライアント側で区別できない。状態を表す別のフィールドを立てるか、メッセージを分ける。**不在の意味は1フィールドにつき1つ**。

### 命名

[AIP-140](https://google.aip.dev/140) が正。要点:

- **lower_snake_case** で書く（proto のフィールド名）
- **前置詞を使わない** — `reason_for_error` ではなく `error_reason`。前置詞は同じ意味を複数の綴りで書けてしまう
- **修飾語は名詞の前に置く** — `error_reason` であって `reason_error` ではない
- **単位を名前に含める** — `timeout_seconds`、`size_bytes`。単位をコメントだけに書くと、コード補完しか見ない読み手に届かない
- **`repeated` フィールドは複数形**にする

### 論争: JSON プロパティの casing

| 選択肢 | 根拠 |
|---|---|
| snake_case（[Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/)） | IDL のフィールド名とワイヤ上の名前が一致し、変換の層が消える |
| camelCase（[proto3 JSON mapping](https://protobuf.dev/programming-guides/proto3/#json)） | proto の JSON マッピングの既定。JavaScript のクライアントで自然に読める |

**どちらでもよい。混在だけが誤り。** 対象サーフェスの支配的な慣習に従う（SKILL.md のステップ5）。新規サーフェスならどちらかを選んで全体に適用し、選択を文書に残す。

## 4. リソース名と識別子

### リソース名は恒久的な識別子

リソース名（[AIP-122](https://google.aip.dev/122)）はクライアントが保存し、他システムに渡し、ログに残すもの。したがって:

- **メジャーバージョンをまたいでも変えてはならない**。API のバージョンが上がってもリソースの同一性は変わらないため、バージョンをリソース名に埋め込むと、保存済みの名前がバージョンアップで無効になる
- **有効な名前の集合を縮めてはならない**（[AIP-180](https://google.aip.dev/180)）。「これまで受け付けていた形の名前を今後は拒否する」は、既存クライアントが保存している名前を無効化する破壊的変更

### リソース間の参照は文字列のリソース名で

他のリソースを参照するフィールドは、**埋め込みメッセージではなく文字列のリソース名**にする（[AIP-122](https://google.aip.dev/122)）。メッセージを埋め込むと、参照先の定義変更が参照元のレスポンスにも波及し、参照先の一部だけが欲しいクライアントにも全体が配られる。参照の実体が必要なクライアントは、その名前で参照先を取得すればよい。

## 5. エラー設計

### gRPC: canonical status code を意図された区別で使う

status code は**クライアントが分岐に使う機械可読な情報**であり、その最大の用途は**リトライしてよいかの判定**（[gRPC Status Codes](https://grpc.io/docs/guides/status-codes/)、[AIP-193](https://google.aip.dev/193)）。区別を潰すと、クライアントは無駄なリトライか、リトライすれば通る要求の放棄をする。

踏みやすい取り違え:

| コード | 意味する状況 | 取り違えやすい相手 |
|---|---|---|
| `INVALID_ARGUMENT` | 引数そのものが、システムの状態に関わらず不正 | `FAILED_PRECONDITION`（引数は正しいが、今の状態では実行できない） |
| `NOT_FOUND` | 指定されたリソースが存在しない | `PERMISSION_DENIED` |
| `FAILED_PRECONDITION` | 状態が変われば成功しうるが、**リトライしても今は成功しない** | `UNAVAILABLE`（そのままリトライすれば成功しうる） |
| `UNAVAILABLE` | 一時的な障害。**そのままリトライしてよい** | `INTERNAL`（サーバー側のバグ。リトライしても直らない） |

存在を隠す設計判断として、権限が無いリソースにあえて `NOT_FOUND` を返すことはある。その場合は方針を文書化する（さもないと、後の実装者が「バグ」として `PERMISSION_DENIED` に直す）。

### 機械可読なエラー詳細を載せる

コードだけでは「どの引数が、なぜ」が伝わらない。かといって**クライアントにメッセージ文字列をパースさせてはならない** — 文字列は文言の改善で変わり、ローカライズされ、パースは静かに壊れる。

構造化されたエラー詳細（`ErrorInfo` の `reason` / `domain` 等。[AIP-193](https://google.aip.dev/193)）を付け、**クライアントが分岐に使う情報はすべて構造化された側に置く**。メッセージ文字列は人間の読み手（ログを見る開発者）向けと割り切る。

### REST: RFC 9457 の problem details

REST では、エラーの本文を独自形式で作らず [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) の problem details（`application/problem+json`）に従う。`type`・`title`・`status`・`detail`・`instance` という共通の枠があるため、クライアント側のライブラリ・ミドルウェアがそのまま扱える。追加の情報は拡張メンバーとして足す。

### 成功のステータスにエラーをトンネルしない

`200 OK` の本文に `{"success": false, ...}` を入れる形は、HTTP のセマンティクスを無効化する。中間のプロキシ・キャッシュ・監視・クライアントのライブラリはすべてステータスコードでエラーを判定しているため、成功として計上され、キャッシュされ、アラートに出ない。

gRPC でも同じで、`OK` を返してレスポンスメッセージ内の `error` フィールドや `success` フラグで失敗を表すと、生成クライアントのエラーハンドリング・リトライ機構・メトリクスがすべて素通りする。**失敗は、そのプロトコルが持つ失敗チャネルで返す**。

## 6. 冪等性と部分更新

### 作成のリトライは冪等性キーで安全にする

ネットワークは、リクエストが届いたのにレスポンスが返らない状態を作る。クライアントはリトライするしかなく、素朴な作成 API はそこで二重に作成する。

**クライアントが生成した冪等性キー**をリクエストに載せ、**サーバーは同じキーの再送に対して最初の結果を再生する**（[Stripe, Idempotent Requests](https://docs.stripe.com/api/idempotent_requests)）。キーはクライアント側で生成することが要点 — サーバーが払い出す形だと、キーを取得するリクエスト自体が同じ問題を抱える。

設計時に決めること: キーを載せる場所（フィールド / ヘッダー）、キーの保持期間、保持期間を過ぎた再送の扱い、同じキーで**異なる内容**が来たときの扱い（エラーにするのが安全）。

### 部分更新は field mask で

更新 API を「渡された全体で置き換える」形にすると、**古いクライアントが知らないフィールドを silent に消す** — クライアントは取得したリソースを送り返しているつもりだが、そのクライアントのバージョンには存在しないフィールドが欠けており、サーバーはそれを「削除の意図」として解釈する。データが消え、エラーも出ない。

**PATCH + field mask**（更新するフィールドを明示的に列挙する。[AIP-134](https://google.aip.dev/134)）を既定にする。マスクに現れないフィールドは触らないので、クライアントとサーバーのバージョンがずれても壊れない。

## 7. コメントの規律

### 全コンポーネントに public なコメントを付ける

サービス・メソッド・メッセージ・フィールド・enum とその値のすべてにコメントを書く（[AIP-192](https://google.aip.dev/192)）。IDL のコメントは生成されるクライアントコードとリファレンスドキュメントに現れる、**契約の一部**であって実装メモではない。

### 共有型のコメントは型の外の文脈に依存してはならない

複数の場所で使われる型（およびそのフィールド）のコメントは、**現在と将来の全利用箇所で成り立つ**ことだけを書く。破っているサインは:

- 片方の利用箇所でしか成り立たない制約を書いている（「〜のときは必ず入る」）
- 値の導出方法を、その型の外で定義される手順として書いている（「〜から計算される」）
- 特定の呼び出し元・特定のユースケースを名指ししている

これらを書くと、**新しい利用箇所が増えるたびにコメントの修正が要る**（そして修正は忘れられ、コメントは静かに嘘になる）。利用箇所ごとの制約は、**その利用箇所側のフィールドのコメント**に書く。

### 内部向けのメモは内部向けと明示する

実装の TODO・移行の経緯・チーム内の申し送りを、公開コメントと同じ場所に区別なく書かない。読み手はそれを契約と受け取る。残す必要があるなら「内部向け」と明示するか、コメントではなく Issue・設計文書に置く。
