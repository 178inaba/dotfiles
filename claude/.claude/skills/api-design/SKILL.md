# /api-design

ネットワーク API のインターフェースを、最初の起草で正しい抽象に当てるための判断プロセス。個別論点の使い分け基準は [catalogue.md](references/catalogue.md) に置く。

対象は IDL ファイル（`.proto`・OpenAPI ドキュメント）に限らない。spec・Issue の中に書く API 定義も同じ判断を通す（レビューを経ずに確定しやすく、実装時にはもう「決まったこと」として扱われるため）。

## 判断プロセス

### 1. 既存サーフェスを実装ではなく契約から調査する

**API サーフェスが何であるかの正は IDL**（proto ファイル、OpenAPI ドキュメント）であって、デフォルトブランチの実装状態ではない。調査を実装から始めると、契約上は存在する API を「無い」と誤認する。

調査に含めるもの:

- **公開されている契約** — IDL に定義されたメソッド・エンドポイントの全体
- **in-flight の作業** — open PR、feature ブランチ。デフォルトブランチにマージされていない実装は「まだ無い」だけで「存在しない」ではない

**stub は死んだ API ではない**。未実装・`Unimplemented` を返すだけのメソッドを見つけたら、扱いを決める前に**由来**（それを導入した PR・コミット）を確認する。これから実装される予約席なのか、放棄された残骸なのかは、由来を見ないと区別できない。

### 2. エンドポイントを足す前にホストを判断する

新しい RPC・エンドポイントを起草する前に、**同じ消費者・同じリソース・同じ粒度**をすでに提供する既存 API を探す。3つが揃っているなら、それがデータの正しいホストである。

- **既定は既存レスポンスの拡張**（フィールドの追加）
- **新規 RPC / エンドポイントには明示的な理由が要る** — 例えば、消費者が違う、リソースが違う、粒度が違う、認可の境界が違う、既存 API の互換性を壊さずには載せられない

理由を書けないなら、それは新規 API が不要だというサイン。エンドポイントが増えるコストは恒久的で、クライアントの実装・権限設計・監視のすべてに波及する。

### 3. メッセージの意味を先に宣言する

フィールドを1つも書く前に、**このメッセージが何を表すか**を1つの名詞で述べる。1メッセージ = 1つの概念であり、**全フィールドがその概念の属性**でなければならない。

宣言したら1フィールドずつ確認する。**フィールドの説明に「〜する前の」「〜した場合の」「〜のときだけ入る」といった条件が要る**なら、1つのメッセージに概念が2つ以上ある。

**「変更を記録したい／返したい」という要件を、そのままイベント型に具象化しない**。一方の側の値を `old_*` で包んだメッセージは、要件の語彙をそのままインターフェースに写した結果で、ほぼ常に誤り。同種のデータの異なる時点は、**1つの共有型を、異なる名前のフィールドに置いて**表す。

**この宣言は成果物に残す**（メッセージのコメント・spec の1行）。後からフィールドを足す人が同じ判断軸を再現できるようにするため。コメントに書く際は7節の規律に従う（型の外の文脈に依存させない）。

**スメルチェック** — 宣言した意味と矛盾する形が出ていないか、以下を機械的に見る（各項の展開は catalogue「リソース指向とメッセージの抽象」）:

- **1メッセージ内に、同種の値の2時点が時間順序の修飾語だけで同居している** — `old_*`/`new_*`、`before_*`/`after_*`、`from_*`/`to_*` の接頭辞の対が典型だが、接尾辞形（`*_before`/`*_after`）、`previous`/`current` のサブメッセージ対、`XxxChanged` という名前のメッセージも同じ形。特定の綴りではなく、この同居の有無を見る
- **型の利用箇所の一方で常に空になるフィールド** — その型が2つの役割を兼ねている。フィールドを型の外へ出す
- **ストレージのテーブルを写したレスポンス形状** — 永続化の都合がインターフェースに漏れている
- **他フィールドの有無で意味が変わるフィールド** — 1つのメッセージに複数の状態が同居している

### 4. カタログの使い分け基準を当てる

設計が触れる論点について [catalogue.md](references/catalogue.md) の該当節を読み、そこに書かれた判断軸で選ぶ。カタログが勝者を決めていない論点（冒頭に列挙してある）では、**この API の条件でどちらを選ぶか**を根拠付きで書く。

### 5. 対象サーフェスの既存イディオムを調査する

一般論より、そのサーフェスの支配的な慣習が優先する。新しいメソッドだけが浮くと、クライアント側の実装コストが恒久的に増えるため。既存の IDL を読んで確認する:

- **命名** — メソッド名の動詞、フィールド名の casing、リソース名の付け方
- **ページネーションの形** — page token / cursor / offset のどれか、フィールド名
- **エラーの形** — status code の使い分け、エラー詳細の載せ方
- **リソース指向の度合い** — 名詞 + 標準メソッドで揃っているか、動詞ベースの RPC が主流か

**リソース指向設計**（名詞としてのリソース + 標準メソッド、カスタムメソッドは理由を述べたときだけ）を推奨の既定フレームとする。ただし**対象サーフェスがリソース指向でないなら、そちらの確立されたスタイルに従う** — 一貫性のない混在は、どちらのスタイルよりも悪い。慣習から外れる場合はその理由を成果物に書く。

### 6. 提示前のセルフレビュー

要件から設計を **greenfield として導き直す**（`~/.claude/CLAUDE.md`「設計判断原則」のセルフチェック）。既存メッセージにフィールドを足す形の変更ほど、局所的には妥当なパッチの積み重ねで抽象が侵食される。

**設計を別のホスト API へ移すとき・形を変えるときも、同じく導き直す**。レビューで移動を指示されたときに最小 diff で型を移植すると、移動前の誤った抽象がそのまま生き残る。

加えて、**API 定義を含む spec・Issue を書くときは、設計を確定する前に別視点での反証レビューを挟む**ことを推奨する。ファイル外の起草では本スキルの自動ロードが確率的で、そもそもこのプロセスを通らずに書き上がる経路が残っているため。反証レビューでは「メッセージの意味の宣言」「フィールドと概念の一致」「共有型のコメントが型の外の文脈に依存していないか」を最初に問う。
