# /db-schema-design

テーブルスキーマの抽象化を最初の起草で当てるための判断プロセス。個別論点の使い分け基準は [catalogue.md](references/catalogue.md) に置く。

対象は DDL ファイルに限らない。spec・Issue の中に書くテーブル定義も同じ判断を通す（レビューを経ずに確定しやすく、実装時にはもう「決まったこと」として扱われるため）。

## 判断プロセス

### 1. 行の意味を先に宣言する

DDL を1行も書く前に、**このテーブルの1行が何を表すか**を1文で述べる。型は4つ:

| 型 | 1行が表すもの | 例 |
|---|---|---|
| エンティティ | 実世界の対象そのもの（現在の状態） | ユーザー、商品 |
| イベント | 起きた出来事（不変・追記のみ） | 注文、決済、ログイン |
| スナップショット（バージョン） | ある時点での対象の状態 | 価格履歴、設定のバージョン |
| 関連 | 2つ以上の対象の結び付き | ユーザーと組織の所属 |

宣言したら、**全カラムがその同じ主語を説明しているか**を1カラムずつ確認する。主語の異なるカラムが混ざっていたら、それは分けるべき別のテーブルか、そもそも行の意味の宣言が間違っている。

この宣言は成果物に残す（テーブルのコメント・spec の1行）。読み手が後からカラムを足すときの基準になるため。

### 2. スメルチェック

宣言した行の意味と矛盾する形が出ていないか、以下を機械的に見る:

- **同一行内の接頭辞の対**（`old_*`/`new_*`、`before_*`/`after_*`、`from_*`/`to_*`）— 1行が「変化」を表そうとしているサイン。ほぼ常にスナップショット2行に分けるのが正しい（catalogue「行の意味と抽象」）
- **状態によって意味が変わる NULL カラム** — 「未入力」「該当なし」「未確定」が同じ NULL で表現されている
- **入力の隣に置かれた導出値** — 他カラムから計算できる値（合計、距離、期間）が同じ行にある

### 3. カタログの使い分け基準を当てる

設計が触れる論点について [catalogue.md](references/catalogue.md) の該当節を読み、そこに書かれた判断軸で選ぶ。カタログが勝者を決めていない論点（冒頭に列挙してある）では、**このスキーマの条件でどちらを選ぶか**を根拠付きで書く。

### 4. 対象 DB の既存イディオムを調査する

一般論より、そのスキーマの支配的な慣習が優先する。新しいテーブルだけが浮くと、読む側のコストが恒久的に増えるため。既存スキーマ（マイグレーション・DDL・ORM のモデル定義）を grep して確認する:

- **履歴の持ち方** — `*_histories` / `*_versions` / `*_logs` / `*_audits` に相当するテーブルがあるか、どの形（スナップショット / イベント / 差分）を採っているか
- **命名** — テーブル名の単数/複数、主キー名（`id` か `<table>_id` か）、日時カラム名（`created_at` / `inserted_at` 等）
- **キー** — サロゲート PK の型（bigint / UUID）、外部公開 ID の有無
- **制約** — FK 制約を実際に張っているか、enum 相当をどう表現しているか

慣習と一般的な推奨がぶつかった場合は慣習に従い、外れる場合はその理由を成果物に書く。

### 5. 提示前のセルフレビュー

要件から設計を **greenfield として導き直す**（`~/.claude/CLAUDE.md`「設計判断原則」のセルフチェック）。既存テーブルにカラムを足す形の変更ほど、局所的には妥当なパッチの積み重ねで抽象が侵食されるため、既存の形を出発点にしない。

加えて、**スキーマを含む spec・Issue を書くときは、設計を確定する前に別視点での反証レビューを挟む**ことを推奨する。ファイル外の起草では本スキルの自動ロードが確率的で、そもそもこのプロセスを通らずに書き上がる経路が残っているため。反証レビューでは「行の意味の宣言」と「カラムの主語の一致」を最初に問う。

| FK・NOT NULL・CHECK・enum の表現 | 4. 整合性を DB で宣言する |
| 日時・金額・文字列・エンコーディング | 5. 型とエンコーディング |
| ソフトデリート、保持期間、PII の削除 | 6. 削除と保持 |
| JSON カラムに何を入れるか | 7. JSON カラム |
| テーブル・カラム・インデックスの命名 | 8. 命名 |
| 既存テーブルの変更手順 | 9. スキーマ進化（設計時スコープ） |
| 正規化・非正規化 | 10. 正規化の基準 |
