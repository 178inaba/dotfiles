## 1. 行の意味と抽象（中核）

### 1行 = 1つの主語

テーブルの1行はエンティティ・イベント・スナップショット（バージョン）・関連のいずれか1つを表し、**全カラムがその同じ主語を説明する**。この不変条件が守られていれば、後述のアンチパターンの多くは自動的に避けられる。

破れているサインは、カラムの説明に「〜する前の」「〜した後の」「〜の場合の」といった条件が要るとき。条件が要る = 1行の中に主語が2つ以上ある。

### スメル: 同一行内の接頭辞の対

`old_status` / `new_status`、`before_price` / `after_price` のような対が同じ行にあるのは、**「変化」を1行として具象化してしまった**サイン。これは要件（「変更を記録したい」）を、そのままの語彙でテーブルに写した結果で、ほぼ常に誤り。

正しい形は各時点の**スナップショット行**で、変化は隣接する2行の差として導出する。理由は非対称性にある:

- 2つの隣接スナップショットからは差分を計算できる
- 差分の列からは、初期状態を別途持たない限り任意時点の状態を復元できない（全差分の再生が必要で、1件でも欠けると壊れる）

つまり**スナップショットの方が情報量が多い**。差分行を選ぶのは、行サイズが極端に大きくカラム数個しか変わらない等、計測された理由があるときに限る。

### スメル: 意味が多重化した NULL

1つの NULL カラムが「未入力」「該当なし」「未確定」「削除済み」を兼ねていると、クエリ側で区別できない。状態を表す別カラムを立てるか、NULL を許さない設計（別テーブルへの外出し）にする。NULL の意味は1カラムにつき1つ。

### スメル: 入力の隣に置かれた導出値

他カラムから計算できる値（合計金額、2点間の距離、期間の日数）を同じ行に保存すると、入力と導出値が食い違う状態が必ず発生する。**計測された性能上の理由がない限り保存しない** — ビュー・生成カラム・クエリ側の計算で済ませる。

保存する判断をした場合は、整合性を維持する仕組み（生成カラム、トリガー、アプリ側の単一の書き込み経路）を設計に明記する。「アプリが常に両方を更新する」は仕組みではない。

### 履歴モデリングの選択

「変更を記録したい」という要件を、既定で差分行に具象化しない。用途で形が変わる:

| 用途 | 形 |
|---|---|
| アプリの監査ログ・変更履歴の表示・特定時点の状態の復元 | スナップショット履歴テーブル、または DB の temporal 機能（system-versioned tables） |
| 分析・DWH で「その時点のディメンション値」を保ちたい | SCD Type 2（`valid_from` / `valid_to` + 現行フラグ） |
| 「誰が何をしたか」の追跡（状態の復元は不要） | 追記専用のイベント/監査ログテーブル |

スナップショット履歴と SCD Type 2 は形が似ているが目的が違う。前者は運用系の復元・監査、後者は分析系の結合キーとしての履歴。どちらを名乗るかを決めてから列を設計する（[Temporal tables vs SCD](https://sivaro.in/articles/temporal-tables-vs-slowly-changing-dimensions-the-real/)）。

## 2. 構造のアンチパターン

以下はいずれも [SQL Antipatterns (Bill Karwin)](https://pragprog.com/titles/bksqla/sql-antipatterns/) が扱う古典。

### EAV（Entity-Attribute-Value）

`entity_id` / `attribute_name` / `value` の3列で任意の属性を持たせる形。型制約・NOT NULL・FK・意味のあるインデックスがすべて効かなくなり、1エンティティの取得に属性数分の JOIN が要る。

「属性が動的に増える」要件には、まず**カラムを足すマイグレーション**が回せないかを疑う。本当に予測不能な属性だけが要るなら JSON カラム（7節）を検討する — EAV より制約と型が効く。

### ポリモーフィック関連

`target_type` + `target_id` で複数テーブルのどれかを指す形。**FK 制約を張れない**ため、参照先の存在を DB が保証できず、孤児行が静かに溜まる。

代替:
- 参照元ごとに交差テーブルを分ける（`post_comments` / `photo_comments`）
- 共通の親テーブル（`commentable`）を作り、そこへ FK を張る（クラステーブル継承）

### 繰り返しカラム

`tag1` / `tag2` / `tag3`。上限を超えた瞬間にスキーマ変更が要り、「タグで検索」が `OR` の羅列になる。1対多のテーブルに分ける。

### カンマ区切り値

1カラムに `1,5,9` を詰める形。FK が張れず、部分一致検索がインデックスを使えず、値に区切り文字が現れた瞬間に壊れる。1対多のテーブルに分ける。

### 期間別テーブル

`sales_2024` / `sales_2025` と年ごとにテーブルを作る形。年をまたぐクエリが `UNION` の羅列になり、新年度のたびにアプリ側の変更が要る。1テーブル + **パーティショニング**（PostgreSQL の宣言的パーティション、MySQL のパーティション）で、物理分割を DB に任せる。

## 3. キー設計

### サロゲート PK を既定に、業務上の一意性は UNIQUE で

主キーはサロゲート（意味を持たない ID）を既定にする。業務的な識別子（メールアドレス、商品コード）は変わりうるため、PK にすると変更時に全参照の更新が要る。

ただし**サロゲート PK を置いたら、業務上の一意性には必ず UNIQUE 制約を別に張る**。ここを省くと、DB は重複を止めなくなる（サロゲート PK 導入で最も多い事故）。

### auto-increment vs UUID: 判断軸

どちらが正解ということはなく、以下の軸で決める（[Bytebase, UUID vs auto-increment](https://www.bytebase.com/blog/choose-primary-key-uuid-or-auto-increment/)）:

| 軸 | auto-increment（bigint） | UUID |
|---|---|---|
| 生成場所 | DB のみ（INSERT するまで ID が決まらない） | アプリ・クライアント側で事前生成できる |
| 分散・シャーディング | 単調増加なので複数ノードで衝突する（採番の仕組みが別途要る） | 調整なしで衝突しない |
| ID の外部露出 | 連番なので件数が漏れ、他人の ID を列挙できる | 推測・列挙が困難 |
| インデックスのサイズ | 8 バイト | 16 バイト（+ 全セカンダリインデックスに載る） |
| インデックスの局所性 | 末尾に追記されるので挿入が局所的 | ランダムだとページが分散し、書き込み増幅が起きる |

**UUID を選ぶなら時系列順序を持つ UUIDv7 を使う**。ランダムな v4 をクラスタ化主キー（InnoDB の PK、PostgreSQL でクラスタ化したインデックス）にすると、挿入のたびに B-Tree の全域が触られ、書き込み性能とキャッシュ効率が落ちる。

**ハイブリッドも有効**: 内部の PK・FK は bigint、外部に見せる ID だけ別カラムの UUID/ULID にする。インデックス効率と列挙耐性を両取りでき、内部 ID の露出だけを塞げる。代償はカラムが1本増えることと、外部 ID からの引き当てに追加のインデックスが要ること。

### PostgreSQL: `SERIAL` ではなく identity カラム

`SERIAL` は標準外で、シーケンスの所有関係が暗黙になり権限・所有者の付け替えで壊れやすい。標準の `GENERATED BY DEFAULT AS IDENTITY` を使う（[PostgreSQL wiki, Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This)）。

## 4. 整合性を DB で宣言する

アプリ側のバリデーションは、バッチ・管理コンソール・データ修正 SQL・別サービスからの書き込みを通らない。**DB に宣言した制約だけが全経路に効く**。

### FK 制約は既定で有効

外すのは、シャーディングで参照先が別ノードにある・極端な書き込みスループットで制約チェックのコストが測定上問題になる、といった**文書化された運用上の理由**があるときだけ。「後で消しにくいから」「テストデータの投入が面倒だから」は理由にならない。

エンジンの罠:
- **MySQL は FK に対応するインデックスを自動作成するが、PostgreSQL はしない**。PostgreSQL で子テーブルの FK カラムにインデックスを張り忘れると、親の DELETE/UPDATE のたびに子テーブルの全走査が起きる（[MySQL, FOREIGN KEY constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)）

### NOT NULL を既定に

NULL 許容は「値が無い状態が業務上ありうる」ことの表明であって、既定値ではない。そして 1節でも述べたとおり、**1つの NULL に複数の意味を持たせない**。

### 値のドメインは CHECK で

「0 以上」「開始日 <= 終了日」「2つのうち片方だけが NULL」といった条件は CHECK 制約で表現する。

エンジンの罠:
- **MySQL が CHECK 制約を実際に強制するのは 8.0.16 以降**。それ以前は構文が通っても無視される（パースして捨てる）ため、「書いたのに効いていない」状態になる

### enum 相当をどう表現するか

3つの選択肢があり、**集合の変化しやすさと、値に付随する情報の有無**で決める（[Crunchy Data, Enums vs Check Constraints](https://www.crunchydata.com/blog/enums-vs-check-constraints-in-postgres) / [CYBERTEC, lookup table or enum](https://www.cybertec-postgresql.com/en/lookup-table-or-enum-type/)）:

| 選択肢 | 適する条件 | 代償 |
|---|---|---|
| ネイティブ ENUM 型 | 集合がほぼ不変（曜日、性別区分など）。値の順序を型で持ちたい | 値の追加・削除・並べ替えが DDL になる。PostgreSQL は値の削除が特に面倒 |
| CHECK 制約 + 文字列 | 集合はたまに変わるが、値そのもの以外の情報を持たない | 変更のたびに制約の張り替え。値の一覧を SQL から引くのが制約定義の解析になる |
| ルックアップテーブル + FK | 値にメタデータ（表示ラベル、並び順、有効フラグ、多言語名）が要る。集合が運用中に変わる | JOIN が1つ増える |

**値にラベル・並び順・有効期間などのメタデータが要ると分かった時点でルックアップテーブル**に倒す。ENUM や CHECK でメタデータをアプリ側の定数表に持たせると、DB とコードの2箇所に集合の定義が分裂する。

## 5. 型とエンコーディング

### 日時

- **PostgreSQL**: `timestamp`（= `timestamp without time zone`）ではなく **`timestamptz`** を使う。前者はタイムゾーンの情報を持たないまま「どこかのローカル時刻」を保存するため、複数タイムゾーンやサマータイムが絡んだ瞬間に復元不能になる（[PostgreSQL wiki, Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This)）
- **MySQL**: `TIMESTAMP` と `DATETIME` は**明示的に選ぶ**。`TIMESTAMP` は UTC で保存し接続タイムゾーンで変換して返す（アプリのタイムゾーン設定に挙動が依存する）一方、範囲が 1970-01-01 〜 2038-01-19 に限られる。`DATETIME` は範囲が広く変換もしないが、「UTC で入れる」という規約をアプリ側で守る責任が残る（[MySQL, DATETIME/TIMESTAMP](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)）

有効期限・将来日付を扱うテーブルで MySQL の `TIMESTAMP` を選ぶと、2038 年問題を自分で作り込むことになる。

### 金額

浮動小数点（`FLOAT` / `DOUBLE` / `REAL`）を使わない。10進小数が2進で正確に表現できないため、加算を繰り返すと誤差が出る。**`NUMERIC` / `DECIMAL`（精度・スケールを明示）か、最小通貨単位の整数**を使う。

PostgreSQL の `money` 型も使わない — ロケール設定に依存し、通貨コードを持たず、精度が固定される（[PostgreSQL wiki, Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This)）。

複数通貨を扱うなら、金額と通貨コードは必ず対で持つ。

### 文字列

- **`char(n)` を使わない**。固定長のために空白でパディングされ、比較・結合時の空白の扱いがエンジンごとに違う。`varchar` / `text` を使う（[PostgreSQL wiki, Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This)）
- **長さ制限は業務上の理由があるときだけ**付ける。「なんとなく 255」は、後で伸ばすときにマイグレーションを強いるだけで何も守っていない。逆に「郵便番号は7桁」のような実在の制約は書く価値がある

### エンコーディング・照合順序

設計時に決めて明示する（既定に任せない）。

- **MySQL は `utf8mb4`**。`utf8` は `utf8mb3` の別名で、1文字3バイトまでしか扱えず絵文字と一部の漢字が入らない
- 照合順序（collation）は大文字小文字の区別・アクセントの扱い・ソート順を決める。UNIQUE 制約の判定にも効くため、「大文字違いを別の値として扱うか」を意識して選ぶ

## 6. 削除と保持

### ソフトデリートは既定ではない

`deleted_at` を全テーブルに付けるのは、コストを見ずに選ばれがちな既定。判断軸は3つ（[brandur.org, Soft Deletion Probably Isn't Worth It](https://brandur.org/soft-deletion)）:

1. **復元が実際のプロダクト要件か** — 「いつか要るかも」ではなく、ユーザーに提供する機能として復元があるか。無いなら、消したデータはバックアップから戻せば足りる
2. **全クエリが `IS NULL` フィルタに耐えるか** — 1箇所でも書き忘れると削除済みデータが表に出る。しかも「多めに出る」バグは気付きにくい。ORM のデフォルトスコープで隠すと、今度は JOIN 越しの漏れが起きる
3. **一意制約と衝突しないか** — 削除したメールアドレスで再登録できない。部分インデックス（`WHERE deleted_at IS NULL`）で回避できるが、対応はエンジン依存

代替を先に検討する:

| 代替 | 適する条件 |
|---|---|
| アーカイブテーブルへの移動 | 履歴として参照はするが、通常のクエリからは完全に外したい |
| 追記専用の監査ログ | 「何が削除されたか」の記録だけが要る（行そのものの復元は不要） |
| バックアップからの復旧 | 復元が運用上の例外対応であり、プロダクト機能ではない |

### PII の削除戦略は設計時に決める

「削除要求が来たらどうするか」を後から考えると、ソフトデリート済みデータ・監査ログ・バックアップ・分析基盤のコピーが全部残っていることに気付く。設計時に決めるのは:

- **ハード削除**か、**暗号消去**（対象ごとに鍵を分けて持ち、鍵の破棄で復号不能にする）か
- 監査ログ・履歴テーブルに PII を入れるか（入れないなら、参照 ID だけを残す）
- バックアップ・分析基盤への伝播をどう扱うか（保持期間で自然に消えるのを許容するか）

## 7. JSON カラム

### ハイブリッド規則

**属性の使われ方でカラムか JSON かを決める**（[PostgreSQL JSONB guidance](https://www.architecture-weekly.com/p/postgresql-jsonb-powerful-storage)）:

- **カラムにする**: クエリの条件・ソート・集計に使う、制約（NOT NULL・UNIQUE・CHECK・FK）を効かせたい、他テーブルと結合する
- **JSON でよい**: 構造が対象ごとに変わる、外部 API のレスポンスをそのまま保持する、読み出しは常に「行ごと丸ごと」

判断に迷ったらカラムにする。カラムから JSON へ緩めるのは移すだけで済むが、JSON からカラムへ締めるときは、制約が効かない間に溜まった不整合データの手当てが先に要るから。

### JSON の中に EAV を作り直さない

`{"attributes": [{"name": "color", "value": "red"}]}` のような形は、2節の EAV を JSON の中に再現しただけで、失うもの（型・制約・インデックスの効き）は同じ。JSON を使うなら**キーが直接の属性名**になる素直な形にする。

### 運用上の注意

- JSON 内の値で検索するなら、その式にインデックスを張る（PostgreSQL の GIN インデックス、MySQL の生成カラム + インデックス）。張らないと全行の JSON をパースする全走査になる
- JSON はスキーマを持たないので、キーの追加・改名がアプリ側だけで起きる。**どのキーが存在しうるかを別途文書化する**（さもないとスキーマの一部が誰にも見えなくなる）

## 8. 命名

### 小文字 snake_case

大文字を含む識別子は、引用符の要否がエンジン・クライアントで変わるため避ける（PostgreSQL は引用符なしの識別子を小文字に畳む）。

### テーブル名の単数 vs 複数

**どちらでもよい。混在だけが誤り。** 単数（`user`）にも複数（`users`）にも一貫した根拠があり、決着していない論点（[Bytebase, singular vs plural](https://www.bytebase.com/blog/sql-table-naming-dilemma-singular-vs-plural/)）:

- 単数派: テーブルは「型」を表す。ORM のクラス名と1対1で対応する。不規則複数（`person` / `people`）で悩まない
- 複数派: テーブルは行の集合であり、`SELECT * FROM users` が自然な英語になる

**対象スキーマの支配的な慣習に従う**（SKILL.md のステップ4）。新規スキーマならどちらかを選んで全体に適用し、選択を文書に残す。

### インデックス・制約にも命名規則を

`idx_<table>_<columns>` / `fk_<table>_<referenced>` / `uq_<table>_<columns>` のような一貫した形にする。自動生成名に任せると、エラーメッセージから「どの制約に引っかかったか」が読み取れず、マイグレーションでの名指しもできない。

## 9. スキーマ進化（設計時スコープ）

設計の段階で「この変更をどう出すか」まで決めておく。出し方を後回しにすると、無停止で出せない設計が確定してしまうため。

### expand–contract（parallel change）

スキーマ変更を3段階に分ける（[Expand and Contract](https://medium.com/@jasminfluri/expand-and-contract-method-for-database-changes-414d236f236f)）:

1. **expand**: 新しい形を追加する（新カラム・新テーブル）。旧コードは影響を受けない
2. **migrate**: 両方の形に書き、読み取りを新しい形へ移す。データを埋める
3. **contract**: 旧い形を削除する

**スキーマ変更とそれに依存するコード変更を1ステップに結合しない**。デプロイ中は旧コードと新コードが必ず並行稼働するため、片方だけでも壊れない中間状態が要る。ロールバックも同じ理由で必要になる。

### バージョン管理されたマイグレーション

DDL は手打ちせず、バージョン管理されたマイグレーションツール（Flyway・Liquibase・各フレームワーク内蔵のもの）で適用する。適用済みバージョンを DB 側に記録する仕組みがあるものを選ぶ。

### MySQL はトランザクショナル DDL を持たない

PostgreSQL は DDL をトランザクション内で実行でき、途中で失敗すれば全体が巻き戻る。MySQL は DDL が暗黙にコミットするため、**1マイグレーション = 1変更**にしないと、途中で失敗したときに「半分だけ適用された」状態が残り、手作業の復旧が要る。

## 10. 正規化の基準

**既定は第3正規形（3NF）**。各非キー属性が主キーだけに依存し、他の非キー属性に依存しない状態を目指す。3NF を守っていれば、更新時異常（同じ事実が複数行にあり片方だけ更新される）は構造的に起きない。

非正規化するのは、以下がすべて揃うときだけ:

1. **計測された根拠**がある（実際のデータ量・クエリで遅いことを確認した。「遅くなりそう」は根拠ではない）
2. インデックス・クエリの見直し・マテリアライズドビューといった**先に試すべき手段を試した**
3. **整合性を維持する仕組みを文書化した**（生成カラム、トリガー、単一の書き込み経路、定期的な整合性チェックのいずれか）

1節の「入力の隣に置かれた導出値」と同じ判断で、非正規化は導出データの保存の一形態にすぎない。
