# コメントモードON時の投稿とスレッド返信

## 8. コメントモードON時: PRにレビュー投稿

レビュー本文（body・各行コメント）を素の Markdown ファイルとして `work_dir`（`ccx pr prepare-review` の出力。補助ファイルもこの配下に置く）直下に Write し、`review_path`（同出力。自分で命名しない）にはそれらを `body_file` で参照する JSON を Write して、投稿コマンドを実行する:

```bash
ccx pr post-review <context_path> <review_path>
```

### review_path に何を書くか

書式は `ccx pr post-review --help` にある。本スキルが決めるのは中身:

- `assessment` には「レビュー結果出力」の総合評価をそのまま書く
- **本文は原則 `body_file` で渡す**（JSON 文字列に手でエスケープしない）。インラインの `body` は短い一段落までに限る
- 本文の内容（`body_file` の参照先・インラインとも）: 「レビューコメントの原則と口調」の原則・口調・言語（対象 PR の言語）で書く
- `comments[]` に入れるのは行に紐づく指摘のみ。無ければ空配列で body だけのレビューになる
- **折りたたみの原則**: 作者のアクションが不要な内容（コメント内の長い根拠・検証記録・前回指摘の対応状況・nit）は `<details>` で折りたたむ。`<details>` は PR への投稿（body・行コメント）専用で、「レビュー結果出力」のローカル出力には入れない
- **行コメント本文（`comments[].body_file` の参照先・インラインとも）は冒頭に重要度ラベルを付ける**。ラベルは `**必須修正**:` / `**推奨修正**:` / `**質問**:`（対象 PR の言語の相当表現）
- **行コメントの折りたたみ外に置くのは要求と根拠の要点まで**。機序の段階的解説・前例の列挙・代替案の得失比較・実測値・コードスニペットは、分量によらず `<details><summary>検証詳細</summary>` に折りたたむ（長さではなく内容種別で振り分ける）。修正案の提示そのものは折りたたまない
- **行コメントにした指摘も `body` の指摘事項リストに1行で索引する**（「<指摘概要>（`path:line` に行コメント）」の形）
- **`body` の「前回指摘の対応状況」「確認して問題なしと判断した点」「確認した内容」は `<details>` で折りたたむ**。summary に件数を書き、「前回指摘の対応状況」は判定の内訳まで書く（例: `前回指摘の対応状況: 4件（解消3・議論中1）`）。未解消・部分対応・議論中は、ステップ 9 の指摘事項への再掲とスレッド返信で作者に届ける
- **nit は `comments[]` に入れず、`body` 末尾に `<details>` で折りたたんで集約する**。折りたたみ内には `path:line` を明記する:

  ```markdown
  <details>
  <summary>nit: N件（non-blocking・対応は任意）</summary>

  - `path:line` — ...

  </details>
  ```

### 投稿が拒否されたとき

`ccx pr post-review --help` の指示に従って直し、再実行する。**指摘自体の削除・格下げはしない**。`#N` そのものを見せたいときはコードスパンに入れる。
成功したら PR のレビュー URL をユーザーに表示する。

## 9. コメントモードON時: 前回指摘スレッドへの返信・解決

ステップ 8 の投稿後に実行する。自分が過去に出した指摘スレッドのうち、作者が応答してボールが自分に戻っているものに確認結果を返信し、解消済みのものを解決済みにする。

対象は `ball` が `"mine"` のスレッドのみ（値の意味は `ccx pr context --help`）。0件ならスキップ — ただし**`threads_truncated` の警告が出ている場合は「0件」を対象なしと解釈せず**、警告の指示に従い再取得してから判定する:

```bash
jq '[.review_threads[] | select(.ball == "mine") | {path, line, original_line, resolvable_by_me, last_comment}]' <context_path>
```

### 判定の4分岐

「レビュー実行」の投稿前セルフチェックで記録した「対応状況の根拠」の種別を、そのまま resolve 可否に写像する:

| 判定 | 根拠 | 返信 | resolve |
|---|---|---|---|
| コード修正で解消 | 該当コミットの差分で解消を確認できた | 確認した旨（参照した差分箇所を添える） | する |
| 説明で解消 | 作者の説明を読み、指摘が成立しない／対応不要と**自分が納得できた**（コード変更を伴わない決着） | 納得した旨と、その根拠 | する |
| 未解消・部分対応 | 差分を読んだが指摘が残っている | 残っている点を具体的に示す | しない |
| 反論・議論 | 作者が意図的な設計判断・スコープ外と説明したが**納得できていない**、作者が質問・確認を返してきた、または対応が本 PR の差分外で確認できない | 根拠を添えて議論を続ける | しない |

- **「解消」と「反論・議論」を分けるのは合意の有無**。作者の説明で決着したなら「説明で解消」で閉じる。納得できていないなら閉じない
- **コード修正で対応したと主張された場合は、差分が唯一の根拠**。「対応しました」という返信の存在は根拠にならない。「説明で解消」の根拠は説明そのもの
- **「修正報告あり・差分未確認」は終端の判定ではない**。差分を読んで解消／未解消のいずれかに落とすまで判定を確定させない
- 未解消・部分対応と判定した内容は、「レビュー結果出力」の指摘事項にも再掲する
- 反論・議論は resolve せず、修正を求めるか押し返すかの最終判断をユーザーへの報告に残す
- **判定と伝える内容が前回の自分の返信から変わっていないなら、返信を重ねない**（`body` を省略する）
- ユーザーが明示的に指示した場合は、自分が起こした `ball: "theirs"` のスレッド（自分の返信が末尾で作者の応答待ち）も対象にできる

判定結果を `threads_path`（`ccx pr prepare-review` の出力）に Write し、以下を実行する:

```bash
ccx pr reply-threads <context_path> <threads_path>
```

### threads_path に何を書くか

書式は `ccx pr reply-threads --help` にある。本スキルが決めるのは中身:

- スレッドは `path` と `line`（`review_threads[]` から取る）で指す
- `resolve` は上記の決定表に従う
- `body` は「レビューコメントの原則と口調」の原則・口調・言語（対象 PR の言語）で書く。省略して resolve だけを実行するのは、前回の自分の返信から判定が変わっていない場合と、resolve 権限不足からの回復の 2 つ
- コードスパン・`"` を多く含む長い返信は素の Markdown を `work_dir` 直下に Write して `body_file` で指す:

  ```json
  {"threads": [
    {"path": "internal/cache/cache.go", "line": 192, "body_file": "t1.md", "resolve": true},
    {"path": "internal/cache/cache_test.go", "line": 40, "body": "確認しました。", "resolve": true}
  ]}
  ```

### 作者の push で拒否されたとき

`ccx pr reply-threads` が鮮度の再確認で「同期せよ」と拒否したとき、**`worktree-resolution` の「共通サブ手順: PR head との鮮度確認」では復旧しない**（`ok` を返し、拒否が繰り返される）。`ccx pr prepare-review` を同じ引数で再実行してドキュメントごと取り直し、判定と返信文を新しい head で組み立て直す（同期だけして返信文を再利用しない）

### 実行後の扱い

- 返信・解決したスレッド数をユーザーに報告する
- `resolve_failed[]` が空でない場合: **返信済みなので同じ本文で再実行しない**（再試行の形は `--help`）。warning はユーザーへの報告に併記する
- 途中で失敗して停止した場合: `--help` の指示どおり未処理分だけで再実行する
