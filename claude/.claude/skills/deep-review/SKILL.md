# /deep-review

コード差分を経験豊富なシニアエンジニアとして、本番運用を考慮しながら詳細にレビューし、Approve可能か判断

## 引数

- `<pr-number>`: 対象 PR 番号（省略時はカレント branch の PR を推論）
- `--issue ISSUE_NUMBER`: 指定したIssue要件を満たしているか確認
- `--worktree`: 対象 PR の worktree に切替（既存があれば再利用、無ければ作成）
- `--local-only`: 強制的にローカル出力のみ（PRコメント投稿しない）
- `--no-autofix`: 強制的に自動対応モードOFF（修正・コミット・プッシュしない）。コメント投稿には影響しない

ベースブランチは自動判定: PRがあればPRのベースブランチ、なければリポジトリのデフォルトブランチ（フォールバックは `origin/main`）。

## 実行内容

### 1. 準備

`--worktree` 指定時は、先に Skill ツールで `worktree-resolution` を起動し、その「PR worktree 解決手順」に従って対象 PR の worktree に session を切り替える。

次に準備スクリプトを実行する。スキル引数（`<pr-number>` とフラグ）をそのまま渡す:

```bash
ccx pr prepare-review <scratchpadディレクトリ> [<pr-number>] [--issue N] [--worktree] [--local-only] [--no-autofix]
```

出力の読み方は `ccx pr prepare-review --help` にある。本スキルがそれに対して行うこと:

- `status` が `ok` 以外 → **停止**。`branch_mismatch` はユーザーに「`--worktree` を付けて再実行」または「`git switch <head_ref>` してから再実行」を提示する。鮮度確認由来の status は、Skill ツールで `worktree-resolution` を起動し、その「共通サブ手順: PR head との鮮度確認」の status 別対応に従う（`--local-only` でも適用する）
- `pr_exists: false` は縮退なので続行する。PR があるのに取得系が失敗した場合はコマンドが非ゼロ exit で止まるので、stderr を提示して停止する（両者を混同するとモード判定が自動対応ONへ倒れる）
- `context_path` の読み方は「PR コンテキストの読了」
- `local_change` は「差分取得と確認」、`issues` は「Issue情報取得」で使う
- `warnings[]` が空でなければユーザーへの報告に併記する（打ち切りが解消しなかった場合は、記載の指示に従い再取得してから「PR コンテキストの読了」へ進む。ただし Issue コメントの打ち切りは「Issue情報取得」の規則に従い再取得しない）

### 2. PR コンテキストの読了（`context_path`。PR なし縮退（`pr_exists: false`）時はスキップ）

コンテキストの読み方は `ccx pr context --help` にある。

- `context_path` のファイルは jq で必要部分を段階的に参照する。`cat` での全文表示や `| head` での部分読みはしない
- 通常コメント（`comments[]`）・レビュー本文・レビュースレッドの 3 つすべてを読む

#### comments[] の読了手順（省略不可）

サイズや Bot ノイズを理由に comments[] を後回し・読み飛ばししない。以下の順で処理する:

1. **俯瞰**: `jq '[.comments[] | {author, author_type, created_at, body: .body[0:120]}]'` で全件を一覧する
2. **精読**: `author_type != "Bot"` のコメントは全文読む（`null`（削除済みユーザー）や `"Mannequin"` 等の未知タイプも読む）。Bot は俯瞰での種別確認だけでよいが、AI レビュー投稿と、人間のコメントが参照している Bot コメントは読む
3. **自分の既存レビューがある場合**: `reviewers[]` に `author` が current_user の要素があれば、その `submitted_at` 以降の comments[] とスレッド返信を必ず時系列で読む。この `submitted_at` が自分の最新レビューより前でも `reviews[]` から取り直さない。`reviews_truncated: true` の場合は、`reviewers[]` に無いことをもって過去レビュー無しと判断しない

### 3. Issue情報取得

Skill ツールで `pr-reading` を起動し、その手順に従って読む。起動時に名指すのは、container が「準備」で得た `issues`（読めなかったものを説明する `warnings[]` も同じ出力のもの）、文書が `context_path`、差分・コミットの取得元が `local_change` の有無で決まるもの（分岐は「差分取得と確認」）、報告先が「レビュー結果出力」の「確認した内容」。

本スキル固有の扱い:

- **取得元は「準備」で得た `issues` だけで、Issue を自分で取りに行かない**
- 読めなかった Issue は「レビュー結果出力」の充足表に「読めず」の行を残し、総合評価直下の行にも書く
- Issue コメントの打ち切りは再取得しない

あわせて各 Issue の親子関係を `ccx issue tree <N> [-R <owner>/<repo>]` で確認する。非ゼロ exit した場合は stderr を提示して停止する（飛ばして進めない）。役割分担:

- **充足判定（「レビュー実行」の「Issue 情報が取得されている」項）の対象は当該 Issue の受け入れ条件のみ**。親は横断ルールへの準拠確認と要件解釈の参照に使い、親の受け入れ条件をこの PR の「未実装」として計上しない
- `issues[]` の要素自体が親（`kind` が `parent` / `parent_and_sub`）の場合も同じ役割分担で、充足表には載せない。代わりに `Closes #<親>` の妥当性を確認する: 当該 PR が閉じる Sub 以外の全 Sub が closed（`sub_issues[]` の state）で、親の `release_manual_steps` 節が「なし」マーカーであること（Skill ツールで `github-sub-issues` を起動し、その「本文の節の読み取り」に従って節を引き、マーカーを照合する）。満たさなければ指摘する

### 4. 差分取得と確認

「Issue情報取得」で起動した `pr-reading` の「順序」のうち、`pr.body` から差分までをここで実行する。この節が決めるのはその取得元だけ。

- `local_change` が null でない → コミットメッセージは `local_change.commits[]`、差分は **`local_change.diff.path` が指すファイル**、ファイル一覧は `local_change.diff.files[]` から読む
- `local_change` が null → コミットメッセージは `commits[]`、差分は **`diff.path` が指すファイル**、ファイル一覧は `diff.files[]` から読む
- `pr.body` は `pr_exists` が true ならコンテキストから読む（false では読むものが無い）

### 5. レビュー実行

#### レビュー scope（指摘の in/out を決める唯一の境界）

「重要なことを言う、雑音は出さない」を原則とする。機械的に検出できるものは下記でツールに任せ、選好レベルの指摘は nit として出す。

**原則として指摘しない（他のツールの仕事）**:
- インデント・改行・空白・コーディングスタイルの軽微な揺れ（formatter）
- import 順・未使用変数・型注釈漏れ（linter）
- secrets リーク・既知脆弱性パターン（secrets scanner / SAST）
- これらが CI で未検出のままなら「linter/formatter 設定の不備」として1行触れて良いが、各ファイル個別の nitpick として指摘しない

**レビュー対象（差分全体に常時適用する観点）**:
- バグ・潜在的な問題（実行時エラー、ロジック誤り、競合状態、境界値漏れ）
- セキュリティ上の設計問題（権限管理、入力検証、認証フロー等、SAST が拾わないレイヤー）
- パフォーマンス・スケーラビリティへの影響（明らかなボトルネック、N+1、不必要なネットワーク呼び出し等）
- アーキテクチャ・設計判断（責務分離、結合度、抽象の妥当性）
- 可読性・保守性
- ビジネス要件・仕様との整合性
- テストの妥当性（Skill ツールで `test-implementation` を起動し、その3原則で判定する）

**断定を避ける箇所**:
- アーキテクチャ・ビジネスロジックの妥当性は断定せず質問形 (`〜という理解で合っていますか？`) で提示する
- 負荷・性能への影響は、コードから確認できる事実（設定値・クエリの形・書き込み量等）と、本番の負荷特性・データ分布に依存する影響仮説を分ける。確認できる範囲を検証してから指摘の強度を決め、検証できない仮説だけが残るなら推奨修正ではなく質問形で出す
- シニアエンジニアの判断を置き換えるのではなく、観点として提示する

**指摘の出し切り**: 発見した指摘はすべて一度のレビューで出し切る。

#### トリガー式チェックリスト

各項目は「トリガー（差分内容、または PR の有無・モード・Issue 取得状況）→ 実行する検証行為」で構成する。「レビュー対象」は指摘の分類軸、検証手続きの正は本チェックリスト:

- **トリガーが成立しているのに検証を実行しないまま、総合評価に進まない**。実施済みと数えるのは、検証行為の成果物（grep/Read の結果、列挙したケース、読了した文書）を示せる場合だけ
- トリガーが成立しない項目はスキップしてよい。ただし「トリガー非該当」の判断は事実確認（該当差分の再読・リンクテキストの確認等）に基づかせ、迷ったら実施側に倒す

**差分外コードとの突き合わせ**（`Grep`/`Read`/`Glob` で能動的に確認。純粋なリファクタリング（既存コードの移動・抽出でシグネチャ・実装とも既存のまま）とドキュメント・コメントのみの変更は、本グループのトリガーにならない。ただし移動で参照パス（import 等）が変わる場合は「公開 API/インターフェース/型/関数シグネチャの変更」トリガーの対象）:
- [ ] **新規追加されたコード要素（関数・メソッド・定数・型・フィールド等）がある** → 同ファイル・同クラス/struct 内の同種要素のシグネチャ慣習（引数の型と順序（特に第一引数）、エラー返却スタイル、命名パターン等）と突き合わせ、新規追加分だけが慣習から外れていないか確認する。新規追加を含むファイルごとに個別に実施し、同ファイル内に同種要素が無い場合（新規ファイル等）は同ディレクトリ・同レイヤーの兄弟ファイルを基準にする。比較は近傍の同種要素数件で足りる
- [ ] **公開 API/インターフェース/型/関数シグネチャの変更がある** → 呼び出し元を `Grep` で全て探索し、変更が破壊的でないか確認する
- [ ] **データ構造・スキーマ・列挙型の変更がある** → 同じ構造を参照している他箇所が更新漏れになっていないか確認する
- [ ] **共有モジュール・ユーティリティの変更がある** → 利用箇所への影響（特に副作用やパフォーマンス特性の変化）を確認する
- [ ] **テスト追加の無い挙動変更がある** → 既存テストファイルの場所を `Glob` で探し、対応するテストが存在するか、追加・更新されているか確認する
- [ ] **設定・定数の変更がある** → 同じ設定キー・定数名を参照している他箇所を確認する

**実装内容の検証**:
- [ ] **エラーハンドリング経路、または新たな失敗モードを持つ処理の追加・変更がある**（ハンドリング未記述の場合を含む） → 失敗モードを列挙し、握りつぶし・誤った変換・観測不能な失敗が無いか経路を追って確認する
- [ ] **外部 I/O（DB・API・キュー・ファイル等）の呼び出し追加・変更がある** → 以下の4点をそれぞれ確認する
  - 性能: N+1・ループ内 I/O・データ量増加時の挙動（全件走査・無制限読み込み）
  - 障害時挙動: 依存先障害時のタイムアウト・リトライ・フォールバック
  - 観測可能性: 本番で失敗を観測できるか（ログ・監視）
  - 冪等性: リクエスト・メッセージが再送・再配信されたとき、書き込み・通知・外部呼び出し等の副作用を二重に発火させず処理しているか（副作用を起こした処理の再送には、成否を問わず前回の結果を返す）
- [ ] **DB マイグレーション・スキーマ変更・データ変換がある** → 後方互換性（旧コードとの並行稼働）・ロールバック可能性・実行時の安全性（ロック・データ量）を確認する
- [ ] **条件分岐・境界判定・件数/サイズ/並行度に依存する処理の追加・変更がある** → 差分内の該当ロジックについて境界値（空・0件・null・上限・同時実行）を列挙し、各ケースの挙動を確認する。許可・拒否・対象内かの判定を返す関数では、入力の欠落（nil・空・未ロードのリレーション・デフォルト値）をそれぞれケースに含め、欠落時に判定がどちら側に倒れるかを確認する。呼び出し側へ注意を促す doc comment は安全策に数えない
- [ ] **状態を読み取り、その値を根拠に書き込む処理（採番・上限チェック・楽観ロック等。ストアは DB・ファイル・外部 API・キューを問わない）の追加・変更がある** → 以下をそれぞれ確認する
  - 読み取り元: 書き込み先と同じ一貫性を持つストアである（レプリカ・キャッシュ・スナップショットでない）こと。プロジェクトのルールがプライマリからの読み取りを要する例外を定めている場合は、このケースがその例外に該当するかを判定する
  - 書き込みより前に得た値: 書き込みの根拠になる値（判定・条件・上限・版数等に使う値）のうち、ロック・トランザクションの取得前（取らない書き込みでは書き込みより前）に得たもの（ストアから読んだ値・一緒に取得したリレーション・前の読み取りから引き継いだ条件・一度だけ取得した時刻）、それらから算出した判定、呼び出し元が渡した値を列挙し、「確認した内容」に 1 値 1 行で書く。値ごとに次を確認する
    - 呼び出し元が渡した値以外は、値を得てから書き込むまでの間に別の書き手が書き込んだり書き込みが再試行されたりしたとき、書き込みの時点で取り直すか（ストアから読んだ値は書き込み先から）、または書き込みの条件で変わっていないことを検証しているか
    - 呼び出し元が渡した値なら、信用せず、呼び出し元が操作できない側の状態（書き込み先・検証元のサービス）と照合しているか
  - 再送: 外部 I/O 項目の「冪等性」を、件数・上限の消費にも当てはめて確認する（再送・再配信で二重に消費しないか）

**文書化されたルールとの突き合わせ**:
- [ ] **（常時）** リポジトリの CLAUDE.md に記載されたルール・方針と差分を突き合わせる
- [ ] **（常時）** リンク元 CLAUDE.md のリンクテキスト・周辺説明から、差分の変更種別（新規コード要素・テスト・スキーマ・設定等）に関わるリンク先ドキュメントを特定して読み、準拠を確認する。リンク元の記述だけで関連の有無を判別できない文書は、冒頭を確認してから除外する（主題が PR の中心論点と違うという印象だけで省略しない）
- [ ] **「推奨」等の非必須と記載されたルールからの逸脱がある** → Skill ツールで `finding-triage` を起動し、その「非必須ルールの一様準拠判定」の基準で拘束力を判定する（事実上の必須慣習と判定したら指摘対象にし、nit にしない）
- [ ] **個人ルールモードON時** → 上記3項目と同じ基準を、個人グローバル `~/.claude/CLAUDE.md` にも適用する

**仕様・説明との整合**:
- [ ] **PR が存在する** → PR 説明と実際の変更内容が整合しているか確認する
- [ ] **Issue 情報が取得されている**（`issues` が空でない） → Issue の要件・受け入れ条件を箇条書きに展開し、各項目を「充足（対応する差分箇所を特定）／未実装／逸脱」のいずれかに分類する（結果は「レビュー結果出力」の「Issue要件の充足状況」に反映する）。チェックリストの各項目は、Issue が指定した設計にも他の差分と同じ強さで適用する。Issue との一致は「充足」の行の根拠にし、「確認して問題なしと判断した点」「良い点」の根拠にしない。Issue が指定した設計に問題を見つけたら、Issue に要る修正を添えて指摘として出す
- [ ] **親 Issue が取得されている**（「Issue情報取得」の読解で `parent` の本文を読めた） → 親の横断ルールを箇条書きに展開し、差分がそれに反していないか確認する（違反は通常の指摘として出す。親の受け入れ条件は充足表に載せない）

#### 既存レビュー考慮

過去レビューの対応確認とは別に、新規論点も探す。

コンテキストの各情報の意味:
- **解決済みスレッド（`is_resolved: true`）**: 既に議論・解決済みの論点
- **未解決スレッド（`is_resolved: false`）**: 他レビュアーが指摘済みの論点（補足や異なる観点の言及は重複にあたらない）
- **古くなったスレッド（`is_outdated: true`）**: 指摘後にコードが変更されたスレッド。必要に応じて現状を再確認する
- **ボールの所在（`ball`）・解決可否（`resolvable_by_me`）**: 値の意味は `ccx pr context --help`。`"mine"` のうち自分が出した指摘はステップ 9、自分の PR 上でレビュアーに答える番のものはステップ 10 で扱う
- **PR本体への通常コメント（`comments[]`）**: 補足、Q&A、対応報告、AIレビュー結果（`[AIによるレビュー]` プレフィックス等）とそれへの対応コメントなどが入る
- **レビュー本文（`reviews[].body`）**: 各レビュアーの総括コメント。総合的な評価軸を把握するために参照する
- **コメント引用時**: 取得した `url` を併記する

指摘を確定する前に、投稿前セルフチェックとして以下を確認する（全指摘に常時適用する）:

- [ ] 各指摘を上記のスレッド・通常コメント・レビュー本文と突き合わせ、既に指摘・議論・解決済みの内容の重複や、未解決の既存指摘と矛盾する指摘になっていないか判定したか
- [ ] 「PR コンテキストの読了」の「comments[] の読了手順」を完了したか（特に自分の既存レビューがある場合、その `submitted_at` 以降の comments[] を読んだか）
- [ ] 自分の過去レビューの各指摘について、対応状況の根拠を確認したか（根拠未確認のまま同じ指摘を再提起しない）。**コード修正で対応したと報告されたものは差分が唯一の根拠**で、報告コメントは根拠にならない（差分を確認するまで「対応済み」と認定しない）。コードに現れない対応（説明での決着・スコープ外・別Issue 化）は説明そのものが根拠になる。**過去レビューの nit は本項と「前回指摘の対応状況」の対象外**
- [ ] 自分の過去レビューがある場合、前回指摘への対応確認とは独立に、前回レビュー以降の追加コミットを含む全差分へ全観点を適用したか（「差分取得と確認」「レビュー実行」を対応箇所に限定せず実施していれば満たされる）
- [ ] AIレビューへの対応コメントがある場合、対応後のコード状態を無批判に良いと評価していないか（対応経緯を踏まえて言及する）

**コメントモードON時**: 各指摘の `path:line` を記録する（行を特定できない指摘は body に含め、nit は行コメントにせず `path:line` だけ記録する）。

**自動対応モードON時**: 各指摘に修正対象のファイルとコード範囲（関数・ブロック単位）と修正方針を明記する。

### 6. レビューコメントの原則と口調

本節は「レビュー結果出力」のローカル出力と、PR 投稿の body・行コメントの両方に適用する。

**原則（指摘の中身）**:
- **コードを主語にする**: 「あなたは〜」ではなく「このコードは〜」
- **根拠（なぜ）を添える**: 意見が割れうる箇所ほど根拠を厚くする。ただし要求（何をしてほしいか）が先、根拠は後
- **重要度を明示する**: 各指摘を「必須修正／推奨修正／質問・確認事項／nit」のいずれかに分類する
  - **nit（non-blocking）の判定基準**: 選好ベースで、修正してもしなくても動作・保守性に実質差が出ない指摘。作者は無視してよい。修正の便益（可読性・保守性等の改善）を根拠付きで主張できるなら推奨修正、選好の域を出ないなら nit
- **断定しすぎず質問形も使う**: 前提を見落としている可能性がある場合は確認形にする
- **質問の前に自力検証を試みる**（事実/判断の切り分けはグローバル CLAUDE.md の質問の原則）: 自力検証で解消した項目は質問ではなく「確認して問題なしと判断した点」に置き、「こちらからは確認できない」と書くのは検証を試みた後に限る
- **良い点も書く**: 優れた実装は明示的に評価する。1項目1行程度に留める

**口調（文体）**:
- 中立・簡潔・事実ベースで書く。感情的・誇張的な表現や不要な「！」は避ける
- 断定や指摘で角が立つ箇所は「〜した方がよさそうです」「〜ですかね？」で柔らかくする

**言語**（コメントモードON時）: PR に投稿する body・行コメントは、見出し・定型文も含めて対象 PR の記述言語（PR 本文・既存レビューコメント）で書く。サブエージェントの作業言語に引きずられない。

### 7. レビュー結果出力

自動対応モードのON/OFFに関わらず、レビュー結果は常に出力する。

以下の形式で出力:

```markdown
## レビュー結果

### 総合評価
- Approve可能 / 修正が必要 / 要議論 ← 判定はこの 1 行のみ
- <読めなかった Issue がある場合のみ: 何が読めず、そのぶん何を確認できていないか>

### 良い点
- ...

### 指摘事項
#### 必須修正
- ...

#### 推奨修正
- ...

#### 質問・確認事項
- ...

#### nit（non-blocking・対応は任意）
- <path:line> — ...

### 前回指摘の対応状況（自分の過去レビューがある場合のみ）
- <path:line>: <指摘概要> — 解消 / 未解消 / 議論中（根拠: <確認した差分・コミット、または報告コメントのみ>）

### Issue要件の充足状況（Issue情報が取得されている場合のみ）
- ...
- <読めなかった Issue は「読めず」の行>

### 確認して問題なしと判断した点（該当がある場合のみ）
- <懸念した点> — <問題なしと判断した根拠（参照した箇所）>

### 確認した内容
- 差分: <`pr-reading` の「報告」の1文><`ahead_own` なら: PR の head より先のローカルコミットを含む>
- <実行したテスト・コマンドとその結果（該当がある場合のみ）>
- <書き込みより前に得た値> — <取り直し／書き込みの条件で検証／照合のどれで守られているか>（該当がある場合のみ。1 値 1 行）
```

「確認して問題なしと判断した点」「確認した内容」は指摘ではなく検証記録で、指摘に昇格させない検証はここに置く。前提（「backfill 不要の理解で見ています」等）もここに書く。「確認した内容」の差分の行に何を書くかは `pr-reading` の「報告」が定める。

**総合評価の判定の注意**:
- 以下の判定基準以外の観点（レビュアーとしてのアサイン有無、作成者との関係、遠慮・忖度）で評価を変えない
- **質問・確認事項が残っていても「Approve可能」を「要議論」に格下げしない**。質問を添えて Approve し、質問が対応必須でないことをレビュー本文に明記する
- 「要議論」は「設計判断が割れており、解消しない限り Approve も Request Changes も選べない」ケースに限定する。運用確認レベルの質問は該当しない
- **nit は総合評価の判定から除外する**（nit しか残っていなければ「Approve可能」）
