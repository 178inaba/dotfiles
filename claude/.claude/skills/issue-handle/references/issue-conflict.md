# 「Issue 側の修正が要る指摘」のユーザー確認

ステップ 4（/simplify の finding）と 6-2・6-4（レビュー指摘）の対応リストで「Issue 側の修正が要る指摘」が空でない実行が、その指摘の扱いを確定する前に読む。回答を各呼び出し元の区分へ移すのは呼び出し元の行が定める。

1 指摘 1 問の `AskUserQuestion` を 1 ラウンド（5 問以上なら複数回の呼び出しで 1 ラウンド — ラウンドの定義は `grilling` が持つ）で聞く。`--file` 指定時は、この区分と選択肢の「Issue」を仕様ファイルと読み替え、1 つ目では Issue 本文の代わりに仕様ファイルを書き換える。

各指摘について、Issue の記述と指摘を対等に比べる（Issue が指定していることは比較の重みにしない）。判定とその理由（双方が失うもの、Issue の背景と受け入れ条件にどちらが適うか）を 1〜2 文で推奨選択肢の `description` に書き、推奨選択肢を先頭に置く。推奨選択肢は判定で決める:

- 指摘が優れる →「Issue を修正して指摘を適用する」。ただし修正が Issue のリリース単位（`github-sub-issues` の「運用規約」）の外にあるなら「別 Issue として起票し、ここでは対応しない」
- Issue の記述が優れる →「Issue を維持して対応しない」

選択肢:

- 「Issue を修正して指摘を適用する」→ 適用する（修正方針は指摘が提案した修正）。修正の適用より前に、親セッションが Issue 本文を取り直し、その写しを指摘が挙げた修正で書き換えて `gh issue edit <issue-number> -R <owner/repo> --body-file <path>` で更新し（本文の既存言語で書く）、書き換えた旨を報告する
- 「別 Issue として起票し、ここでは対応しない」→ 適用しない。親セッションが `gh issue create -R <owner/repo> --assignee @me --title <title> --body-file <path>` で単独の Issue（現 Issue の親の Sub にしない）を起票する。本文は指摘と Issue に要る修正で、対象リポジトリの言語で書き、本構成のスキル名を出さない
- 「Issue を維持して対応しない」→ 適用しない
