# 「Issue 側の修正が要る指摘」のユーザー確認

6-2 の対応リストで「Issue 側の修正が要る指摘」が空でない実行が、対応リストの確定後の分岐より前に読む。

1 指摘 1 問の `AskUserQuestion` を 1 ラウンド（5 問以上なら複数回の呼び出しで 1 ラウンド — ラウンドの定義は `grilling` が持つ）で聞き、回答で各指摘を移す。`--file` 指定時は、この区分と選択肢の「Issue」を仕様ファイルと読み替え、1 つ目では Issue 本文の代わりに仕様ファイルを書き換える。

- 「Issue を修正して指摘を適用する」（推奨として先頭）→「対応する指摘」へ（修正方針は指摘が提案した修正）。修正の適用より前に、親セッションが Issue 本文を取り直し、その写しを指摘が挙げた修正で書き換えて `gh issue edit <issue-number> -R <owner/repo> --body-file <path>` で更新し（本文の既存言語で書く）、書き換えた旨を報告する
- 「別 Issue として起票し、ここでは対応しない」→「対応しない指摘」へ。親セッションが `gh issue create -R <owner/repo> --assignee @me --title <title> --body-file <path>` で単独の Issue（現 Issue の親の Sub にしない）を起票する。本文は指摘と Issue に要る修正で、対象リポジトリの言語で書き、本構成のスキル名を出さない
- 「Issue を維持して対応しない」→「対応しない指摘」へ
